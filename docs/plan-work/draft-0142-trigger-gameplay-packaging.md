# Draft：Trigger 玩法类型与数据包包装

状态：draft — 玩法分类与作者包装建议，待裁定；不构成实现授权

## 目标

回答“监听某事物变化并最终反应”的玩法通常有哪些类型，并提出一套谨慎、可理解、可逐步开放的数据包包装。目标是避免把所有条件规则都塞进通用 `TriggerDef`，同时让确实属于事件联动的玩法可以由数据包作者表达。

## 设计边界

- 本文是设计草案，不改变当前 `TriggerDef`、`TriggerSystem`、事件目录、Schema 或运行时行为。
- 现有 Trigger 的执行模型是：选择受支持的事件类型 → 可选过滤 → 可选条件 → 执行 `Effect[]`；`once` 默认开启。支持的侦测类型以 `src/engine/types/trigger.ts` 为准。
- `revealTriggers` 是信息揭示规则；Affector 条件是持续效果激活规则；StoryEntry 的可用条件、奖励条件和进入效果各有自身语义。字段名相似不代表适合合并。
- 一项玩法若能用更窄、更安全的领域声明表达，应优先使用该包装；通用 Trigger 负责真正的“事件发生后做反应”。
- 不在本草案中增加任意 EventBus 事件名、脚本回调、任意代码表达式、存档迁移或无限重复行为。

## 当前事实与代码落点

- `src/engine/types/trigger.ts` 定义 `TriggerEventDef`、`TriggerDef`；目前侦测面为 tick、resource、spotLevel、item、story、init、area、shop、character、cultivated。
- `src/engine/effect/trigger-system.ts` 负责订阅映射、过滤、条件检查、效果执行与 once 状态；状态写入仍经 Effect / StateMutationService 管线。
- 默认内容在 `src/arona-clicker/content/triggers.ts` 声明 Trigger；AronaClickerCore 的 JSON 分片和 addition_test 也提供数据包实例。
- `StoryEntry.reactions` 是已存在的局部反应包装：完成后派生运行时 Trigger，并按 StoryEntry / Init 生命周期挂载。
- `StoryEntry.followUps` 是受限的剧情后续包装；它等待进入指定 Area，再尝试启动 StoryEntry，不是通用 Trigger。
- `revealTriggers` 用于实体存在性和信息层级揭示；`enterEffects`、故事条件奖励和 Affector 条件也各自有单独入口。

当前挂载事实补充：`TriggerSystem` 已支持按 group 挂载和卸载；卸载定义不清除 `triggersCompleted`。Init 切换会卸载旧 Init group，再挂载新 Init 的 Trigger；Lobby 不挂载 Init 专属 Trigger。当前 Registry 以完整启用集构建只读视图为主，因此本草案中的“部分加载”需区分 Trigger 有效集切换与未来 Datapack 内容按需解析。

## 玩法分类

| 玩法类别 | 典型“监听 → 反应” | 建议包装 | 与通用 Trigger 的关系 |
| --- | --- | --- | --- |
| 里程碑奖励 | 累计产出达到 100，发奖励/旗标/剧情 | `milestone` 领域规则，或受限的 resource/stat Trigger | 是；重点是阈值跨越与一次性语义，需避免每次资源变化都重复结算 |
| 状态变化响应 | 某 Spot 升级、物品获得、故事完成后执行效果 | 通用事件 Trigger | 是；典型通用 Trigger 用例 |
| 角色成长联动 | 招募角色、突破星级、获得经验时解锁内容或发奖励 | 角色领域事件规则；简单效果可用 Trigger | 是；事件过滤应能按角色或培养类型收窄 |
| 交易/消费反应 | 完成指定 Shop 购买后奖励、计数或解锁 | Shop 交易结果规则 | 是；应在交易成功提交后触发，避免支付校验阶段误触发 |
| 剧情完成后反应 | 故事完成后等待某事件，再执行效果 | `StoryEntry.reactions` | 是，但建议保持 StoryEntry 局部挂载和明确生命周期 |
| 剧情串接 | 故事完成后等待进入区域，启动下一段剧情 | `StoryEntry.followUps` | 是“事件驱动”但不应开放任意 Trigger；目标和结果保持窄类型 |
| 解锁/揭示 | 达到资源/旗标条件后显示实体、名称或效用 | `revealTriggers` / 领域解锁字段 | 否；它表达可见性或可用性，不是发生事件后执行副作用 |
| 进入时结算 | 进入 Init / Area 时按条件给效果 | `enterEffects` | 通常否；这是入口时机上的一次性结算，应有专用 first/条件语义 |
| 持续条件效果 | 持有强化、库存变化或条件满足时持续产出/加成 | Affector | 否；条件决定激活状态，持续产出有独立求值通道 |
| 周期/冷却玩法 | 每隔 N Tick 发放、冷却结束后再次触发 | 受限 timer/cooldown 机制 | 可由 Trigger 承载侦测，但频率、重置和保存语义需领域化，避免裸 `tick` 轮询膨胀 |
| 组合收集/进度任务 | 收集 N 种物品、完成一组故事、持有若干标签后领奖 | Quest/Objective/Progress 机制 | 不建议直接堆叠 Trigger；需要显式进度、聚合与完成状态 |
| 连锁反应 | 一个效果又引发另一个事件并继续响应 | 通用 Trigger 有风险 | 需防循环、重复执行和单帧级联；应通过效果/事件策略另行裁定，不作为首批作者能力 |

## 建议的包装层级

### A. 保留领域专用声明

继续使用 `revealTriggers`、`enterEffects`、Affector、StoryFollowUp、故事奖励等高层 API。这些 API 把意图和合法操作收窄，能让内容审查、编辑器字段提示和验证规则更清楚。

### B. 提供受限的通用反应规则

对没有合适领域包装的事件响应，提供单一的 `reactions` / `triggerDefs` 类能力。推荐作者心智模型为：

```text
当 [一个受支持的事件] 发生，且 [可选过滤 + 条件] 成立时，执行 [有限效果]；[执行策略]
```

设计时将其拆为四块，而不是让作者接触事件总线细节：

1. **When**：事件种类及可选对象过滤；只能选择登记过、可测试的事件。
2. **If**：可选 Condition；应明确它是在事件发生时求值，不代表持续订阅任意状态依赖。
3. **Then**：有限的 `Effect[]`；状态写入继续走现有 mutation 管线，演出效果交给现有领域宿主。
4. **Policy**：执行次数、作用域及去重身份；默认一次，重复行为必须显式声明并说明上限/间隔。

### C. 对常见玩法提供更语义化的快捷包装

在通用反应规则稳定后，再评估 `milestone`、`story reaction` 等作者常用包装。它们可编译/派生为内部 Trigger，但作者不必处理底层事件映射、持久化 ID 或运行时挂载组。派生关系必须可诊断且不产生第二套事实状态。

## 部分加载下的准入与准出

### 目标与术语

“准入/准出”指规则定义仍属于内容，但因来源启用状态、实体拥有者状态、当前 Init 或局部生命周期而进入/离开 TriggerSystem 的**运行时有效集**。这不等同于从内容源删除定义，也不自动重置 once 进度。

准入分成四个判断层：

1. **来源可用**：所属 Datapack / 内容源存在且处于有效加载集。
2. **拥有者有效**：局部反应所属实体满足激活前提，例如 StoryEntry 的完成状态已提交。
3. **作用域匹配**：全局、当前 Init 或局部 StoryEntry 作用域有效。
4. **监听有效**：规则进入 TriggerSystem 事件分桶；退出时移除监听索引，不擅自改写持久完成状态。

四层均通过才算准入。Condition 通常仍在匹配事件发生时求值，不应默认把它当作挂载资格；若要“条件满足才挂载”，应另设 `eligibility` 语义并说明如何侦测其失效。

### 状态模型

```text
unavailable ──来源/拥有者/作用域满足──> admitted
admitted ──来源暂失或作用域离开──────> suspended
suspended ──重新满足────────────────> admitted
admitted ──once 执行完成────────────> consumed
任意有效态 ──定义从内容移除─────────> retired
```

- `unavailable`：定义未在当前内容集，或所属来源未启用。
- `admitted`：当前能够响应符合 `on` 的事件。
- `suspended`：定义仍存在，但暂时不应监听，例如离开所属 Init。
- `consumed`：once 已完成；重新准入也不再执行，除非显式重置规则另有定义。
- `retired`：作者从权威内容源删除定义；如何清理其运行进度属于独立内容/存档治理。

运行时可把 `unavailable` 和 `suspended` 都表示为“未挂载”，但只读诊断应能说明原因。

### 准入规则建议

1. **启用集加载**：完成 Registry 合并与引用校验后再装配全局规则；加载失败不能留下新旧混合的监听集。
2. **进入作用域**：进入 Init 后准入该 Init 的规则及已满足拥有者前提的局部反应；Lobby 不准入 Init 专属规则。
3. **拥有者提交后**：局部 Reaction 在所属实体完成状态正式提交后准入，不能在演出开始或奖励预览时提前挂载。
4. **重建而非补发**：重新准入只建立监听，不回放离开期间错过的事件，也不立刻对当前状态补触发。需要当前状态对账的玩法应使用明确的 milestone/reconciliation 语义。
5. **原子替换**：来源切换时先构造并校验目标有效集，再一次性替换监听集。
6. **幂等准入**：重复收到准入请求不能重复订阅、触发效果或改变已消费状态；按稳定逻辑身份去重。

### 准出规则建议

准出撤销“当前可响应”资格，但不默认撤销规则身份和进度：

- **离开 Init / 局部作用域结束**：卸载该作用域监听，保留 once 完成记录；再次进入只恢复未消费规则。
- **Datapack 停用/移出加载集**：撤销该来源当前规则；玩家进度是否保留必须与存档的包卸载语义一致，不能只依赖内存 Map 的删除。
- **局部实体暂不可用**：暂停局部监听。只有作者正式删除定义时才进入 retired 候选。
- **定义编辑替换**：仅改文案不应意外重置 once；事件、条件或效果变化是否沿用进度要明文规定，不能让结构哈希悄悄决定身份。
- **多来源/多拥有者共享**：只要仍有一个所有者有效，就不能因另一所有者准出而卸载；须用来源记录或引用计数，避免最后写入者覆盖。

### 身份与进度

建议逻辑身份由“来源命名空间 + 拥有者身份 + 作者规则 ID”组成，例如：

```text
<modName>:<owner-kind>:<owner-id>:reaction:<rule-id>
```

序列化格式待定；不同 Mod、实体和作用域中相同的局部 ID 必须隔离。运行时 group 只作卸载索引，不直接充当存档身份。省略 ID 时应在局部列表内校验并提示；不建议把结构哈希当长期进度身份，因为编辑内容会改哈希并丢失 once 连续性。

需裁定 once 是否跨 Init 保留、来源临时卸载时是否保留、Mod 永久删除时何时清理孤立进度，以及 ID 冲突和定义更新如何报告。本草案建议：**临时准出保留进度，重新准入沿用稳定身份，正式删除产生可审计的 orphan/retired 记录，由独立策略清理**；准出本身不清除 `triggersCompleted`。

### 重叠加载与并发边界

- 重复启用通知、Datapack 重载和 Init 重入应幂等；规则 ID 冲突须在合并/校验阶段拒绝或显式解决。
- 局部规则只由有效拥有者准入；共享规则需声明可审计来源。
- 事件派发中发生准出时，当前回调是完成还是取消必须固定；之后的事件不得再命中已准出规则。
- 作用域切换应在派发边界原子生效，避免一个事件同时命中新旧 Init 规则。
- 不得出现“事件类型已注册但定义未校验”或“旧来源已卸载而新来源只挂一半”的可见状态。

### 诊断与验收

只读诊断应显示规则来源、身份、拥有者、作用域、准入/准出原因、监听事件、once 状态和定义版本/指纹。诊断不能成为第二份事实状态，也不能触发事件回放。

实现至少验证：包启停/替换/失败原子性、Init 与 Lobby 切换、StoryEntry 完成后准入、暂停期间不补发、once 准出再准入、ID 冲突和定义编辑、孤立进度处理、回调中的加载集切换，以及无重复派发/重入风暴。

### 建议的首发范围

1. 先对完整 Registry 提供 **Trigger 有效集的原子准入/准出**；不同时承诺任意内容表按需分块解析。
2. 先限定全局、当前 Init、StoryEntry 局部三种作用域，不开放任意 group 字符串给作者。
3. 离开作用域视为 suspend/unmount 并保留完成记录；永久内容移除的进度清理另行治理。
4. 首发不做错过事件补发、准入即检查、任意时间窗或任务型累计进度。
5. 若未来需要 Registry 内容真正按需加载，另立数据包生命周期/依赖解析设计，复用稳定来源身份和原子切换原则。

## 建议的执行策略词汇

目前的 `once` 可以支持第一步，但草案建议先统一产品术语，后决定是否扩展模型：

| 作者语义 | 建议含义 | 初始建议 |
| --- | --- | --- |
| `once` | 首次条件满足时消费并执行一次 | 默认行为，优先保留 |
| `repeat` | 每个匹配事件都可执行 | 谨慎开放；必须有明确的事件粒度和防刷边界 |
| `maxRuns` | 最多执行 N 次 | 可作为有限重复的安全上界；需定义次数状态归属 |
| `cooldown` | 两次执行至少间隔 N 帧/事件 | 不与 maxRuns 混为一谈；依赖时间状态 |
| `scope` | 全局、当前 Init 或实体/剧情局部 | 先选定少量有清晰生命周期的作用域，不允许任意字符串组 |

这些是候选作者语义，不是现有类型保证。实施前需确认 `once`、`maxRuns` 和存档状态的实际当前语义，并避免在一个字段里混合“什么时候监听”和“何时重置”。

## 谨慎开放的建议

1. **第一阶段只开放白名单事件**：继续沿用已映射的 `TriggerEventKind`；新增事件须连同 `GameEvent`、`EVENT_CATALOG`、映射表、Schema 与测试一起登记。
2. **一次性优先**：默认执行一次；暂不把无限重复作为普通内容作者的默认选项。对必须重复的具体玩法，先由领域规则给出限制。
3. **控制触发时机**：条件在匹配事件到达时检查；不承诺“初次挂载即检查”或后台持续轮询，除非某类包装明确规定。
4. **隔离副作用**：事件只提供触发上下文，效果仍走 EffectEngine / StateMutationService；不要在 Trigger 中加入脚本或直接状态写引用。
5. **避免自激与循环**：识别 Trigger 效果可能再次发出侦测事件的路径；测试重复事件、级联和重入，必要时设置每次派发预算或禁止某些反馈组合。
6. **定义存档身份**：持久完成状态要有稳定、可解释的 ID 与清晰状态层。不得依赖数组下标；匿名结构哈希对内容改写后的 once 状态连续性需要单独决策。
7. **保持局部生命周期**：实体拥有的反应跟随实体激活/完成状态挂载和卸载；不要因为使用同一 Trigger 引擎就把所有实体规则提升为全局常驻监听。
8. **提供诊断投影**：编辑器应能说明规则来源、当前是否已挂载/完成、最近不执行的主要原因；诊断只读，不生成或改写运行状态。

## 推荐的首轮范围

- 先确认当前通用 Trigger 的实际使用覆盖、一次性/重复语义、状态持久化和事件条件检查时点。
- 维持现有 `TriggerDef` 能力，对外文档按 `When / If / Then / Policy` 解释；不新增 `TriggerEventKind`。
- 以“资源里程碑”“Spot 等级变化响应”“StoryEntry 完成后的局部反应”三个内容样例验证作者是否能准确表达意图。
- 将揭示、进入结算、持续效果、剧情串接和累计任务作为对照样例，确认它们仍由窄领域包装处理。
- 在编辑器支持前，先确定事件过滤器的合法字段、条件求值时机、生命周期和测试矩阵。

## 施工切片

当前没有获准的代码施工切片。建议裁定后按下列顺序另立实现范围：

### P0：准入生命周期与当前行为核验

- 核实 `TriggerSystem` 的事件匹配顺序、条件求值时点、once/maxRuns 行为、ID 分组、保存层级和卸载语义；梳理 Datapack 启用集切换与局部来源装配时序。
- 核对当前数据包实例并选出覆盖三类典型玩法的最小样例。
- 裁定“部分加载”具体指 Trigger 有效集切换还是 Registry 内容懒加载，并产出准入/准出状态与不支持清单。
