# Draft：GALHCG 内容维护体验与闭环问题

状态：draft — 已归纳 ACProgram 调用侧的维护摩擦与既有复现；GALHCG 服务实现尚未核对，未裁定改造范围

## 目标与最终方向

让项目维护者能从“文档、源码或目录已变更”出发，清楚判断 GALHCG 图谱哪些清单、Evidence owner 与关系需要处理，并在有限且可见的范围内完成可复核更新。流程应保留现有项目身份核验、版本令牌、dry-run、批次限制与提交审计，同时减少调用者手工串联工具、猜测分页参数和从大段结果中寻找下一步的负担。

本 Draft 讨论 GALHCG 图谱内容维护及其调用体验，不把内容陈旧、文件清单差异、工具合同不清和服务端实现缺陷混为一谈。它不授权修改 GALHCG 服务，也不意味着需要重建 ACProgram 全图。

## 本阶段玩法语义与边界

- 已裁定：`project_id` 只用于选择项目命名空间；每次项目调用仍须显式绑定身份，不能由项目名或默认项推断。
- 已裁定：`refresh` 只维护文件清单；它不会自动重建 Concept、推断 `maps_to` 或证明新旧文件语义等价。
- 已裁定：Evidence 更新须基于实际读取的 `{path, version_token}`，逐批完整 dry-run 后提交；多批不是整体事务。
- 已裁定：归档位置不代表目标完成；历史 Goal Set、Draft 和 Task 的生命周期不能仅凭路径推断。
- 明确暂缓：自动按同名路径重绑概念、自动删除历史图节点、无范围限制的全图修复、绕过忽略规则的磁盘盘点，以及未核对服务源码即归因的“服务端 bug”。
- 本 Draft 聚焦维护者如何发现、理解并处理变化；GALHCG 服务端实现与工具产品语义需在对应项目核验后另行裁定。

## 候选问题分组

1. **变更发现与归属**：清楚列出变更路径、受影响 node/edge owner、直接依据数量、当前文件是否可解析及需人工判断的迁移关系；与现有 `review_changes`、`audit_manifest_disk`、`map_inventory` 能力对照，避免重复建设。
2. **维护步骤与部分提交**：将 refresh、差异审查、当前令牌获取、更新预检/提交及写后检查呈现为有范围的维护清单；每批明确已提交、失败和待处理内容，不承诺跨批原子性。
3. **范围与分页体验**：调用前明确过滤条件、预算与可能的截断；返回可直接续用的参数；区别普通续页、预算截断和 revision 变化后的游标失效。
4. **维护结果可读性**：摘要说明“发生什么、依据什么、接下来做什么”，保留 effective query、完整性、参数钳制原因和逐 owner 证据供审查；不要只返回成功/失败总数。
5. **维护状态与 freshness**：分别表达已观察变化、已更新 Evidence、最近 freshness 观察与未检查 owner；禁止从 `status` 快照、已刷新文件清单或 `confirmed` 推断全库当前正确。

以上是待研究的问题组，不是已经选定的服务功能或实现设计。
