# Draft：超级图鉴与游戏内内容编辑工作区

状态：active — 阶段 A/B 于 2026-10-15 完成施工与验收；阶段 C 编辑器迁入与阶段 D 扩充仍保留后续。Draft继续作为C/D设计来源。

> 本文回答：怎样基于现有 Datapack、定义引用和游戏内 Runtime Editor，提供容易查阅、容易追踪引用、与编辑工具共用框架的超级图鉴。

## 1. 推荐方向与需求解释

推荐：**一个内容工作区，两种工作视图；图鉴读当前生效内容，编辑器写指定编辑态数据包。** 两者共用导航、列表、资料页和关系行的界面结构，保留各自的数据边界与命令入口。

按本轮需求，将图鉴主详情理解为两部分：

1. **本体资料**：名称、说明、关键定义字段，以及经过解释的功能、条件和效果。
2. **被哪些内容使用**：列出引用当前条目的实体，说明用途，点击可继续查阅。

“它又引用了什么”不作为常驻主表；所属区域、目标剧情等必要信息可直接作为资料里的可点击字段。完整向外引用、字段路径、字段树、JSON 放进按需展开的“技术详情”，避免阅读时出现三套内容重复。

这里的图鉴是内容资料库，首期继续显示当前加载的完整定义，不按玩家收集进度隐藏。已有收集图鉴、角色通讯录和玩家背包保持各自语义；若将来需要玩家防剧透版，应增加独立可见性投影，不能直接开放当前全量查询给收集流程。

本轮交付为背景调查和处理建议，不改变功能、数据字段、Schema、存档或包内容。下文“建议”“拟”均不代表已实现或已裁定。

## 2. 当前项目背景：已有基础比外观成熟

### 2.1 内容有三个不同来源层次

| 层次 | 当前事实 | 对界面的影响 |
| --- | --- | --- |
| 包库 | PackManager 保存包记录、版本、启用选择、编辑态副本；以 `packRecordId` 定位具体记录 | “正在编辑哪个包”不能仅用 Mod 名或 ID 前缀判断 |
| 当前生效内容 | Registry 按加载顺序合并，同 ID 后载覆盖；查询层再补充当前 AffectorPack / TriggerDef | 图鉴默认只读最终有效结果，不是所有已导入文件，也不是覆盖历史 |
| 编辑草稿 | Runtime Editor 维护表单暂存、Draft、最近成功应用快照及移除状态；本地长效保存 | 未保存输入、已保存草稿、当前生效版本必须能区分 |

多数全局实体使用三段式 ID，但角色键、资源、标签、单例配置和玩法 B 局部对象不都遵循同一种身份语义。`xxxId` 字段也可能是局部键或状态键，不能统一当成 Registry 外键。

证据：`src/data-services/contracts/datapack.ts`、`src/data-services/registry/registry.ts`、`src/data-services/contracts/runtime-content-browser.ts`、`src/ui/runtime-editor/state.ts`，以及 [[docs/docs-829/03-data-structures/datapack-contracts]]、[[docs/docs-829/04-mechanisms/data-services/pack-loading]]。

### 2.2 超级图鉴已经具备的能力

- `runtimeContentBrowser` 从 Registry 公开 getter 发现内容类型，提供只读快照、搜索、详情、正反向引用；补充源可枚举 Runtime 的 AffectorPack 和 TriggerDef。
- 已有“包／类型与条目／详情”三栏、窄屏栏位切换、跨条目跳转和前进／返回。
- 已有概览、关系、原始数据三个详情页签；语义摘要和完整字段树可作为友好资料与技术兜底的基础。
- 图鉴不要求先选择编辑态包。没有可靠来源信息的条目会进入“Runtime 有效配置”，不会仅按命名空间猜包来源。
- 点击条目和详情页签已经有局部更新及节点保留测试，不应退化为整页重建。

主要入口：`src/ui/runtime-editor/codex/`、`codex-details/`、`view.ts`、`actions.ts` 和 `src/data-services/registry/runtime-content-browser.ts`。

### 2.4 用实际发布内容核对覆盖规模

本轮在内存 Registry 依次装载 `base@1.0.2`、`gameplay-b@1.0.0`、`gameplay-b-strategy-park@1.0.0`，没有改动包库或玩家状态：

- 查询得到 **30 个非空类型、453 个目录条目**。条目包含派生的 `storyEntries` 和单例，不能称作 453 个独立原始实体；该统计也没有接入 Runtime 规则补充源。
- 其中只有 **47 条带查询层的可靠 `sourceMod`**。这反映查询适配覆盖，而不是其余内容真的没有来源。
- 六类玩法 B 定义均可被通用浏览器发现，但缺少专用资料 Profile：Event 5、Location 21、Action 56、Student Profile 11、Strategy Profile 3、Card Pool 7。

这些数字只描述上述固定装载集，不推断用户当前实际启用了哪些包。来源核对使用发布 base JSON 与当前两份 TS 样例，而非旧测试数据包。

## 3. 需要优先处理的问题

### 3.1 已复现：反向引用展示丢失了引用者

查询层边有 `source → target`。但 `view.ts: inspectorView` 将 incoming 和 outgoing 都交给同一个只取 `target` 的适配器；查看 B 的“引用它”时，行里的跳转目标仍是 B。

本轮用内存样例验证：设施 A 的 `areaId` 指向区域 B，查询返回 incoming 的 source=A、target=B，而关系页输出的按钮仍指向 B。这个问题会直接破坏本次最重要的用户路径。

建议：共享关系行显式带原始 source、target、方向与来源字段路径；入向行显示、跳转 source，出向行显示、跳转 target。不要通过互换整条边来丢掉原始语义。

### 3.2 已复现：启发式引用不等于可靠关系

当前 `collectReferenceStrings` 会扫描看起来像三段式 ID 的字符串，也会扫描名称以 Id/Ids 等结尾的字段。`diagnosticFor` 只按全 ID 查候选，`targetKind` 目前没有参与候选类型过滤；`relationMetadata` 主要由末级字段名产生标签，还不是契约驱动的完整语义模型。

本轮内存样例中，普通说明 `text:looks:qualified` 与嵌套局部 `actionIds: ['local-action']` 都被报告 missing。玩法 B 的 actor、track、fact、position、scene 等局部对象尤其不能据此报全局缺失。数组末级为数字时，部分已知字段还会退回“推断”。

建议分离：**关系类别与作用域、解析状态、规则覆盖程度**。明确规则生成主界面的关系；未登记字段只进入技术详情里的“可能相关”，不计入确定错误，也不参与阻止保存／删除。

### 3.3 来源、命名空间和版本不能混作一件事

查询层 `ownerOf` 当前只读取 Init / Area / Spot 的来源方法。Registry 还存在 `characterVariantOwnerOf`、`resourceDisplayOwnerOf` 等可靠入口，尚未全部接入；其它表也没有一个已被查询层采用的统一来源合同。

例如加载包可以覆盖 `base:...` 的定义，所以 `base` 前缀不证明最终来自 base 包。当前图鉴侧栏的包名与数量会因此给人“选包后很多内容消失”的感觉。

建议首期先补接已有可靠来源方法，始终提供“全部生效内容”和“来源暂不可确认”。需要完整按包浏览时，沿实际加载／覆盖步骤建立统一的定义来源投影，并由 Runtime 装配关联包库记录及版本。未完成前不得展示猜测来源；不为补来源而在基础 Data Services 反向读取产品包库。

### 3.4 UI 同样式不等于共用结构

现有内容浏览器虽然复用了图鉴 CSS，但布局和图鉴并非一个组件。图鉴仍有 `SOURCE RAIL / QUERY DECK / DEF INSPECTOR`、Mod、Def 等主标签，详情也重复出现身份信息。

另有两点需保留边界：

- Runtime Editor 是挂在 body 的浮动工具宿主，不随游戏 `#app` 路由重建。
- 工具目前采用局部 `--re-* / --codex-*` 固定配色，与普通游戏工作区的 Presentation 主题宿主不同；两套局部强调色也尚未完全一致。

建议统一工具内部的框架、颜色角色和控件，先继承现有浅色工具表面与图鉴强调色，不自动把工具变成随场景换肤的游戏面板。这个视觉方向属于待裁定建议，施工后再补入 `ui-style/`，本轮不把建议写成既定风格规范。

## 4. 用户看到什么

### 4.1 桌面布局

```text
超级图鉴                 [浏览生效内容] [编辑数据包]          [关闭]
范围：全部生效内容        编辑时：目标包名称与版本
┌──────────────────┬──────────────────────┬─────────────────────────────┐
│ 内容分类          │ 搜索名称或标识       │ 信用点制造机                │
│ 世界与设施        │ [名称、说明、ID…]    │ 设施 · 来源包／来源待确认    │
│ 角色与培养        │                      │ [资料] [被引用] [更多]      │
│ 物品与经济        │ 信用点制造机         │                             │
│ 剧情与对话        │ 通信终端 …           │ 名称、说明、所属区域        │
│ 行动与场景        │                      │ 功能、购买、升级、条件      │
│ 外观与素材        │ 名称优先，ID 次级    │                             │
│ 规则与配置        │ 当前类型与结果数     │ 被引用：引用者＋用途＋跳转  │
│                  │                      │ 技术字段默认收起            │
│ 包筛选／编辑目标  │ 编辑时：[新建设施]   │ 编辑时：同位置承载表单      │
└──────────────────┴──────────────────────┴─────────────────────────────┘
编辑时固定操作区：草稿保存状态／待应用数量       [检查改动] [应用改动]
```

这是一张结构线框，不是已完成的视觉验收。重点是把常用“内容分类”提到左侧，包筛选降为范围工具；不再要求先理解 Mod 才能找东西。

左栏分类来自对真实 kind 的展示映射，不新增数据包枚举。一个类型只进入一个主分类，未登记的新类型进入“其它内容”兜底。单例配置进入“规则与配置”；派生 `storyEntries` 不与原始剧情入口并列制造重复感，必要时在技术视图标明派生来源。

### 4.2 “资料”页的展示层级

| 内容 | 用户默认看到 | 按需查看 |
| --- | --- | --- |
| 身份 | 名称、类型中文名、来源、简短说明 | 完整 ID、命名空间、版本、复制标识 |
| 简单字段 | 标签／值，例如“所属区域”“等级上限” | 原字段名与路径 |
| 复杂字段 | 功能行、条件描述、费用行、奖励行、集合摘要 | 完整集合及表达式 |
| 引用字段 | 目标名称与可点击链接；找不到时保留原标识 | 解析证据和字段路径 |
| 未专门包装字段 | 折叠“其它定义字段”，保证可查 | 字段树与原始 JSON |
| 运行中状态 | 本体资料首期不混入库存、等级、拥有状态 | 将来需要时增加独立“当前游戏”投影 |

本体资料展示静态定义，例如“每 Tick 产出”的定义说明；不把随世界线、等级、Buff 改变的当前收益伪装成固定数据。可沿用现有语义摘要，但需要分类型组织、去重和中文标签，不只是把内部字段全摊开。

首期优先四类编辑内容，并补资源、物品、角色原型／差分、剧情入口和六类玩法 B 的基本资料。其余类型保留通用友好字段兜底；不能为了等所有专用页面而隐藏已有数据。

### 4.3 “被引用”清单

每个引用者一组，默认展示三列：**引用者、用途、查看**；类型与包作为次级说明。多处引用合并在该组，显示“3 处使用”，展开后看人类可读位置，技术路径再展开。

真实内容例子：查看“信用点”时，“信用点制造机”应合并成一组，分别说明购买费用、升级费用、资源生产；查看“信用点制造机”时，`base:area:schale_main` 是一个引用者，而制造机自身升级效果的引用应单列为“自身使用”，不算外部引用者。

规则：

- 分组键是引用者的 `{definitionKind, fullId}`，不是目标或展示名称；计数区分“引用者数”和“引用位置数”。
- 默认只列直接静态引用。沿行点击可继续追踪，不默认计算传递闭包，不把间接依赖显示成直接使用。
- 自引用单列；派生视图重复引用和 Runtime 生成规则来源单列，不能虚增作者实体数量。能证明生成规则 owner 时归到 owner 的位置说明，不能证明时保留独立技术条目。
- 歧义边进入“可能使用”，与确定引用分开；不能把同 ID 的所有候选都列为确定使用者。
- 没有结果时显示“当前范围内未发现直接引用”。覆盖不完整时附上范围提示，不声称“可安全删除”。
- 来源跨包的引用仍可打开。保持原列表筛选，右侧显示当前条目位于筛选外及“在列表中定位”；只有用户点击定位才调整筛选。
- 返回历史至少保存条目、详情页签和详情阅读位置；跨包定位后返回还原之前的列表范围。历史有明确容量上限，候选失效后清理。

### 4.4 编辑与新建的完整路径

1. 在同一外壳切到“编辑数据包”，选择具体编辑态记录。顶部持续显示目标包名与版本，浏览范围和写入目标分别呈现。
2. 首期列表默认只显示目标包支持的四类内容；用户可切到“参考其它内容”，此时只读，并可将目标选入引用字段。
3. 点“新建设施”等按钮，右栏进入同风格表单。先填写名称、标识、必要归属；高级集合分区按需展开。Init 创建继续承接默认 Area 辅助。
4. 引用字段以名称搜索、类型约束、来源说明和次级 ID 呈现，沿现有候选查询合并已保存的同包草稿；未提交的无效条目不能成为合法候选。跨包合法性最终由既有领域校验判断。
5. “保存草稿”只写编辑草稿；“检查改动”展示新增／修改／移除及验证问题；“应用改动”走既有内容命令，并显示实际提交结果。导出包保留为次级动作。
6. 切条目、切包、从表单进入引用资料时，先以条目键暂存输入；不要继续用一个无归属的 `formDraft` 覆盖不同条目的编辑。引用查看可占用右栏的只读子视图，“返回编辑”恢复原表单、焦点与阅读位置。
7. 支持修改且能证明目标包 owner、字段可无损往返时才提供“编辑此内容”。只读发布包引导进入现有“创建编辑态副本”流程；首期不提供任意跨包覆盖／复制实体。

首期编辑器的“被引用”采用当前生效版本，明确标注该范围；尚未应用的新条目显示“尚未生效，暂无运行中引用记录”。草稿候选用于表单选择，**不冒充已经建立了草稿全量引用索引**。草稿影响分析可在后续基于候选启用集的独立只读快照实现。

窄屏复用“分类／列表／详情”的单栏切换，两种视图都支持；切换只改变可见性，保留输入与滚动节点。按钮保留明确文字和键盘焦点，长名称与 ID 可换行，关系不能只靠颜色表达。

## 5. 关系和来源的实现方案

### 5.1 保持只读查询与内容写入分离

```text
Registry + Runtime 规则补充源
    → 只读内容／关系查询 → 图鉴资料适配器 ┐
                                        ├→ 共享内容工作区
目标编辑态包 + Editor Draft → 编辑适配器 ┘
用户动作 → Controller → 已有 GameCommands → 校验／应用／回写包
```

图鉴组件不读取包库文件、不持有 Registry 写引用、不写玩家状态。包记录及版本在 Runtime 组合层接到只读来源投影；编辑目标以包记录身份确定。

### 5.2 从猜字符串升级到有作用域的字段规则

拟在 Data Services 查询侧维护小型引用规则描述，不放进 UI Profile，也不复制一套可写字段授权。每条规则至少说明源 kind、字段／union 分支、目标类型、作用域、关系用途和原始字段路径。

| 作用域 | 例子 | 解析方式 |
| --- | --- | --- |
| Registry 全局定义 | Spot.areaId、Event.locationIds、场景包装的 actionId | 先约束目标 kind，再按 ID 解析 |
| 所属定义内部 | Event actor、Location scene、局部 position、track、fact | 结合 owner 与局部声明解析；跳到 owner 内部位置 |
| 玩家／运行状态键 | 条件、flag、自定义计数等 | 作为状态读取／条件语义，不要求存在同名 Def |
| 复合结构 | Effect、Condition、支付、Presentation、池成员 | 按判别字段解析；同名 resourceId / itemId 不自动等同于全局资源／物品 |
| 不确定值 | 未登记扩展、疑似 ID 文本 | 仅技术候选，不生成确定错误 |

首批覆盖世界归属／默认集合、资源费用与效果、剧情入口、角色关联和六类玩法 B 的关键全局／局部引用。标签路径、Extra 自定义结构和表达式需按其真实合同适配，不能承诺“所有动态引用都已解析”。

解析状态继续区分已找到、未找到、多个候选；规则命中的语义可靠性另行表达。主清单只使用明确规则且唯一解析的边，字段规则未覆盖不等于引用不存在。图鉴诊断不替代 Registry 和候选包集验证。

正反向索引从同一批边生成，避免两个方向各算一次。修正 incoming 的行适配后补实际 UI 跳转回归，不能只测试查询返回有 incoming。

### 5.3 来源采用逐步补齐

第一步接入已经存在且语义可靠的 owner 方法，并同步列表计数与筛选的来源口径；没有 owner 的内容继续保留在可见兜底范围。

若首期要求完整“按来源包过滤”，再对 Registry 表装载／覆盖及 Runtime 补充源引入统一来源台账：记录最终提供者及来源类别，Runtime 据本次装载记录补具体包记录和版本。clear、reload、覆盖、热 CRUD 均必须更新；来源改变而定义对象身份不变时，也必须使查询缓存失效。不能只根据当前对象 identity 缓存来源。

首期只承诺最终有效来源，不承诺覆盖链历史、包文件行号或跨版本差异。无法证明提供者的聚合单例保持“合并配置／来源待确认”，不能硬指定唯一包。

## 6. 共用 UI 框架与更新边界

### 6.1 复用入口与新增范围

- 保留 `syncRuntimeEditorPanel` 的 body 级宿主和入口注册表；现有入口继续可用，进入统一工作区的对应视图／新建目标。
- 在现有 `codex/` 范围内收敛一份内容工作区框架，由浏览／编辑适配器提供导航、条目、详情、操作内容；不把两套状态强合成一个 reducer。
- 列几何、滚动与宿主优先复用 `renderWorkspaceFrame / renderWorkspaceColumn`。但其当前输出绑定 Presentation host，窄屏规则也不等同于图鉴的选栏模式；施工前应以最小工具布局适配验证可复用部分，并窄扩展必要能力，不能直接套游戏 host ID 或让场景主题改变工具表单。
- 图鉴资料与表单保持各自渲染器；共用标题、中文类型描述、引用行、状态控件和列表项。不是把每一种内容都塞入万能表单。
- 内容名称和说明来自只读查询；编辑权限来自 Policy、具体定义的往返能力以及实际命令可用性三者，不由 Profile 或 UI class 推断。

拟固定以下语义区，框架常驻。除复用 Frame 自身包装外，新增业务包装限定为一个工具根、一个详情页签宿主、一个详情内容宿主和一个编辑操作区；已有同职责节点直接复用，不再套同义卡片。

```text
body 工具宿主（稳定，不随游戏路由重建）
└─ 内容工作区
   ├─ header：标题、工作视图、目标／范围、关闭
   ├─ nav：内容分类与包范围（独立滚动）
   ├─ section：固定搜索栏＋条目列表（列表独立滚动）
   ├─ article：固定条目标题＋详情页签＋详情内容（内容独立滚动）
   └─ footer：草稿／应用结果与动作（编辑时显示）
```

新增包装的确切 DOM 数量取决于 Frame 适配；必须在首个 UI 施工 Task 记录实数。此处给出业务职责预算，不把尚未编码的包装数写成已验证事实。

### 6.2 状态归属

| 状态 | 所有者 | 生命周期 |
| --- | --- | --- |
| 搜索、分类、范围、选中项、页签、历史 | 工作区浏览会话 | 工具会话；不写 PlayerState |
| 目标包、按条目暂存输入、草稿、诊断 | Editor 会话与既有持久化 | 按 `packRecordId + kind + fullId/新建会话键` 隔离 |
| 生效定义、引用索引、来源 | Registry／Runtime 查询侧 | 内容 revision 改变后更新，不随普通 Tick 重算 |
| 游戏进度、当前世界线 | 既有 Runtime 服务 | 仍经既有写入口；工具不新增平行状态 |

### 6.3 DOM 更新合同

| 动作 | 对应更新范围 | 必须保持 |
| --- | --- | --- |
| 输入搜索 | 复用现有调度入口，更新列表与结果计数的 region | 搜索 input、本体光标／输入法组合、左栏、未受影响条目 |
| 选分类／包范围 | 列表 region 与必要的详情空态；导航仅 patch 选中属性 | header、搜索 input、未受影响表单草稿 |
| 单击条目 | element 更新旧／新选中项；更换详情内容 region | 列表及其 scroll container、左右栏外壳 |
| 切详情页签 | 页签属性＋详情内容 region | 条目标题、列表、焦点锚点 |
| 点被引用实体／返回 | 详情身份与内容；必要时显示筛选外提示 | 列表筛选、滚动、历史上下文 |
| 改表单值／增删集合项 | 对应字段／集合 region 及状态计数 | 其它字段输入、光标、其它集合 |
| 普通 Tick | 不重建工具 | 整个工作区与编辑输入 |
| 应用内容成功 | 按实际提交 receipt 更新列表、详情、引用及状态 | 不相关导航和可保留输入；一次收敛 |

`structure` 仅用于首次挂载、浏览／编辑视图结构切换、目标包会话切换或真实宿主损坏；切换前暂存受影响表单。目标局部节点缺失时先恢复该责任区；只有工具根不存在／损坏才回退重建工具，不调用整页游戏 render 作为普通点击兜底。

替换 region 前走现有 popover mutation range 生命周期，关闭范围内锚定浮层、保留范围外浮层；替换后校验锚点。当前图鉴直接替换 Pane、搜索后重新找 input 恢复 focus 的做法应收敛到这份合同。

## 7. 建议施工顺序与独立验收

| 阶段 | 完成后可观察的结果 | 主要范围与验收 |
| --- | --- | --- |
| A：关系可相信 | “被引用”确实显示引用者；普通文本／局部键不会误报全局缺失；来源不误导 | 只读查询规则、入向适配、来源可靠性；补最小回归并验证真实包集 |
| B：图鉴容易读 | 中文分类、资料＋被引用、技术详情收起、跨包跳转和窄屏可用 | 共享框架先承接图鉴；真实内容、未知字段和主题隔离验收 |
| C：编辑器同框架 | 原四类新建／编辑进入同一布局，切条目不丢输入，保存和应用含义明确 | 编辑适配器、按条目暂存、引用选择器、差异与结果反馈；保留既有命令 |
| D：按需求扩写能力 | 经独立验收后，更多类型可编辑或提供草稿影响分析 | 主题适配、玩法 B 专用表单或其它表逐类立边界；不作为前三阶段的完成条件 |

建议先实施 A→B→C。D 是后续路线，不先开全表编辑器，也不以统一 UI 为由重做独立 Datapack / Schema Editor。

初始施工范围预计命中：

- Data Services：`contracts/runtime-content-browser.ts`、`registry/runtime-content-browser.ts`；完整来源台账按裁定再触及 Registry 装载／mutation。
- UI：`runtime-editor/codex/`、`codex-details/`、`view.ts`、`actions.ts`、`state.ts`、`reference-options.ts`、`persistence.ts` 及适用 CSS；共享 Frame 仅做必要窄扩展。
- Runtime：只读来源装配、编辑命令对接按实际需要；不顺手改世界线或玩家存档合同。
- 机制稳定后更新 [[docs/docs-829/06-wiki/20-data-services/definition-authoring]]、相关 UI 机制页和 `ui-style/`；计划文档不升格为当前事实。

### 验收必须覆盖的行为

1. A→B：查看 B 的被引用清单显示 A，点击打开 A；同一 A 的多位置引用正确合并，自引用及派生重复不虚增外部引用数。
2. 同 ID 跨类型只按规则允许的目标解析；普通文本、局部 actor/fact/track/scene/position 和状态键不误报全局缺失；未知扩展仍可完整查看。
3. 后包覆盖 `base:...`、来源未知、包停用、reload 与热更新后，来源、列表数、关系和缓存一致；未加载包不会混入生效图鉴。
4. 正式三包集的世界／资源／剧情／角色／玩法 B 代表条目可读；六类 Operation 不只剩英文 kind 和空摘要。
5. 选择、搜索、页签、跨包跳转、前进／返回与窄屏切换保留约定节点及阅读位置；中文输入法不被中断；键盘可完成主要路径。
6. 四类内容的创建、保存草稿、恢复、应用和导出仍工作；不同包／条目输入隔离；不支持字段不会被清空；ID 锁定与已有所有权约束仍成立。
7. 应用失败保留输入并准确报告结果。当前 Spot 批次允许前项成功后某项失败，必须显示已生效／未生效范围；除非另行实现并验收事务，不显示“全部已回滚”。
8. 桌面和窄屏浏览器验收；工具配色不受场景主题污染；检查长说明、长 ID、空结果、未选目标、只读、缺失目标和未覆盖字段。

测试入口优先沿用 `tests/data/runtime-content-browser.test.ts`、`tests/engine/runtime-content-browser-rules.test.ts`、`tests/ui/runtime-editor-codex-*.test.ts`、`runtime-editor-definition*.test.ts`、`runtime-editor-persistence.test.ts`、`runtime-editor-pack-export.test.ts` 和 Runtime 内容命令相关测试。涉及跨层合同补类型与架构检查；UI 施工后补浏览器交互及刷新范围证据，不只验证 HTML 字符串。
