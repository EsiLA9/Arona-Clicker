# 05-conventions/testing — 测试约定

> 本文回答：如何为引擎、数据服务、产品 Runtime 和 UI 的行为变更选择测试入口。

## 组织方式

- `tests/engine/`：Engine 机制、Runtime 装配和领域协作测试。
- `tests/data/`：Datapack、Registry、包管理、资产和持久化测试。
- `tests/ui/`：组件、Controller、UIContext 与 DOM 可见行为测试。
- `tools/datapack-editor/**`：独立编辑器模型、Schema、校验和 UI 测试。

测试目录按测试主体大类组织，并不保证与每个源码文件一对一。跨层行为可在适当目录中用集成测试验证。

## 验证与审查分级

- **普通小需求**：文案、样式、局部 UI、Datapack 内容及边界清晰的局部机制调整，默认直接实施并核对实际结果。按影响选择已有定向测试、类型检查、浏览器验收或文档检查，不强制新增测试、全量测试、完整 Task / Unit / Receipt 或严格结构审计；避免只复述实现的测试。
- **重要系统结构设计**：新增核心子系统、改变模块依赖 / 状态归属 / 写入口、跨模块契约或关键生命周期时，优先构造关键行为与边界测试，核对设计、调用方和受影响契约，并严格审查。仅讨论设计尚未施工时记录测试方案，不预建占位测试。
- **已报告 bug**：优先建立最小复现与回归测试，核对根因、修复结果和直接受影响行为。难以自动化的视觉 / 交互问题可用明确的复现步骤和修复前后验收证据；说明未补自动化测试的原因，不为形式完整搭建额外测试设施。
- 全量测试或扩大审查范围仅在影响广泛、定向验证不足或用户明确要求时执行。任务负责人按实际影响选择验证强度，不因文件数量、出现“机制”字样或模板默认项自动升级。
- 架构边界、状态写入口、Schema 生成与禁改目录等工程护栏仍按 `AGENTS.md` 执行；降低流程强度不改变这些约束。

## 命令与证据

- `npm test` 执行 Vitest 一次性全量测试。
- 文档变化运行 `npm run check:docs`；涉及文件还应核对差异空白。
- 机制修改按上述分级选择验证；报告结果时区分已运行与未运行，不把未验证写成通过。
- Schema 源类型变化另按 [[docs/docs-829/05-conventions/schema-sync]] 执行同步与校验。
