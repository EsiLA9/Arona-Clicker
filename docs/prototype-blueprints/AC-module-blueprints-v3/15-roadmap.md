# 总体阶段制作路线图

## 1. 路线的用途与完成判据

本页定义 M01–M14 的建设顺序、依赖、交付与退出条件。阶段编号是路线索引，实际 Task 另行登记。M01 的优先级已确认，五份 Task 已就绪待授权。本页与 Task 的登记不授权修改生产代码。

建设分为两条主线：作者工程（A–F）与玩法工程（G–I），随后进入内容生产（J）和正式切换（K）。作者工程先交付可读取/转换/检查/保存/构建的实物，再扩展工作台和语言工具；玩法工程可直接用旧 JSON 和 Runtime 平行建设。两条线通过 Datapack 领域合同、真实运行服务和试播样本对接，不要求等正式 DSL 语法或者全部编辑器完成。

### 阶段 F：全量实体编辑覆盖

按 M05 的实体覆盖表拆成领域批次，M02-D、M05-C、M06-D 同步推进。推荐依次：Story/Entry/目录；Item/Shop/DropTable；Character/Variant/Profile/成长/卡池；生产、Enhancement/Trigger/Affector/Milestone/Achievement；主题/Pic/配色；AreaMap 与 Gameplay Map；Operation 及元数据/单例/extras。每个批次按实际数据规模可拆为若干 Task。每种定义必须具备目录/Schema、真实引用、普通/复杂字段、创建/修改/保存/删除影响的实际消费者；缺的功能标未覆盖。Gameplay B 只是作者工具覆盖，不借此改玩法。旧表单、重复草稿、引用与校验仅在对应真实消费者完成后退出。F 可与 E、玩法工程并行，公共规则变动需统一接口。

## 4. 第三批：玩家实际可玩的探索与收藏（可独立提前）

### 阶段 G：世界与地点行动

G1（M09-A）：现有 Reveal、Map、Travel、真实许可及遮蔽，给玩家可理解的已知/可达/到访状态。G2（M09-B）：Area/Spot 局部调查 Def、持久记录、真实 Story/Effect 动作与完成回执，接现有地点 UI。G3（M09-C）：地图/地点知识来源回顾、调查入口与下一步提示。验收活动“旧图上的第二条路线”，两个实际调查项、地图收藏和许可独立、重访与读档正确。可直接使用旧 JSON；M02/M03/M05 在新增字段进入各自可用阶段时同步登记，不要求 G 等待新编辑器。

### 阶段 H：物品档案与人物知识

H1（M10-A）：现有获得入口实际提交、取得记录、库存条件与依赖；Story/Shop/Drop 成功/失败。H2（M10-B/C）：物品 archive、CollectionGroup、背包和回顾/系列界面；真实资料使用和三项收藏。H3（M11-A/B）：人物/Variant/Roster 独立，Character 知识条目、持久揭示及真实条件；未持有也能完成地区初见。H4（M11-C/D）：资料页/回访、实际来源与下一次 Entry；联动地点与物品。H5（M10-D）：出示、消费、礼物和真正交易边界。H1/H3 可并行；H2/H4 共享 M09 来源描述，不共享库存/人物写入权。跨 Init 的知识及系列范围须裁定后生产启用。

### 阶段 I：可靠投放、里程碑成果及综合活动

I1（M12-A）：既有 PassivePool/Entry/followUp 的可靠候选、持久机会、接取/取消/完成，关键剧情不依赖随机。I2（M12-B）：接 G/H 新事实的真实依赖、事件与主动重查，验证未映射条件与读档。I3（M12-C）：完成条件直接开放能力；明确需要独立授予的动作增加 pending、稳定 grantKey 和真实领域幂等回执；故障注入不丢不重，原 listener 普通行为保持。I4（M09-D/M12-D）：一个单独 Init 中交付可完整游玩的活动：旧地图与两项调查 → 人物访谈和芯片线索 → 三份不同档案（调查/交易/重访）→ 实际设备或必要 Entry → 回访和回顾。测试覆盖未满足条件、普通日常随机、消费后回顾、重复、取消、读档、跨 Init、授予失败；以玩家实际看见/能做/得到的内容验收，不是只读状态单测。

G/H/I 可并行，但新事实和投放应通过各领域真实服务与现有状态/事件装配连接，不在领域之间建立循环所有权；由 Runtime wiring 装配依赖、订阅与命令。I3 的保证交付是特定领域受支持能力，不允许把任意 Effect 重试视作可靠事务。正式存档迁移在 K 前单独批准。

## 5. 第四批：内容生产与正式切换

### 阶段 J：还原导入与实际作者应用

J1（M13-A）：本地真实样本的原文单元、映射、未知标记与缺资源；J2（M13-B）：真实项目文件计划、构建、重复导入和人工修改保留；J3（M13-C、M14-D）：实际游戏进入方式、试播与覆盖审阅，并以 CLI 完成一次新作者流程；J4（M13-D）：负责人确定起始故事、原版世界文本、1.3R/2.3/2.3R 的实际范围与资源后，按篇目分批正式生产。J1 可先行，J2/J3 依赖相应作者服务，J4 不得虚构原文或先宣称全量完成。

### 阶段 K：生产切换及旧职责退出

K1：在正式授权后决定数据源、包产物和应用接线。保留 Base TS 原始构建、测试与可回退基线，只有明确需要切换的权威版本才逐项裁定历史差异。K2：M04-D/M05-D/M06-D/M02-D 按真实消费者退出旧重复目录、验证、草稿、字段和导出。K3：M07-E/M08-D/M14-D 统一真实工具帮助、语言和试播报告。K4：M09–M12 存档新增字段按产品裁定实施，实际玩法验收后再应用。K5：更新机制文档、视觉规范和 ai/guide，记录生产入口、旧符号退出及明确未覆盖的事项。Task 测试、浏览器结果和版本按实际执行记录。

上述推荐不是让 Agent 因为不确定停止一切。明确可逆的副本试作可按本稿合同进行，正式长期格式、产品形态、存档和内容须审阅。若真实源与本稿候选字段不一致，核实后修订对应模块的字段、消费者和验收，不自行另开平行模块。

## 7. 如何据此编写实际 Task

每个 Task 以一个实际建设结果为核心：列对应 Mxx 小节及阶段，指定源码入口与真实消费者，写清目标数据结构/函数责任/调用链/旧职责退出，给正常与失败行为、实际输入输出、测试与浏览器验收。例：B3 不是“完善引用服务”，而是从现有 `runtime-content-reference-rules.ts` 提取 AreaMap 动作和局部边规则，并使运行 Codex、作者目录使用它，再让 CLI/引用选择器消费同一 ReferenceEdge；验收缺失引用、错误 discriminator、同名局部节点、动态/不完整与实际定位。D5 不是“增加通用条件编辑器”，而是迁移 Story 条件树与 World 条件的公共编辑生命周期和真实领域参数，使确认写回一次 DraftEdit，并退出两处重复的树/候选/保存逻辑。禁止用“完成调查、建接口、加测试”代替实际服务。

Task 应使用项目已有 `ai/guide/task-workflow`、路由、任务入口和文档规范；只为实际需要读的模块提供具体路径，不全仓重读。代码变更涉及共同数据合同，应同步主文档与实际消费者。阶段交付需要真实可用产物而非仅 types/adapter/demo。既有测试失败应保留原业务断言，分类报告，不为通过而删掉行为。未经负责人确认不擅自改变重大产品裁定。
