# AronaClicker 模块原型设计 V3

## 1. 本文档集的作用

这是一套待负责人评审的模块建设规格。它替代原型蓝图的主体组织方式，不替代现行机制文档，也不授权直接修改源码。原来的 P0–P6 是需求来源，不再作为软件模块。每个编号对应未来工程中具有明确责任、输入输出、数据所有权和退出对象的一组服务。读者应当能单独读完一个模块，知道当前问题、目标结构、必须发生的改造、分阶段交付和验收，然后据此编写 Task，而不必重新参加历史讨论。

版本基准来自本地第三轮调查（HEAD `391fc1cc4fbd1c7dffc989c82547aafc9531e5f1`，含未提交工作树变动）。本稿以本次上传的 20 份文件和此前裁定为基础；没有重新执行仓库测试或确认最新工作树。下文的“现况”指材料所报告的实现，“目标/拟议”指本稿提出的结构。TypeScript 片段是目标接口说明，不声称可直接复制编译；领域原有 Def 的真实字段以源码为准。除明确标为待裁定的产品选择外，每个模块给出一条足以开始试作的推荐路径，而非让施工者自行选择架构。

## 3. 总体结构

```
文件/ZIP/已安装包 ─ M01 项目文件服务 ── 固定项目输入
                       ↑                 │
                       │                 ├─ M07 文本接入（JSON 也用统一格式入口）
                       │                 ↓
                 M04 作者会话 ←── M02 定义目录、Schema、关系
                       ↑                 │
             M05 Workbench / M06 控件    ↓
                       │           M03 检查、构建 ──→ Runtime 准入
             M14 CLI / M13 导入 ────────┘                  │
                                  M08 作者阅读/隔离试播 ←─┤
                                                          ↓
                         M09 地点  M10 物品  M11 人物  M12 投放与成果
```

图表达数据流，不是允许模块任意反向 import。M01 接受 M07 提供的格式解码函数；M07 只依赖共同数据合同，不调用 M01 读磁盘。M02 消费 M01/M07 的结果，M03 调用 M02 而不是再建一套目录。M04 调用前三者，并由 M05/M06/M07 的 UI 接入端消费。M08 通过明确的预览适配器调用 Runtime，核心文本解析不依赖它。M14 是命令入口，不提供第二份业务实现。M09–M12 是独立的运行领域改造，依赖现有引擎和状态服务，可直接使用 JSON 开发，不等待 M01–M08 全部完成。

## 4. 全局设计裁定（推荐，供审阅）

- 作者源、作者草稿、构建定义、已启用定义、玩家存档五者具有独立生命周期。保存未完成的源不是正式构建；构建不自动应用；试播不写正式状态。
- 保留现有 Datapack/StoryNodeDocument/StoryEntryDef 作为首轮运行语义合同。作者侧新增的文件定位、语言、诊断和引用数据不进入正式存档。玩法模块可明确扩展 Def 与 PlayerState，必须同时说明迁移。
- 作者源使用自由目录与多文件；提供按表、按实体全拆、选中/全包合一、快速层级化。物理路径与游戏目录、Init/Area 归属不互相改写。单个实体默认由一个源声明拥有，关联对象用引用连接；不预建任意字段跨文件合并。
- 保留当前实际包覆盖规则，但将同包重复、跨包覆盖、单例和 extras 规则区分；不得为了新工具“统一”而改变现有合法行为。Base 两种产物的差异必须裁定后才切换权威源。
- 首个完整作者宿主采用现有 Advanced Workbench；独立工具先接文件与检查，继续作为真实消费者；是否最终合并独立产品界面留待负责人决定。不能再新建一个与原工作台平行的演示应用作为最终成果。
- DSL 管线与工具本轮设计到接口级；具体语法、简写、文件扩展名、正式版本未来独立设计。临时解析器只验证接口可替换，不是语言正典。
- 玩法优先在已有实体上增加可使用的能力，允许修改核心数据结构；不以“已有测试能过”为完成目标。新增字段及范围默认在各模块明示，拒绝让后续 Agent 临时发明另一套存档。Gameplay B/Operation 的全量作者覆盖保留，本轮不扩张其玩法规则。

## 5. 数据合同唯一出处

M01 定义 SourcePoint、EntityKey、Owner、DefinitionRecord、ProjectRead 和文件写入请求；M02 定义字段、目录、引用；M03 定义 Diagnostic 的规则归属（基础类型在 M01）、检查/构建/应用结果；M04 定义 Draft 与 Edit；M07 定义 TextWork/Output；M08 定义 PreviewInput/Trace。各消费方引用这些类型，不另起名称不同但含义相同的协议。M09–M12 的玩家事实归各自领域所有，M12 的持久交付记录不是通用事件总账。

## 6. 资料与变更控制

[evidence/implementation-audit.md](evidence/implementation-audit.md) 是本地原调查底稿，[evidence/story-semantics.md](evidence/story-semantics.md) 是现有 Story 语义与测试入口，均作为历史证据，不是未来设计的第二权威。源材料中的外部仓库相对链接可能在本包内不可用，回仓库核对。原第三轮各文档的来源映射与主要改动见总体制作路线。旧技术备选 technical-notes-v1.md 本轮未上传，不作为本稿强制依赖。

实际 Task 必须从当前源码确认入口和现有工作树状态；若目标规格与实际 Def 冲突，指出具体字段和行为后修订对应模块，而不是自行另建一个类似系统。允许在可逆试验中调整接口，但公共合同变更要同步消费者及测试。批准某阶段不等于批准全部生产迁移或存档变更。
