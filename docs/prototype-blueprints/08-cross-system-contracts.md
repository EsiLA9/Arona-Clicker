# 共同工作规则：保存、检查、构建、试播和应用

本页讲使用行为。[共同作者服务的原型工作合同](13-authoring-service-contract.md)固定首轮交换字段、来源范围和作业结果。涉及多个原型的构造页面直接链接该合同。

## 用一个真实操作解释谁改什么

作者打开 `base:area:schale_rooftop`，从地图节点也能打开。同一项目和同一实体，只维护一份正在编辑的内容。切到其他标签不清掉修改。实体的唯一定位起点是当前合同的种类、实际 ID、包来源及原文件。它有多种打开途径，仍应指向同一作者定义。改变显示名称影响读到这个名称的标签和卡片，Area ID、存档到访、地图的目标和 Story 的起始位置仍由各自字段表示。

然后作者在文本中增加一个暂时不存在的地点。他允许保存原文和当前错误。另一份编辑器点击检查同一来源时应得到对应诊断。只有构建通过才产生可发布候选；只有应用时，Runtime 才重新检查当前启用集、正在进行的游戏及保存数据，决定是否接收。试播从单独构建或明确的候选复制定义和初态；它不回写自己与正式游戏的区别。

## 动作分别返回什么

| 动作 | 允许的输入与写入 | 成功与失败后可观察结果 |
| --- | --- | --- |
| 编辑或打开详细条件 | 活动草稿、明确的实体和字段；打开弹窗产生本地副本 | 确认只写该字段，一次撤销可撤回；结构不完整留在弹窗，取消不写草稿 |
| 保存作者文件 | 原文或明确的结构化修改、原来读到的文件内容、所需权限 | 成功只更新实际作者文件与读取记录，未完成语法、缺引用保留可读诊断。外部冲突拦保存，草稿还在 |
| 检查文件／项目 | 当前编辑版本或保存版、选择的文件和依赖 | 说明来源、显式范围、所检内容和无法检查的部分。旧报告可看但标明已过期 |
| 构建 | 选择的一份已固定源和依赖；正式产物需无阻断错误 | 写指定产物并给报告。失败保留旧成功包和原因。可选警告按实际规则说清。构建没有自动保存或应用 |
| 预览 | 选定的定义版本、Entry/Story、Init、临时初始状态与输入 | 返回展现、实际动作、拒绝及可能的人工放行。临时变化留在试播环境。新编辑不会暗换运行中的试播版本 |
| 应用到游戏 | 已构建包、已选择启用关系、当前实际游戏状态 | Runtime 能接收时统一更新定义和启用记录。失败仍可使用旧包、旧状态和有效存档。选择未知旧档策略时保持可恢复信息 |

## 定义、文件和关系位置

文件夹用于作者组织，归属字段用于领域行为。查某对象时先说明它所在项目/包，接着从实际类型和 ID 找到定义。Character 原型 `shiroko` 与 Variant `Shiroko` 不简单转换大小写。AreaMap 节点 ID 只在地图内唯一。并非所有表都有通用 id 字段。首批用领域可查的键和来源，通过 “移动原文件、重开标签、查询相同 ID” 验证。给每个文件和实体加独立永久身份，需要实际长期重命名、离线同步或多个写入入口的证据。

引用必须能解释“从哪份文件某字段指向哪个真实对象”。 `nodes[].action.areaId` 只有在相应地图动作中才作为 Area 的目标，不能扫描所有像 ID 的字符串。一次索引分别提供去哪里和谁在用。坏文件、动态表达式、无权查看的依赖意味着这次查找可能不完整，报告不能把“没看到”当安全删除。普通读取用实际文件当前版本。改名与删除先显示影响，检查完整后再应用。

位置按真实文本给路径、实体、字段或范围。错误有阶段、规则名或稳定代码及原因，跨文件重复展示双方位置。支持选择建议时，先展示更改，用户确认才写。构建用内容摘要或其它实际可复查标记关联输入与依赖。预览和诊断回指此版本。列位置以一个约定给终端和编辑器，首轮先拿 CRLF、汉字及长单行复现定位；当前原型合同使用 UTF-16 零起始半开区间，消费方需用真实输入验证显示转换。

## 首次文件写入怎样保护作者

1. 写单文件前检查实际路径和读到的文件版本，确认目标不越出用户选择的项目。浏览器未授权目录时只导入、导出，不假装可回写。
2. 磁盘变化时保留原草稿，比较基础、磁盘和拟改内容。区分单字段改动与外部重排/删除。重新确认后用新基础保存。
3. 首轮副本试验用暂存、备份、可读报告验证恢复。项目的范围读取保证此时用一致的一组输入；直接读取磁盘的外部编辑器可能在多文件操作途中看到部分结果。文档中实际报告这一点。
4. 只有涉及跨文件改名与多人真实写入、重复提交或重启恢复时，再进一步实验锁、长寿命计划 ID、持久日志与原子发布。长期合同见[第一轮技术备选](technical-notes-v1.md)和 [D04](10-decision-register.md)。

## 所有权、版本和旧系统切换

P1 管作者文件、位置和项目能写什么，P0 管共同结构、引用、领域检查和构建。P3 负责语言的文本读法及来源范围，P2/P6 直接消费服务，界面及终端没有自己的领域真相。项目语言声明、内容格式、生成的 Schema 与 Save 各有目的。首轮保留当前可以运行的发行格式，报告区分不同实物版本。正式切换时，旧 Base 与新构建先经实际游戏消费对照，再改接。是否迁旧档、包如何重载、哪些作者热编辑需要保留按 [D06/D11](10-decision-register.md) 核定。采用新入口后要明确停止哪一次旧写入和哪条重复校验。

玩家状态仍跟随现有各领域。如果一个改动需要从“当前 Init”移到“整个保存”，先写玩家跨线会看见的具体差异及回归，再决定合同。P4 五个可玩样本和 P5 原始内容清单各自拥有领域事实。作者和试播对同样的对象可观察不同位置和状态，但必须明确显示当前场合。
