# 总体设计：一份内容从作者手上走到玩家面前

## 先认识项目里的几个对象

AronaClicker 把文字、地点、设施、角色和玩法参数放进数据包。Data Services 解析文件并装入 `Registry`。这个运行目录提供“某个 ID 的定义是什么”的查询。游戏则持有玩家状态，比如他现在在哪、有哪些装备和读过什么。作者编辑一处名称时改的是定义；玩家抵达天台时改的是存档中的玩家事实。这里要建设两者之间更清楚的交接。

- **Init** 是游戏可进入的一条世界线，提供相应区域和开始条件。**Area** 是其实际地点。**Spot** 是地点里的设施或可用对象。**AreaMap** 是导航图，其节点可尝试前往 Area，也可打开另一张地图；地图上看见一条线还要经过真实通行判断。
- **Story** 是有顺序的正文与动作。**StoryEntry** 是玩家怎么找到并进入正文的入口，带适用 Init、前置、投放类别和奖励等数据。一份正文可以有多个入口，玩家目录也和作者放文件的文件夹独立。
- **作者源** 是可编辑文件，保存未完成的想法也合理。**构建产物** 是经过共同检查、可以交给游戏读取的包。**试播** 使用一个临时游戏及明确初态，可重复尝试。玩家游玩的正式存档和当前启用包由 Runtime 管理。

[A01–A17 的审计底稿](11-current-implementation-audit.md)证明了这些工作中的已有入口、限制和实物差异。第二轮规格说明未来怎么让它们服务同一个作者和玩家，构造阶段的交换数据见[作者服务工作合同](13-authoring-service-contract.md)，实际动作和选择见[共同工作规则](08-cross-system-contracts.md)和[待决定事项](10-decision-register.md)。

## 连续走一遍

1. **整理和检查项目。** 作者导入实际包，预览按表或按对象拆分，找到白子相关 Story 文件和 Entry，按工作习惯组织。把文件移到角色目录不会改变游戏目录及适用世界线（P1）。工具同时能指出地图节点实际指向哪个 Area、某个被删的目标由谁使用、诊断来自哪里。检查入口一套，工作台与终端都能得到（P0、P2、P6）。
2. **查看世界定义，修改具体内容。** 从夏莱地图打开主厅和打印机，找到复杂进入条件或引用，使用同样的选择器和校验。另一路打开同一实体看到未保存修改，滚动和选择仍由各标签保存。若本地源还缺一条定义，可以先保存该工作并继续补。编辑器再将正式构建错误单独展示（P2、P1）。
3. **写正文和试播。** 作者直接用 JSON 编辑已有 Story，也可选择支持的文本前端，在左栏写、右栏读，粘贴片段后确认插入。两个输入形式进相同 Story 结构，接同一个播放器。未来语言语法大改时替换接入实现、帮助和测试（P3）。工具按当前情况保存原文、构建有效包并明确何时试播、何时应用（P0）。
4. **玩家获得内容。** 在已有机制上验证从找线索、读地图、取得实际资格到去指定 Area，接受重要邀约并回顾。普通偶遇可随机，关键内容用确定性 Entry 或实际已有投放。优先以现有 JSON 和运行规则实现活动，失败后再找缺口（P4）。不必等新的编辑器。
5. **规模化还原内容。** 取得已经确认来源的文本与资源时，先按原始范围做映射、对照和审阅，再为游戏设计与正文分开的入口。工作台查资料、构建和试播使用同一服务（P5）。正式题材包含起始故事、世界文本、1.3R、2.3、2.3R，内部映射及资料范围由负责人确认。

## 工作归属与首个产物

| 当事人做的事              | 由哪里完成                                      | 下一方拿到什么                     |
| ------------------- | ------------------------------------------ | --------------------------- |
| 选文件、副本、依赖，拆合、组织或保存  | P1 的项目读取与文件转换                              | 文件路径、字节、位置、归属和本次读取的版本       |
| 解析语言、为文本生成实际定义      | P3 的可换语言实现                                 | 候选 Story/Entry、来源位置、语法与支持范围 |
| 查询和检查、构建、准备发行结果     | P0 的共同定义规则                                 | 标准 Datapack、诊断、正反向引用和构建报告   |
| 浏览、用控件修改、查诊断、看预览    | P2 的工作台及专用表单                               | 编辑命令、作者状态和可观察验收；调用同一 P1/P0  |
| 从终端查 ID、核验、编辑或构建新内容 | P6 对相同项目操作的命令入口                            | 能对照工作台的状态、问题和实际输出           |
| 读包与当前游戏一起验证、应用、保存   | 现有 PackManager、Registry、Runtime 与领域服务的明确入口 | 确认安全后应用或给出拒绝，玩家可继续真实玩法      |
| 核对原片段到玩家实际经历的映射     | P5 还原流程和 P4 游戏验收                           | 已校对的作者源、可查出处、试播与真实玩法记录      |

首个可见产物是一套现有 Base 或 addition-test 副本的“全拆／合一／层级化”、能定位两处重复或一个缺引用的诊断，以及实际 Runtime 能加载的临时包。第二条可以并行用白子的定义跑两个临时前端的替换和文本工具。玩法先用许可明确的现有 JSON 研究，正式语言、全量工作台和长期事务不成为这些任务的前置条件。

## 为什么以文件及共用检查为主

现在的独立编辑器、游戏内 Runtime Editor、Story Editor 和脚本各有真实可用能力。继续各自扩展接线很快，但作者仍无法确定检查与构建是不是用同一规则；例如单例覆盖、缺引用、哪些位置会丢，需要不同工具来猜。推荐先保留原文件为作者来源，接统一的可定位检查，再通过真实消费者而非新增演示外壳验证。完成某条迁移后，才能退出其重复规则或保存路径。

实体库提供按对象查询和一致批改的候选，但会增加外部文本、注释、git diff 与回写的工作。完整不可变项目快照、永久编辑身份、依赖锁和多文件事务也有可用场景。用实际改名、并行文件编辑和持久恢复证明需要哪些，再考虑[第一轮技术方案](technical-notes-v1.md)。仍要记住 Base 分片、运行 bundle 和同版 ZIP 已存在不同数据，按实物路径与摘要记录，不以版本名称判断语义。

当前对外提供应用、构造与施工交接设计。开发施工以[实际批次](09-construction-roadmap.md)及负责人确认范围为准。Gameplay B 既有定义和运行可以作为兼容对照，专用玩法扩展按立项范围暂缓。
