# P5：把已取得的世界资料做成可读、可遇见的游戏内容

## 接到一批资料时，作者的第一项工作

假设负责人给出一章已经允许在项目使用的脚本，外加人物名、地区描述、图片清单和几条演出说明。作者要得到可查阅和能在游戏触发的内容，同时让核对的人知道每句话、每个选项出处和哪些行为被改编。立项范围包括起始故事、原版世界文本、1.3R、2.3、2.3R。内部编号对应哪套地区、版本和语言目前待确认，公开公告只能辅助核对目录。正式文本和资源需要实际可用来源，Gameplay B 暂不作为本轮主要内容。

将一批资料做成可玩内容要交两份结果。第一份保留正文、发言者、原始顺序、选择、场景和资源的证据，供对照核对。第二份解释玩家在哪里获得、满足什么资格、怎么看和怎么回顾。一个正式章节可以拆成几份 Story，一个 Story 也可能由多个 Entry 打开。来源顺序、作者文件、玩家目录和地区触发分别管理。

## 一次导入，从原文读到实际游戏

1. **登记可用输入。** 先选原文版本、语言、来源 ID、授权用途和审阅范围。保存只读原件及其位置。一个源记录至少能再找到对应篇章和段号，即使它尚无目标 Story。对不同语言或版本开不同清单。只有元数据时可以标目录和待领取材料，不填造残缺正文或伪造完成率。
2. **提取可逐项核对的内容。** 按原顺序列对白、旁白、选项和分支、出场角色、地点、资源、演出标记。为每个单位标记原文件及范围。未知标记原样保留，报告哪段需要人工解释。读取器适配来源格式，P3 的正式作者语言以后可提供另一种输出。首轮生成标准 JSON 即可继续。
3. **查已有定义。** 分别找 Character、Variant、CharaProfile、Area、Spot、Pic、Item、Story 或 Entry。以真实 ID 和来源核对，查同名、旧称和多个差分。脚本出现“白子”时，需要分别验证这是发言人、人物原型、特定差分或通讯空间。查不到的地点、资产不能写成自造的正式 ID。留下待核对项和实际可选目标。
4. **制作作者候选。** 以 JSON 写可表达的已有定义。对白变成 talklet，选择变成 Click choice，切换既有场景分别按已核实的 Story 动作。通过来源范围关联具体节点与资源。确需简化的演出，保存原标记、受影响段、当前替代、谁要复核和撤回方式。源文本先后关系不经字母排序。逐项确认后一份 Story 的入口先后、地区和引用。
5. **设计遇见方式。** 起始故事用实际 Init/玩家流程确认开播。必要主线用可靠条件、明确 Entry 或已有后续投放，不用随机池决定重要进度。日常可进地区 PassivePool；人物邀约核对好感、角色空间和 Area 续接；资料可来自 Item、地图或 Reveal。每条都写玩家起点、可见提示、需要做什么、如何回顾。资料被读到的实际行为与原文篇次需分别验收。
6. **逐段审阅。** 在同屏或可往返的两处查看原文与目标。按钮要能从节点找原文范围，也能从原段查所有 Story、入口和资源。先对漏段、合并、发言者、字序、分支和备注，再核对旧图或音频替换。项目 P0 通过只证明可构建，演出和文本审阅是额外结果。源版本更新时展示旧源、新源和人改过的目标，保留既有编辑。
7. **从项目能打开到玩家能完成。** 明确提交候选文件，运行 P0 构建和 P3 隔离试播，对照玩家入口、分支、回顾或下一步。只有可复查测试和来源核对都通过才标“已验证”。一个资源缺失会阻断依赖那部分的正式批次；无关章节可推进。反复导入同来源与相同映射应显示“无新增”或具体差异。

## 一组可直接比对的项目样本

以已有夏莱开场和白子天台故事为可用的项目演练材料。它们用于验证转换和入口，正式原版资料待收到后核对。用一项刻意缺图的实验条目检验失败。无需把已有样本文字拷成正式外部内容。

| 输入与转换 | 作者能看见的结果 | 玩家验证 |
| --- | --- | --- |
| 以 bundle 的 `base:story:schale_welcome` 一小段为本地源，记录原节点 ID 与位置 | 对照起始 Area、talklet、明确 Click 与后续动作，各自关联原节点。正文作者目录与开始的 Init 分开。保留熟悉对白的字序 | 查看该版本 Init 的真实启动路径、文案与交互。首轮只演练工具，不能用分片旧值替换运行对照 |
| 现有 `base:story:shiroko_rooftop_invite` 与天台正文 | 生成或对照两个 Story、相应 Passive/Active Entry、Shiroko Variant、天台 Area 和允许回传的两个标记。保留一段对应多目标的映射 | 跑邀约、赴约、选择 photo/route 和返回。核对玩家要满足的好感与前置已读。正式还原若改入场方式须登记为独立设计差异 |
| 一条带未知图片/演出标记的实验段 | 显示具体缺少的资源、来源位置、可选已有资源和不能被表达的演出。作者可保存为未完成文件 | 应阻断该段发布或明确选择经审阅的降级；不能用空图或假演出通过验收 |

第一批让作者能在导入报告中选某段，跳到目标 JSON，手动把错误发言人或缺图修好，再从源重新检查。若导入脚本无法导出保留人工修改的结果，先用小的明确源清单和候选目录，按 P1 的保存规则应用。

## 怎样记录进度和失败

最初一张可检索表就能满足试验。每行包含原始范围、版本和语言、具体对应 Story/Entry/资源、校对者、正文是否核对、资源是否核对、构建版本、试播操作和状态、玩家入口是否验过、阻断与处理选择。多对多的行要可追查。状态建议使用“已列入／已映射／已写入／已构建／已验证／待处理”，每次跳阶段有证据。删除或换源使对应验证变旧，其他条目不受牵连。

覆盖率的分母取已确认清单中同类且同版本的项。存在一段映射多个节点时，按原段算一次。资料单元、剧情入口和需校对资产分项统计，禁止用目标 Datapack ID 数凑比例。举例：三项已知范围里两项完成构建与行为核对，一项缺图，则报告正文/资料的 2/3、阻断原因和未完成资产。范围不清可显示未知分母。

## 现有实现和后续接线

[A05、A08、A09、A16](11-current-implementation-audit.md) 定位了 Story 目录、真实样本和构建入口，尚缺项目选定的原文资料与单项映射。P5 拥有来源、差异和校对证据。P1 保存作者文件，P0 检查和发行，P2 提供可查来源/实体，P3 试播，P4 验证玩家的发现和回顾。任何正常的直接文件编辑仍按 P1 处理。源映射位置或作者文件变化触发相关报告更新。

R9 可以提前用 JSON 和项目样本完成流程，不等正式 DSL。待 [D10](10-decision-register.md) 列出的发行/地区语言、1.3R 等内部范围、可使用原文与资源、可接受替代和次序确认后，再确定首批正式内容。实际验收以[施工路线](09-construction-roadmap.md)及此页双方对照为准。

## 正式还原如何分别评审

在已有映射清单上分别记正文及文本、资源、演出、游戏化四项结果。正文能回溯原资料并核对顺序；资源给实际来源和版本；演出经运行对照并标出有意替代；游戏化验收玩家的真实进入和回顾。每项可标未核实、部分或已验证。当前正式资料、范围仍由 D10 决定。拿到真实输入后再针对实际格式确定转换方式。
