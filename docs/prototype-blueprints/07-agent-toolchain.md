# P6：让不熟悉引擎的人用终端完成一次内容创作

## 使用者的起点与成功结果

给一名新作者一个有 Base 依赖的测试目录和任务：“在观测站的一份 Story 里补一处有真实目标的互动，自己检查、构建，并跑过选择。”他只需要先认识目录、查角色地点、用当前可用格式编辑，再看诊断修正。最后要获得一个临时可用包和试播结果，工作台能够打开同一份源。可以使用 JSON 起步；有 P3 临时接入时也可以使用绑定的测试文本。正式语言另定。这个例子是建设验收，当前仓库没有下列统一作者命令。

`ai/guide/`、GALHCG、Schema 脚本和 npm 工程工具用于了解代码。当前 `scripts/export-base-datapack.mjs` 专门导出 Base，独立编辑器直接导入和导出包。P6 将实际项目操作合成一个薄入口，业务分别由 P0–P3 提供。A17 有现状界限。新作者应能在应用验收时不靠阅读生产代码查真实实体和错误。

## 跟着一次任务走到底

命令表给拟议操作及候选短名，参数用可依实际样本准备的值。施工时在每个命令实际可运行后更新作者帮助，不能将这些候选当成当前终端事实。

| 次序和用途 | 候选命令示例 | 查看什么、去哪里继续 |
| --- | --- | --- |
| 确认项目 | `ac project inspect ./addition-copy` | 根目录、manifest、实际选定 base 依赖和输入类型；核对所在路径是测试副本；同标签 ZIP 的路径和差异可辨 |
| 观察真实合同 | `ac schema show Story` 或 `ac schema show Area` | 字段类型、允许的引用、前端所支持能力及实际样例路径。若文本前端未开通，输出合法 JSON 例子 |
| 找人和地点 | `ac entity find --kind Area --query observatory`，再查 `base:area:schale_main` | 返回真实 ID、所属项目、可读/只读和文件位置。同名列候选。查看 Story ID `addition-test:story:welcome` 找拥有源，Entry 另查实际 `addition-test:activestory:welcome` |
| 查影响 | `ac entity refs --kind Story --id addition-test:story:welcome --direction incoming` | 区分 Init.startStoryId、Active Entry 的 storyId 等实际已检查关系。若一份文件坏了显示“可能还存在其他引用”，不报告安全删除 |
| 编辑和查错 | 直接编辑测试目录的 `02-story.json`，再用 `ac project check ./addition-copy --json` | 添加一个普通测试节点或调整现有节点的合法引用。故意令 Entry 的 storyId 指向缺失，检查文件、字段位置和目标。先查唯一真实 ID，再在同文件修复。未完成文件照常可存，整包不能发行 |
| 要用文本时 | `ac text inspect --format <已登记格式> --version <版本> --input <文件>`，或标准输入 | 显示候选、来源和语法错误。可选 `to-json` 输出到新文件或标准输出。依能力列表使用 format，先看差异。两个临时前端换法不改变这些通用命令 |
| 构建 | `ac project build ./addition-copy --out ./test-output/addition-copy.zip` | 从确认输入产出真实包、采用依赖、警告与摘要。错误时输出路径不替代旧成功包。输出位置不可是受保护目录 |
| 试播 | `ac preview --bundle <构建结果> --entry addition-test:activestory:welcome --init addition-test:init:observatory --case <测试用例>` | 使用实际隔离状态。在原样欢迎故事对照，点 begin，选 registry，只看到该分支加一档案碎片。另跑 save 分支。报告实际结果、拒绝原因、发生的状态变化，无正式存档写入 |
| 交给他人 | 工作台打开同一工作目录；点击共同检查结果 | 与终端核对字段/诊断、实际作者文件、构建结果和试播指令，双入口有同一含义 |

为了验证“直接编辑”，任务发放一个可丢弃的副本和明确允许写入的目录。作者可用任意编辑器保存不完整的源文；工作台下次读取必须发现外部改动。首轮测试的“修改一处”可用改普通台词又恢复、或改一个明确的 Story 引用，随后复核只有拟改文件变化。不把例子投入正式游戏。

## 工具什么时候读、什么时候写

项目、Schema、实体和关系查询只读；解析、检查及构建预检不写源。输出会标输入项目、文件、采用的依赖与语言、可用结果范围和必要位置。格式化、转换、拆合、组织应先给预览或用明确的新输出路径。保存作者源由人直接编辑或调用 P1；批量修改/删除走明确的审阅和应用步骤。新建、编辑普通内容不必申请永久编辑计划 ID。

批量改名试验可以把某测试 Area 的 ID 改为另一个候选。先显示 Area 自己、导航节点、Entry 或条件中确实引用的字段，以及未知/动态/只读一侧。作者确认后再核对原始版本、路径和真正写入文件，写入状态表清楚列已成功与失败。若有缺引用或坏文件影响全局完整性，先修好或交待人工核对。首轮普通文件比较、备份和失败恢复可启动；实际多人动作需要时再采用持续记录、重试回执和锁。无法读取目录、发现版本变化、越权限和逻辑验证失败必须有不同结果。

无论终端还是工作台，预览只使用了试验内容和隔离初态。构建要指定输出位置，不能因为使用“诊断 JSON”就自动修改源。作者工具的授权只决定可访问和可写的项目位置。边界之外不给写权限；对原游戏存档的处理留给 Runtime 的正式流程。

## 人能读的反馈与机器能解析的反馈

在正常文字模式，用一句话指出因果和下一步。机器模式至少提供成功/失败类型、所用项目/依赖/版本和诊断列表；每条有阶段、稳定规则标识、严重程度、消息、实体和来源位置。JSON 标准输出是一份完整 JSON，进度走标准错误。退出码与字段名可按实际用户消费验证，不用临时稿冻结。分页只有真实工作量超出单次输出时再加，届时未知范围和断点来源也必须可查。

~~~json
{
  "status": "invalid",
  "phase": "reference",
  "diagnostics": [{
    "code": "REF_MISSING",
    "file": "02-story.json",
    "entity": "addition-test:activestory:welcome",
    "field": "/storyId",
    "missingTarget": "addition-test:story:missing",
    "message": "入口指向一个未找到的 Story",
    "suggestion": "查 stories 中的真实 ID，再修改 storyId"
  }]
}
~~~

这段是预期反馈形状。真实输出还应带解析出的范围，不能用示意行号。两边报告在相同输入、依赖、语言版本下用相同规则、位置和目标。发生两次动作或重试时保留输出和当时的状态，避免误把先前检查当成现在结果。新增语言无需改变共用命令；帮助从该语言当前支持能力及可运行例子更新，格式不支持时明确说明。

## 接线和验收

从 R1/R2 加项目扫描、拆合、Schema、实体、关系和检查；R3 接实际构建；R4 用工作台核对临时文件操作；R5 接全文/片段、转换和两个可替换前端；R6 接隔离试播。首轮普通 Node 调用足以验证。已有 `tools/datapack-editor/ui/io.ts`、Base export 脚本与游戏预览是行为对照，CLI 调共同操作，不另写一套读取、校验、打包或游戏逻辑。

交给一名第一次接触项目的人或 Agent，仅提供项目目录、任务和作者帮助。观察是否能分清查 ID、存文件、构建与试播，能否不看引擎源码就纠正缺引用；记录用了哪些路径、读了哪些额外资料、卡在哪和是否能在工作台打开同一结果。脚本侧另测无权限、处理中断、错误目标与标准输出无杂字。真正出现常驻连接、多人权限或大量分页需求时，才依 [D12](10-decision-register.md) 选择追加设施。

## 一条命令何时可以放进作者使用手册

随实际改接验收记录可复制执行的仓库根、命令和退出结果、测试输入及输出样例，至少各有一次成功与可自行修正的失败。没有发布的参数和输出形状保持候选。项目位置、诊断与来源沿[共同数据合同](13-authoring-service-contract.md)，语言能力沿[P3 接入](18-story-text-and-preview-design.md)。
