# P3：让不同版本的 Story 文本都能进入作者工具

**阅读对象。** 正在设计作者工作台、文本接入、Story 试播或终端工具的施工者。本文给出第二轮行为规格。实际 Story 字段、可执行行为和回归样本见[现有剧情能力清单](12-story-semantics-and-preview.md)。

[文本接入与三种预览构造](18-story-text-and-preview-design.md)细化能力登记、请求字段、真实解析替换及高级判定子原型。

## 作者从哪里开始

作者想给白子的邀约补一句话。他可以打开原有 JSON 的结构编辑器，也可以打开绑定到同一项目的 Story 文本。如果这篇 Story 已由文本文件拥有，两个入口都要能显示实际来源，只有能保留原文、注释和未知结构的编辑动作才允许直接改写文本。首轮遇到无法可靠回写的节点，结构视图提供“打开源文”，并让作者在那里编辑。一个 Story 的正文由一个来源拥有，其主动或被动入口可以由另一份 JSON 拥有。

打开文本后，左边可写原文，右边可以看它将呈现为什么样子。作者修改地名，右边显示刚解析的正文；引用已不存在的 Area 时，右边保留可用内容，标出具体问题，并提供真实候选。作者可以先保存这篇未完成的文本，再补全地名。正式构建只使用选定的一版原文和依赖，任何阻断错误都会给出原因；已经生成的旧包继续可查，标明它使用了旧文本。切换到玩家试播时，工具用现有播放器在临时游戏中复现赴约，不给正在游玩的玩家发奖励。

本阶段建设的是上述工具行为。未来可单独决定正式语言的关键字、结构、缩进、自然写法、节点锚点和文件扩展名，并做多轮作者测试。此次仅定义语言怎样接入，完成最小替换试验与现有语义清单。正式语言的可读性目标是让普通对白写起来像正文，复杂玩法才需要明确的结构。

## 一份文本怎样交给工具

1. **找到文件。** P1 向工具提供工作项目、文件路径、原文字节及此次读取的版本标记，还有可用依赖。文档配置、显式打开格式或经过项目允许的识别负责选择接入哪一种语言。自动识别只给候选。手动选择的格式和版本应能在文件信息中查到。首轮可以在测试项目配置中指定格式，长期声明存放位置待确认。
2. **交给当前语言实现。** 拟议接入函数接收全文或片段、原文、文件或输入框位置、选定语言版本和上下文。全文需要知道期望种类，片段还需知道目标是哪一个 Story、要插在谁前面以及允许接受几条节点。它返回成功、部分可读或失败、候选定义或节点、定义到原文字段的对应位置、语法问题。部分结果仅用于阅读和定位，含失败内容的片段不能直接插入。识别、格式化、语法帮助、反向生成文本是可以查询的可选能力。
3. **转成项目已有的定义形状。** 普通对话输出 talklet 的正文结构，选项输出 Click 的 choice，StoryEntry 以独立定义输出。具体字节写法和语法树留在此语言内部。JSON 用自己的读取方式，结果进入同一套 Story/Entry 合同。前端如果遇到尚不能表达的节点，返回“此语言版本未支持”及位置。导入或复制时保留可用的原始数据。
4. **用共同规则检查。** P0 读取候选，检查结构、缺少的目标、父子剧情关系和可用依赖。前端可给出别名拼写与位置，候选解析和歧义报告由项目查询完成。原文有语法错误时，不能根据缺失候选断言其他定义完全没有引用。
5. **分送使用者。** 左文右读用共同 Story 数据显示作者可见的结构；独立试播以已检查的候选定义调用游戏；终端以相同文本版本和依赖输出同一条诊断；构建输出当前 Runtime 能使用的 Datapack。Registry 和 Story 播放器从定义得到行为，不读取正文表面语法。

首轮交给接入实现的最小信息是格式与语言版本、文本、来源和工作目的。返回结果至少能回答四件事：识别了什么内容、源文哪里对应这个定义、哪些地方不能继续、接下来允许阅读／插入／构建中的哪些操作。首轮统一采用[文本接入工作合同](18-story-text-and-preview-design.md)的请求和返回语义，由两种临时实现及实际消费方共同验证。一份文本的字符偏移和某节点的稳定身份解决不同问题。前者供跳转，后者决定重排、读档与剧情续接，不能用文本行号冒充节点身份。

## 现有编辑器如何接受一段文本

参照现有的 Story 正文与剪贴板。当前 `src/ui/story-editor/node-clipboard.ts` 的 `copyStoryNode`、`pasteStoryNode` 保存结构化节点、处理目标/身份并插入草稿，控制器里有具体调用。它是插入行为的对照入口。它现在的对象是结构化单节点剪贴，并未提供正文语言识别。施工时先提取可复用的插入命令与校验，让原有按钮和新增“解析并插入”入口调用真实同一条草稿修改路径。多节点批量插入须在目标列表中一次生效，撤销一次收回全部。

### 粘贴提示、预览和确认

- 普通对白输入框按原方式接收键入、换行和粘贴。只有支持多节点的粘贴入口、明确的“解析片段”按钮或明确选择的文本输入框才尝试识别。候选展示必须保留原始文本，作者也能选择“当作正文”。
- 点击片段入口时记住当前 Story、在哪一个节点前插入（或追加到末尾）、当前草稿版本。等待输入法提交组合输入。粘贴触发一次识别；需要自动重解析时，在输入停顿后针对最新内容做一次，结果绑定文本和目标版本。作者在等待期间可以改文字、取消、切标签。
- 对一个匹配的语言，显示“识别为……”及可编辑的格式选择。多个语言有匹配时列候选，作者选定后解析。没有匹配时仍可保留普通文本。上方标明即将改动的 Story 与位置，下面按顺序显示将插入的对白、选择或操作。必需引用缺失可以作为尚待修复的项目问题显示。语法未完成、结构无法解释或节点目标无效时，保留文本、指出位置，不能插入半批结构。
- 确认时再次检查活动编辑对象、锚点、节点 ID 冲突和片段结果版本。位置已被另一处删除时，在当前入口选择新位置；原来的输入和候选可供重新解析。若片段内节点有局部跳转，允许重新分配身份的前提是所有片段内目标能一起改接，外部引用不会误接。不能确定时要求人工处理。
- 成功后显示插入了几条、选中第一条、把一个可撤销操作记录到共享草稿。取消、关闭、切换以及晚到的候选响应都不能改变 Story。若目标为可写文本且当前语言没有局部反向转换，提供复制或打开源文，而非用 JSON 覆盖它。

## 左文本、右渲染怎样工作

把双栏作为 Story 编辑实例的一种查看方式，依附现有 Workbench 标签。进入时保留原 Explorer 和 Inspector 的开合状态，在正文栏改为下列布局。离开该模式恢复原布局，其他标签继续保有各自的视口。左侧和右侧各滚动，点击对应位置才主动定位另一侧；每次打字不会把右栏拉回顶部。

~~~text
Story 实例的正文区域
  文本栏 [文件来源、语言版本、保存状态]
    文本输入和行级诊断
  结果栏 [作者阅读] [玩家试播] [高级判定]
    当前结果或上次成功结果的明确版本
    当前选中节点、对应原文位置
~~~

输入时保留左侧输入元素、选区、光标与输入法状态，右侧按节点和诊断定位做局部更新。成功解析时只改变受影响的阅读节点与诊断区域；坏文本可以显示当前可靠部分，也可显式查看上一次成功结果。旧结果显示其版本，并禁用直接把它当作当前文件试播。若作者同时开了独立试播，继续使用启动时选择的定义，显示“基于较早版本”，由显式“使用当前版本重新开始”才更换。切到另一个正文对象才重建文本编辑区域。沿用范围内浮层处理和关闭后回到原输入的行为，真实浏览器验收需要覆盖输入法、双滚动、返回焦点与长对白。

### 三种右栏用途

**作者阅读。** 以共同节点顺序显示对白、旁白、选择、演出和操作摘要。两个选项里有一个条件未满足时，阅读仍能展开该项，标记条件、所需局部标记和目标；显示的是作者有权看到的完整方案。点击选项条件可以跳到对应原文。若该字段由语言默认生成，说明它是默认并跳到生成它的最近声明。

**玩家试播。** 作者明确选择一个 Entry、Init、起始状态及固定的输入脚本或手工操作。优先复用 `runtime-game-instance.ts:previewStoryWithContent` 建临时游戏、校验候选，并用 `src/ui/story-editor/preview-view.ts` 与现有聊天演出来播放。运行规则只给玩家展示当时合格的选项。作者查看可以是右栏出入的轻量入口，现有三栏试播作为可展开的完整体验，避免为文本再维护另一套播放器。起点先支持现有 Story/Entry；任意节点开播需要重建前序标记、空间和演出，另有证据才开放。

**高级判定。** 复用现有 `StoryPreviewConditions` 的条件解释和待确认状态。结果区分实际求值成功/失败、未经运行、静态未知、作者手动放行。候选增加已发生的局部标记变化、效果结果、跳转来源和目标，优先读取现有效果结果或事件，缺记录能力按真实场景补接。改变测试人物好感、已读标记或选择时，只重启或更新试播状态。把脚本里人为放行的结果当成真实玩家满足条件会导致错误验收。

## 错误定位和格式变动

每条候选定义、节点、字段和引用保留原文范围及读取版本。字段默认生成、来自多个片段或跨文件时，返回主来源和相关位置。写着“第 6 行”之前须确认 UI 和 CLI 使用同一行列计算，包括 Windows 换行、汉字和代理对字符。旧定位在文件外部修改后先重读与重算；无法重解时提示打开原文件，而不是将光标移到同一旧行号。

原文允许按原样保存，且明确显示构建未通过。选择“输出 JSON”写到指定产物位置，正文来源仍是原来的 DSL 文件。“改为用 JSON 维护”是不同操作，需要比较正文、节点身份、引用、注释、要挪走的旧定义和新文件。输出先供审阅，再处理源的归属。语言升级同理。项目能明确识别旧版本时使用对应旧前端；没有旧实现时文件仍可编辑，诊断提示当前支持版本。失败、取消或者转换发现无法表示的结构时保留原文；重命名或语法换代前先证明身份稳定或明确哪些历史运行游标不再兼容。

## 可直接执行的实验设计

第一步用现有 JSON 跨越读取、作者阅读、真正试播，建立共同结构的对照值。第二步注册两个**测试替身**，各自只解析或返回同一段简单对白。临时 A 可以接收一行“白子：你好。”，临时 B 可以接收两行“[白子]”和“你好。”。两份结果都包含可被当前 Story 合同接收的同一个 talklet，测试给它相同节点 ID、真实或明确测试的发言人、相同正文和合法文档上下文。A/B 的源范围分别不同。测试文件名称与版本是试验配置。

### 施工者如何准备一份可比较输出

用测试专用 ID，在项目已有 Base 依赖下拼出可加载文档。下面是两种临时前端对同一说话节点应交出的**标准定义示例**，不是文本语法。实验如需玩家试播，另附已经过实际结构检查的测试 Entry，引用这篇 Story 并允许夏莱 Init。不要把 Entry 信息塞进正文。

~~~json
{
  "id": "test:story:frontend_exchange",
  "name": "文本接入替换检查",
  "startContext": { "type": "area", "areaId": "base:area:schale_main" },
  "stages": { "main": { "advance": "input" } },
  "nodes": [{
    "id": "line",
    "type": "talklet",
    "stageId": "main",
    "content": { "kind": "talk", "characterId": "shiroko", "text": "你好。" }
  }]
}
~~~

运行程序比较定义数据时排除来源映射，不排除会改变显示或顺序的字段。点击同一对白分别回到 A 第 1 行和 B 第 2 行；B 的发言人定位到第 1 行。片段形态只返回同一个待插节点，把正文与目标信息留给调用方；全文件形态返回含起始区的完整定义。把模板中的目标 Area 故意改成缺失值，语法处理仍成功，错误由共同引用检查给出。带语法错误的另一输入则由语言实现报告所处范围。两个消费方能解释错误来自哪个步骤。

| 操作 | 通过判断 |
| --- | --- |
| 通过项目文件、片段输入和标准输入分别调用 A、B | 标准 Story/节点数据一致；各自错误范围指向自己的真实文本；文件读取与工具命令一致 |
| 关闭 A，注册 B；用相同 JSON 作控制 | 修改范围集中在语言实现、登记、语言说明与语法测试。共用编辑器业务操作、P0 领域校验、发行打包、Registry 及 Story 播放逻辑均可沿用 |
| 故意截断语法、粘贴未知引用、输入法正在组合、先后发出两次解析 | 原文可保留；旧结果不覆盖新版本；坏片段不能插入；缺引用能定位且正式构建失败 |
| 保留 JSON 的完整白子邀约与天台 Entry，用同一标准节点文档作为复杂运行对照 | 跑两种选择、赴约、父子运行与保存恢复；相同的行为由同一运行入口完成，不要求试验文本能完整书写白子样本 |

完成后将[语义清单](12-story-semantics-and-preview.md)、实际能复用的工具接口、目前无法回写的字段和作者体验观察交给后续独立语言设计。R5 先通过替换和创作工具，R6 对照运行语义。等正式语言设计时，再评估 100 行对白的写作负担、复杂表达、提示和格式可读性。相关工作顺序见[施工路线](09-construction-roadmap.md)，需要负责人定夺的事项见[决定 D07](10-decision-register.md)。
