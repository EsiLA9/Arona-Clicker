# Task：AronaClicker 全面原型重构调查与建设蓝图设计

## 0. 任务定位

你现在承担 AronaClicker 项目的首席架构设计师、系统逆向调查者与原型规划者职责。

本任务不是常规代码维护、局部重构、技术债清理或功能补丁。

我们要进行一次面向未来的、具有较大改造幅度的**原型构造调查（Prototype Architecture Investigation）**。

这里的原型构造调查具有明确含义：

- 以当前项目的实际实现为调查对象。
- 以此前确定的项目未来目标为设计方向。
- 允许重新划分系统职责、重建模块、替换现有架构、引入全新的数据组织方式。
- 不要求保留当前代码结构、历史接口或既有 UI 形态。
- 不以最小改动、向后兼容或维护成本最低作为首要设计原则。
- 以最终系统的完整性、可理解性、可扩展性和实际构建效率作为主要评价标准。

**当前代码是需要被理解和评价的既有实现，不是未来架构必须服从的边界。**

你需要先彻底理解现有实现及其真实行为，再提出可以显著超越现有实现的目标设计。

最终任务产物是一套新的、完整的、相互关联的原型构建指导文档。

本阶段严禁直接实施代码改造、修改现有业务实现或直接开始制作游戏内容。你可以检查代码、运行只读调查命令、阅读测试和数据包，但主要工作成果必须是设计文档。

# 2. 核心设计原则：从维护现状转向重新构造

这是本任务最重要的要求。

你不应该首先考虑：

- 怎样让现有代码改动最少？
- 怎样保留现有组件？
- 怎样兼容全部旧数据？
- 怎样将新功能塞进当前架构？
- 怎样避免重新设计已经存在的模块？

你应该首先考虑：

- 如果今天从零建设这套系统，应该如何划分职责？
- 哪些现有模块的职责划分本身就不合理？
- 哪些能力应该合并为统一服务？
- 哪些领域必须保留专用实现？
- 哪些数据应该有独立的作者源文件？
- 哪些运行时机制不应该暴露给编辑器？
- 哪些当前系统实际上只是在重复实现同一套功能？
- 哪些已有概念应该被重新定义？
- 哪些部分值得完全替换？

## 2.1 允许的改造方式

你可以自由提出：

1. 完全重建某个子系统。
2. 将多个已有模块合并为统一服务。
3. 将一个庞大的模块拆分为多个独立领域。
4. 废弃不再合理的中间层。
5. 重新设计数据合同、Schema、文件格式和编辑状态。
6. 将当前运行时编辑功能转移到独立作者工具。
7. 重新设计 DSL、编译器和构建管线。
8. 建立新的数据索引、关系系统、诊断系统。
9. 将现有 JSON 编辑器升级为真正的项目级作者工作台。
10. 重新设计 Agent 与本地工具之间的交互协议。

但每项重大改造都必须说明：

- 当前设计为什么不足。
- 新设计解决什么问题。
- 会影响哪些已有系统。
- 需要保留哪些实际能力。
- 如何验证新设计优于旧设计。

激进不等于随意创造抽象。每个新模块都必须有清晰的业务责任和存在理由。

## 2.2 目标设计必须独立成立

请先设计理想目标架构，再研究如何从现有系统抵达它。

不能因为某个现有模块已经存在，就默认未来继续保留它。

也不能因为一个理想设计很漂亮，就忽略现有项目中已经解决的复杂问题。

我们要的是经过现状验证的重新建设，而不是纯粹的 Greenfield 幻想。

# 3. 需要调查和构建的原型体系

以下是目前已经确定的未来方向。

这些方向是设计调查的范围，不代表每一个内部实现细节已经定稿。

你必须分别建立原型设计文档，并研究它们之间的依赖和接口。

## P0：统一内容生产、解析、验证与构建管线

目标：建设一条从作者输入到正式 Runtime 内容的完整生产管线。

重点调查：

- Datapack Source。
- Pack Loading。
- Manifest 和依赖管理。
- JSON / DSL 解析。
- 标准内容模型。
- Schema。
- ID 和引用验证。
- 领域语义验证。
- Runtime 准入。
- Build。
- 导出。
- 诊断与错误定位。
- 内容版本和构建结果。

重点思考：

当前文件解析、Registry、PackManager、ContentAuthoringPolicy、RuntimeContentCoordinator、独立编辑器 Validator 等模块是否真正形成统一管线？

是否需要重新设计为：

Source → Parse → AST / Intermediate Model → Normalize → Schema Validation → Semantic Validation → Reference Resolution → Build → Runtime Admission？

这一流程仅为候选架构，必须根据实际领域需求重新判断。

需要区分：

- 语法合法。
- 结构合法。
- 引用合法。
- 领域规则合法。
- 可以构建。
- 可以进入 Runtime。
- 实际运行行为正确。

不得将这些概念合并成一个笼统的 Validate。

最终目标：提供一套能够被编辑器、CLI、构建系统和 Agent 共同使用的内容生产与审查基础设施。

## P1：多文件、分层、项目化 Datapack

目标：将 Datapack 从单体内容容器发展为真正的项目文件系统。

重点调查：

- 当前 PackSource、PackParser、Fragment Parser。
- JSON 分片合并策略。
- Base Datapack 的拆分和导出。
- 独立编辑器的导入导出。
- 图片和其他资产管理。
- 实体来源追踪。
- 文件级编辑和保存。
- 多文件冲突。
- 命名空间。
- 文件与实体的映射关系。

重点探索：

- 是否需要 Project Manifest。
- 是否需要统一目录约定。
- 是否允许作者自由组织目录。
- 是否支持按实体、领域、Init、Story 或作者指定规则拆分。
- 是否允许同一实体跨文件组织。
- 如何处理重复 ID 和多来源定义。
- 如何保证拆分、编辑、合并、重新导出的完整性。
- 如何为未来 DSL Source 提供文件级支持。
- 如何在不依赖隐式加载顺序的情况下解决冲突。

请至少提出两种不同的数据组织架构，并进行比较。

最终目标：形成一套可以容纳大型内容项目、支持多人或 Agent 分工编辑的 Datapack Project 设计。

A. Workbench Shell

负责窗口结构、工作模式、实例、Explorer、Inspector、工具带和会话。

B. Authoring Data Model

负责实体编辑状态、草稿、历史记录、稳定身份、来源追踪和提交。

最终目标：形成能够承载全部 Datapack 实体，并允许领域专用创作体验接入的统一作者平台。

# 4. 跨原型的统一架构问题

除了各原型自身的设计，还必须对以下横向问题进行统一研究。

## 4.1 数据身份与来源

研究：

- Entity ID。
- Namespace。
- 文件身份。
- 实体来源。
- Source Mapping。
- 稳定编辑身份。
- 文件移动和重命名。
- 跨文件引用。

## 4.2 作者数据与运行时数据

明确区分：

- Authoring Source。
- Parsed Model。
- Normalized Model。
- Compiled Content。
- Registry。
- Runtime State。
- Save State。
- Temporary UI State。
- Draft State。

不要让作者草稿、玩家存档和运行时临时状态混用。

## 4.3 Schema 与领域合同

研究：

- TypeScript 合同是否仍应作为唯一事实来源。
- 是否需要独立的 Schema 描述层。
- Schema 如何提供给 UI、CLI 和 Agent。
- 动态引用与静态字段如何表达。
- 复杂领域合同如何避免落入超大配置文件。

## 4.4 统一诊断体系

研究一个跨解析、编辑、构建和 Runtime 的诊断协议。

每条诊断至少考虑：

- Code。
- Severity。
- Message。
- File。
- Line / Column。
- Entity ID。
- Field Path。
- Related Locations。
- Suggested Fix。

# 5. 每个原型设计文档必须达到的完整度

这是本任务的核心交付规范。

设计文档不能只写愿景、模块介绍、技术选型和几张架构图。

它必须足以让一个没有参与本次调查、没有阅读历史对话、甚至能力较弱的后续 AI Agent，单独阅读文档后就能理解系统并开始按照规格构建。

每个原型必须包含以下内容。

## 5.1 Purpose & Scope

- 原型的目标。
- 要解决的实际问题。
- 使用场景。
- 明确的职责范围。
- 明确的非目标。

## 5.2 Existing Implementation Audit

- 当前实现的模块清单。
- 实际源码位置。
- 当前数据合同。
- 调用关系。
- 测试情况。
- 当前能力。
- 不足与设计问题。

## 5.3 Gap Analysis

提供清晰的现状与目标对照。

每项现有能力必须标注处理方向：

- KEEP：保留。
- REBUILD：重新建设。
- MERGE：合并。
- SPLIT：拆分。
- REPLACE：替换。
- DEPRECATE：逐步废弃。
- REMOVE：删除。
- NEW：全新建设。

必须解释选择原因。

## 5.4 Target Architecture

给出：

- 总体架构。
- 内部模块。
- 模块职责。
- 依赖关系。
- 数据流。
- 控制流。
- 外部接口。
- 模块边界。

必须使用具体模块名称和职责，禁止使用没有定义的抽象概念。

## 5.5 Data Model & Contracts

根据领域实际需要说明：

- 核心实体。
- 数据所有权。
- 身份。
- 状态。
- 引用。
- 生命周期。
- 版本。
- 输入输出合同。

可以使用 TypeScript 风格接口、伪代码、结构化示例和 Mermaid 图。

这些内容用于明确未来建设合同，不代表必须直接采用某种实现语言。

## 5.6 核心工作流程

至少描述：

- 正常流程。
- 异常流程。
- 状态转换。
- 数据提交。
- 失败恢复。
- 依赖变化。
- 并发或重复操作的处理方式（适用时）。

必须让后续 Agent 知道实际应该实现什么，而不是只知道应该有什么功能。

## 5.7 UI 与交互设计

适用于编辑器和作者工具的原型必须给出：

- 页面结构。
- 面板职责。
- 工作模式。
- 用户操作流程。
- 状态管理。
- 交互反馈。
- 错误定位。
- 空状态。
- 复杂数据编辑方式。

不能只给出抽象的「使用现代 IDE 风格」。

## 5.8 最小可行原型

每个原型必须设计至少一个真正能证明架构的 MVP。

包括：

- 使用哪些真实数据。
- 实现哪些功能。
- 哪些模块参与。
- 输入是什么。
- 预期输出是什么。
- 如何证明成功。
- 哪些复杂情况暂时不实现。

优先选择具有代表性、能够检验边界的真实垂直场景。

## 5.9 Validation & Testing

列出具体的测试对象、输入、预期结果和失败情况。

验收标准必须可以执行和判断，不能写「工作正常」「性能良好」「可扩展性强」等不可测量的表述。

## 5.10 Construction Roadmap

将建设划分为明确阶段：

- Foundation。
- Core Model。
- Core Services。
- Prototype UI / CLI。
- Integration。
- Validation。
- Extension。

每个阶段说明：

- 前置条件。
- 建设任务。
- 产物。
- 依赖。
- 验收条件。
- 可以并行的工作。

## 5.11 Unresolved Decisions

对于尚未确认的设计，必须提供：

1. 已知事实。
2. 需要决定的问题。
3. 至少两个可行方案（确实只有一个合理方案时除外）。
4. 各方案的影响。
5. 推荐方案。
6. 验证该方案的实验。
7. 最终决策所需要的信息。

不允许简单写 TODO、TBD 或「后续再研究」。

# 6. 特别要求：不确定设计不能变成模糊文档

当前项目有不少尚未定型的目标。

这些问题不允许被直接假定为已确认的正典。

但也不能因此让设计文档失去可执行性。

请使用以下决策模型：

**Confirmed → Recommended → Alternative → Prototype Experiment → Decision Gate**

- 必须给出一份代表性 Story 作为测试输入。
- 必须定义语法评估标准。
- 必须明确何时需要由项目负责人确定最终语法。

这样既能保持设计开放，也能避免后续 Agent 无法开始工作。

# 9. 文档质量标准

我们希望文档能够成为后续长期开发的主要设计依据。

因此必须避免以下问题：

### 9.1 空泛架构

不能只列出 Service、Manager、Provider、Adapter 等名称，却不说明具体职责和数据流。

### 9.2 维护者思维

不能默认现有模块必须继续存在，也不能把现有架构的局部优化当作最终目标。

### 9.3 过度抽象

不能为了追求通用性，将 Story、World、Character 等不同领域强行变成相同的数据和交互模型。

### 9.4 过度具体

不能在缺乏证据时锁定尚未确认的 DSL 语法、API 名称、字段合同和 UI 细节。

但必须提供足以开始原型实验的临时设计。

### 9.5 只有正向流程

必须处理错误、冲突、缺失引用、无效输入、保存失败、构建失败和状态恢复。

### 9.6 文档互相矛盾

各原型必须使用统一术语、统一身份模型和一致的模块边界。

如果不同原型对某个接口存在不同设想，应在总架构文档中明确处理，而不是让冲突隐藏在各自文档里。

### 9.7 不可执行的验收标准

必须将抽象目标转化为可验证的输入、行为、结果和测试。
