# P5 世界文本还原与内容生产

## 1. 目标与范围

起始故事、蔚蓝档案原版游戏世界文本全量还原、1.3R、2.3、2.3R 是未来内容工程的目标。第一轮审计 A16 发现已有 Story 目录、Base 作品与样例，尚未定位完整原文清单和覆盖体系。现阶段不知道各内部系列与官方版本/语言/内容的准确对应，也没有获得完整原始材料。先用现有自有或获准使用的样本验证工具，不假设已经能完成全量还原，不擅自补写原版正文。

这不是单纯建立 CoverageUnit 和台账。真正需要回答：拿到一批原始脚本、人物资料、地点介绍及资源时，如何转化成可查阅、可触发、可运行、可维护的 AronaClicker 内容。

## 2. 两种不同的内容工程

第一种是忠实保留原始正文与演出意图，例如故事话语顺序、发言者、选择、原有场景/资源和条件。第二种是为 AronaClicker 设计玩家如何遇见这些内容，例如主线顺序、地区入口、人物赴约、地图线索、收藏品说明。这些是不同工作，不能因为原文导入完成就认为玩法已经完成，也不能为了游戏触发而擅自改写原文。

StoryDef 与 StoryEntry 必须分开。正文可以拥有多个合法入口；一个官方章节不一定直接等同于一条玩家 Entry。地图、人物、物品和资料亦可被多篇内容引用。原始文本目录、作者文件目录、游戏内目录、故事触发关系是四种不同结构。

## 3. 一次具体的还原工作流

1. 确认来源范围：版本、语言、系列、章节、实际可用原文与资产。为每个来源文件或原始内容单元记录可复查的身份及版本。未确定的分母不计算虚假完成率。
2. 解析原文结构：读取正文、发言者、选项、演出标记、资源名和原始顺序。保留不能理解的标记和位置；不能把它们当空白丢掉。原始脚本适配器与 P3 正式 DSL 不一定相同。
3. 查询现有数据包：匹配角色原型和差分、场景、图片、音频、地点及既有 Story。自动匹配有多个候选时展示差异；缺少实体时登记待补内容，不凭名字创造虚假定义。
4. 生成作者候选：以 JSON 或届时已经确认的 P3 语言格式表达；正式语言尚未定稿时可直接用 JSON 验证内容导入管线，不等待语法设计。只生成实际需要的文件，不重复定义已有角色和地点。保留原始片段与生成节点的映射，以及无法还原的演出、资源替代和修改理由。
5. 设计游戏入口：结合 P4 确认正文如何被发现。主线保持必要顺序，羁绊使用适当 Entry 与角色关系，普通日常可进入地区池，物品资料可由获得行为显露。原文顺序和游戏访问顺序不强行合一。
6. 作者核对：从原文跳到目标文本/节点，再从目标跳回原文。比较漏句、错误发言者、选择顺序、条件、资源和无法表达的行为。不得把“构建通过”当作文本还原通过。
7. 保存、构建、试播、记录结果。按实际依赖形成可独立检查的批次；一项缺资源时保留阻断信息，其他无关批次可推进。源更新时展示差异，不覆盖人工修订的内容。

## 4. 原始内容与目标实体映射

| 原始内容 | 初步目标 | 需要核实 |
|---|---|---|
| 主线、活动、社团及人物故事 | Story + 独立 Entry | 正文拆分、原顺序、必要触发与接续 |
| 人物介绍、头像、差分 | Character/Variant/Profile 或资料 | 已有角色身份、公开/发现信息、资源版本 |
| 学院、地点与设施描述 | Init/Area/Spot/AreaMap | 实际空间关系、信息揭示与访问许可 |
| 物品说明、记录、信件 | Item/Story/Reveal 等 | 收藏、阅读、来源与玩家行动 |
| 通讯、邀请、日常 | StoryEntry/Story/PassivePool | 主动、确定投放、随机候选、赴约 |
| 无对应演出的原始指令 | 保留源标记和缺口 | 可接受替代或真实引擎改造 |

该表是设计方向，不能自动决定所有原文的游戏化方式。还原 Agent 对实际样本提出具体映射方案，由负责人确认有争议的剧情和入口。

## 5. 覆盖记录与实际使用界面

最初可用简单结构化清单，不要求立即独立数据库。每行记录来源 ID、版本/语言、顺序、目标实体或源文件、映射状态、文本核对、资源核对、构建结果、实际进入与播放验证、未完成原因。原始内容可以对应多个目标节点或实体；必须保留多对多映射。不同版本分开统计。内容缺口要能按原始范围、人物、地区、资源类型和阻断原因筛选。

原型示例使用三项自有样本：起始故事的一段正文、白子邀约与后续关系、一个故意缺少资源映射的实验条目。显示两项实际已验证、一项阻断及其位置。修改其中一项源后，只标记相关旧验证过期，不清空全部进度。重复导入同一来源不重复新增实体。作者能从未完成条目直接打开相关文件或进入现有资源编辑器。台账只是辅助，不是内容权威。

## 6. 建设路线及未决事项

先盘点真实可用来源和内部系列范围，与起始故事的实际内容需求同步；在现有 JSON 工具上做小样本映射，不等 DSL 全部完成；再接 P3 的文本转换和 P0 的构建诊断；利用 P4 建立玩家实际进入路径。之后按实际篇章与依赖扩大覆盖。需要负责人决定版本、语言、正式使用范围、可接受演出替代、作品边界和还原优先级。首轮不以公开公告替代原始内容，也不承诺已还原任何外部文本。
