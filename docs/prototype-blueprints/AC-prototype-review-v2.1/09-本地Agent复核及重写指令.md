## 每个主体原型的修订方式

先以普通中文详细叙述真实作者或玩家的一次完整操作。说明用户看到什么、使用什么操作、哪个实体变化、哪个文件保存、什么结果保持不变、失败之后怎样继续。再将实际过程划分给模块。术语第一次出现时说明含义和必要性；只有真正承担已知职责时才提出新服务、状态或协议。避免用 overlay、facet、scope、trace、receipt、admission、write-set 等词替代过程解释。术语可以在技术合同中保留，不要求生硬中文翻译。

P0：补足检查、构建、应用的实际交互；规则迁移到统一入口而非增加第三个校验器。P1：完整设计全拆、合一、快速层级化的实际输入、输出、示意文件、预览、冲突和精准保存。P2：补足实体覆盖、统一参考选择、条件详细弹窗、Effect/集合编辑、专用 Story 与地图、实际互索引、真实刷新和视觉复用。P3：本轮重点是 DSL 生产管线及工具，而不是语言设计。明确可更换的语言前端、标准结构转换、来源与诊断、现有输入框的识别与解析、左文本右渲染、作者/玩家/高级判定、DSL/JSON 并行、格式切换与 CLI。未来将专门细致修改语法；本轮只用临时输入或测试替身验证工具，不提出成套语法候选，不以语法定稿为前置。通过替换临时前端检验公共服务是否被具体语法污染。P4：先以现有实体配置玩家活动，确定真实不能表达的部分后才设计新模型。P5：补充原文输入到目标作者内容和真实游戏入口的转换方式，不只写台账。P6：提供新 Agent 可以照着完成任务的真实命令流程，而非把所有写入都提前绑定复杂事务平台。

## 修订验收

主体文档必须让没读过前期对话的 Agent 明确知道：为什么建设；具体要提供怎样的服务；实际使用过程；输入输出和状态边界；从现有何处迁移；哪部分是已知缺口；首个真实实验应做什么；哪些选择待确认；如何在实验后决定正式方案。对于没有实际依据的细节可以保留候选，但必须说明具体试验，不能留下无内容的 TODO。

不要机械追求字数；也不能以节省篇幅为理由删除真实应用、具体例子、操作步骤和重要未决事项。优先完整自然段落解释机制，表格用于对照，接口用于固定已经解释清楚的行为。将真正复杂的子原型拆出独立子文档，不通过摘要减少知识。
