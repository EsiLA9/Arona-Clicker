# P1 多文件、分层数据包项目

## 1. 以作者操作为主导

我们不希望未来大型数据包必须以单个 content.json 存在，也不希望为每个项目强制一套目录树。一个作者可以把十篇 Story 放在一份 JSON，另一个作者可以每篇独立文件；可以把人物介绍和人物事件按角色组织，也可以把一段故事的正文写成 DSL 并让 Entry 存在 JSON 中。逻辑实体身份与物理文件位置独立。文件夹首先是作者工作组织方式，不默认等同于 Init、游戏内 Story Directory 或运行时归属。

已有 `PackSource`、`parsePack` 和 `fragment-parser.ts` 支持多个 JSON；Base 导出已经分表；独立编辑器导出路径仍以整体包为主（审计 A01/A02/A05/A06）。真正缺失的是稳定的文件归属、灵活拆分及回写。第一轮设计中的 Project Store、依赖锁、文件身份值得参考，但应由这些功能决定其复杂度。

## 2. 三种基础转换必须成为真实功能

### 2.1 简单全拆

输入可以是已有完整 JSON、分片目录或已合法导入的 ZIP。系统读取定义并生成拆分预览。建议提供两个简单粒度：按顶层表分文件，以及按独立实体分文件（更细的全拆）。单例配置保留独立文件；一个 Story 的正文、节点、分支不机械分成每个节点一个文件。图片等资源保持原始字节，不展开成巨型 JSON 字符串。

操作：选择输入 → 选择粒度 → 查看生成文件路径、实体数量、命名冲突 → 指定输出目录 → 执行转换 → 用原解析和共同检查读取输出并比较语义。默认写新目录，不覆盖输入。保留未识别字段、资产和其他受支持文件；不能转换的内容明确列出阻断项或原样保存，不能悄悄丢失。

### 2.2 简单合一

“合一”有两个不同含义：把所有可合并的结构化定义输出为一份 JSON；或者生成一个可分发的 ZIP（其中仍可包含资产、文本与 Manifest）。两者都应支持并明确区分。JSON 合一不是强制把任何文件嵌入 JSON。若项目包含 DSL，允许生成编译后的统一 JSON；作者源仍保留，不以合一产物反向覆盖作者文件。没有对应编译器的源格式应给出错误或保持独立文件，不能假装已转换。

允许选中若干 JSON 合并为一份，或对整个包进行合一。相同实体重复出现时显示两个来源，不按文件枚举顺序覆盖。合法的现有包覆盖机制若确有用途，应作为显式规则另行保留，而不是与包内重复定义混淆。

### 2.3 简单快速层级化

在全拆基础上，提供少量内置组织方案：按数据类型、按 Init/世界归属、按作者设定的 Story 系列/角色分类。不同实体未必存在唯一 Init 或角色归属，不能随意选第一个；未分类或多重归属的定义可以放入 shared/unclassified 之类的候选目录，由作者确认。自定义规则可在后续根据实际工作需要增加。

操作：选择组织规则 → 预览目录树及文件移动计划 → 必要时手动调整个别实体或目录 → 在新目录生成或执行显式整理 → 检查内容等价与路径引用。提供文件名冲突处理、同名实体提示、路径合法性和不覆盖未参与转换文件的行为。不会因为改变物理目录而改变 Story 的玩家可见目录。

## 3. 一组具体的组织样例

下面是结构示意，实体字段必须由本地合同验证；不将示意文件名当成已经存在的路径。

```
project/
  datapack.json                  # 已有发行 manifest；是否另设作者清单待定
  world.json                     # 多个 Area/Spot/Init 定义
  stories.json                   # 多个 Story/Entry 定义
  assets/...
```

全拆（按实体）之后可以是：

```
project-split/
  datapack.json
  world/areas/schale_main.json
  world/areas/schale_rooftop.json
  world/spots/credit_printer.json
  stories/shiroko_rooftop_invite.json
  stories/shiroko_rooftop.json
  entries/shiroko_rooftop_invite.json
  entries/shiroko_rooftop.json
  assets/...
```

快速层级化可能改为：

```
project-organized/
  datapack.json
  schale/world.json
  characters/shiroko/invite.story
  characters/shiroko/rooftop.json
  characters/shiroko/entries.json
  shared/resources.json
  assets/...
```

第二份示例中的 DSL 只有 P3 转换经过确认后才能生成；首次文件组织实验全部使用 JSON。三种布局在相同合法定义和相同资源下应能得到等价游戏内容。路径引用有实际文件语义的资产须随移动更新或使用稳定资源映射，不能简单断言所有路径移动都无影响。

## 4. 文件、实体和保存怎样联系

每次扫描产生一份定义来源记录：实体类型、现有真实 ID、文件路径、实体在文件中的位置、文件内容版本。只要能正确定位定义并识别外部修改，首轮无需给每个文件和每个实体额外生成永久 UUID；稳定身份映射可以与现有 ID 和移动操作相比做实验。现有 ID 格式有领域差异，暂不强制全局重命名。

推荐默认一个实体定义由一个作者文件拥有，一文件可含多实体；若确有大型实体协作需要，再评估显式分片，不设计任意对象递归合并。文件移动改变位置，不自动改变实体 ID。实体改名必须查询引用并显示受影响定义，区分能修改的项目与只读依赖。删除前显示引用情况，索引不完整时不提供“安全删除”结论。

例如：作者修改 scanner 的容量，P2 根据来源找到 00-world.json，只改变对应定义和必要的格式片段，不把整个项目重新导出到 content.json。另一个 Agent 同时修改同一文件时，保存前比较读取时的内容摘要；冲突时保留草稿、展示实际差异。第一次原型使用文件备份、临时输出和明确失败行为即可；多文件改名需要验证中途失败恢复，再决定是否需要锁文件和持久事务日志。不能声称普通多文件逐个写入对外部读者是原子的。

## 5. 交互与交付

P2 的项目文件视图与逻辑实体视图应同时存在。物理视图展示目录、文件格式、错误和修改状态，逻辑视图按实体分类，打开后进入同一编辑对象。移动文件不能强迫所有实例关闭。P1 提供拆分/合并/整理计划和实际转换函数；CLI 与工作台均调用它。不能各写一套导出器。

第一批：对 Base 和 addition-test 的固定副本完成导入、按表拆、按实体拆、合一、自动组织及语义比较；用同样本验证未知字段、资源和实体数量，特别核对原审计中的语义差异。第二批：提供真实实体来源和精准回写，让独立编辑器中的保存路径消费它。第三批：跨文件引用改名、冲突处理和失败恢复。第四批：接入 P3 文件类型与实际发行包，统一 Base export/sync 和独立编辑器导出入口；旧路径仅作为对照，完成后退出重复构建职责。

未决问题：是否沿用 datapack.json 并增加作者信息，或独立 project.json；依赖版本锁的最低需求；永久文件身份是否必要；哪些单例/覆盖规则是合法的；同实体跨文件是否有实际需求；格式转换是否需要保留注释与原排版。三种转换功能不能因这些更深的选择尚未定案而消失。
