# P4 从现有实体构造玩家实际玩法

## 1. 设计方法：先玩法，再数据

本原型不以新增领域类、事件总线、事务回执或知识账本为目标。先提出真实玩家可以经历的活动，用当前 JSON 和 Runtime 尝试表达。若已有 Area、Map、Item、StoryEntry、Reveal、Milestone、Enhancement 等能够组合完成，就直接利用；只有实际行为无法表达时，才决定应当补一个字段、条件、触发事件、业务操作或新的领域实体。玩法 B 暂不展开。以下示例都是候选内容，不是已确认的正式剧情。

每个样例要说明：玩家在哪里看到入口，采取什么行动，已有定义如何配置，当前服务会怎样处理，获得什么事实或物品，下一步在哪里可见，退出和读档之后如何回顾。尤其要区分“作者已经定义了某个资源”“玩家知道它存在”“玩家拥有它”“玩家现在有资格使用它”。不能用一个 unlock 布尔值解释全部语义。

## 2. 地图、世界知识、到访与重访

现状见 A11：现有 Reveal 的 existence、name、utility、condition，AreaMap 收录，visitedAreas 和实际旅行图是不同机制。地图画出来的连线不等同于可以通行。先保留四面信息合同，而非新建 WorldKnowledgeKey 和额外 facet 后再考虑怎么兼容。

原型场景以 Base 夏莱主厅、天台与现有地图为起点。在测试包中加入一份与天台有关的资料或对话。玩家第一次进入主厅时只知道公开区域；通过阅读获得某个地点的存在信息，再由后续线索获知名称和用途；收录地图后，地图出现新的可认识内容，但未实际到访。若缺乏许可，尝试旅行仍被拒绝，并显示玩家已经知道的获取许可方式，不泄露尚未揭示的信息。获得一个合法条件所需的物品或 Enhancement 后，现有旅行服务允许玩家抵达，记录访问并可触发天台 Entry。重访则提供后续日常或不同资料。

研究哪些行为已能通过现有 Reveal 的 Effect 与条件实现，哪些缺真实事件唤醒。地图收录、知识揭示、通行条件、到访分别核验。只有在现有记录无法让玩家回顾时，才考虑增加来源记录或访问历史；不要额外创建一套旅行图或默认每次旅行都需要报价事务。

玩家界面需能回答：有哪些地图已经收录；哪些地点已知但未到访；为什么某条路线现在不可用；已读线索在哪里。优先扩展现有地图、世界信息和 Story 记录页面。未知地点的实际名称不能通过其他玩家页面泄露。跨 Init 时按现有 save/per-Init 合同对照，知识是否跨线和许可是否跨线由负责人分别决定。

## 3. 物品的三种作用：拥有、认识、使用

现状 A12：ItemService 的给物、使用和掉落，ShopService.checkout，Story 奖励回执是不同合法发放路径。审计提到真实表名为 dropTables；不凭新术语创造另一套掉落系统。

先使用 addition-test 的 signal-chip、archive-fragment 和相关设施/剧情，研究以下活动：通过故事获得一枚信号芯片；在背包看到物品描述和可用方式；调查某设施时要求出示或消耗芯片；因此打开一个新内容；用完之后仍能回顾已经获得过的资料。再选择两到三件物品组成地区收藏，通过现有条件、Milestone 与 StoryEntry 检验能否在收齐后出现可靠后续。

关键需求是区别当前数量与曾经获得。对于普通消耗品不一定需要永久收藏记录；只对具有真实档案价值的物品提供必要的历史或资料。先调查既有累计获得统计、标签、记录、条件能否满足，不直接定义 CollectibleDef 或 ArchiveRecord。若必须新增历史，明确哪些获得路径写入、零数量或失败交易不记录、重复事件不能重复授予。物品来源提示和已读资料可以是现有图鉴或 Item 界面的扩展，不默认需要独立收藏平台。

测试从商店、掉落、剧情三个真实入口获得同一物品；分别核对库存与收藏事实。消耗最后一枚后，曾获得事实保留而现有数量归零。一个同名物品来自不同包时不能混淆。玩家能够从资料知道下一步去哪里，而不是仅看到“收集进度 1/3”。

## 4. 人物认识不等于抽到角色

现状 A13：Character、Variant、Roster、CharaProfile、好感和羁绊 Entry 已存在。用真实白子邀约和天台样例，并对照其他已有角色资料。先尝试让一个未持有的角色在世界中可以通过一次公开会面被认识；界面展示姓名、所属和已读资料，尚未知道的经历保持未知。获得 Variant 后解锁正常持有和培养能力，已有认识不因此重复生成。随后通过真实羁绊或地区故事补充资料或邀请。

调查现有角色图鉴、联系人分组、角色资料切换、Story 记录是否可以组合表达该过程。缺的是人物知识才补人物知识，不直接重做 Roster 或把每个角色划成七个固定阶段。人物认识应作用于角色原型；拥有、培养按实际 Variant 合同。哪些资料是公开的、哪些必须通过 Story 发现、是否跨 Init，需用具体剧情样例确认。联系人出现不等于开放全部互动。

玩家应能在人物资料中知道已发生的接触、已解锁的故事和合理的下一步线索。待确认是否需要独立资料页、扩展当前图鉴或现有通讯界面即可。

## 5. 地区事件和剧情触发

现状 A14：PassivePool 已有条件、权重、owner、冷却和 StoryEntry 资格；Story delivery、follow-up 和 StoryService 承担实际投放与播放。不要默认建设 EncounterChannel 或另一套 Opportunity service。

原型以现有 schale_root/schale_daily、briefing/tea 等真实候选为基线，加入候选的地区调查日常。玩家初次进入地区时见到普通事件；认识人物后候选中增加相关交流；完成重要剧情后出现反映变化的日常。再次进入或等待时根据真实池规则获得事件，不因读档重置冷却或重复兑现奖励。

必须分别设计随机日常和关键事件。重要线索、必要主线及赴约不能只靠低权重随机出现。优先使用已有主动 Entry、条件与确定性投放路径，明确其显示位置、领取/进入条件、尚未接取时如何保留、何时取消。只有这些现有机制不能表达已确认的需求，才增加最小投放状态。用随机池为空、条件改变、跨 Init 返回和重复进入检验；用户不能因为一次抽不到而卡住必要内容。

## 6. 调查目标、实际能力和世界变化

现状 A15：Milestone 的 listener.then 失败时，当前合同允许完成仍成立且不自动重试。Achievement 是完成展示，Enhancement、SpotFunctionality、Affector 等承担能力与规则。不要一开始换成 ObjectiveDef 或统一授权框架。

以 area-achievement-demo 中 archive-fragments 为真实参考：旧样本累计取得三枚档案片并奖励信用点。候选玩法改成（仅实验）完成调查后获得一个实际检索功能或可用权限，玩家可以使用该功能找到后续 Entry。优先采用现有条件和 Enhancement/SpotFunctionality 的真实开放规则。首先核对是否已有足够的条件、写入与触发入口。如果功能必须保证授予而当前 listener 失败会永久丢失它，则针对这种实际用途设计原子完成或可恢复领取；保留一般 Milestone 已有完成语义，不能全局改变所有成就。

调查目标可以公开提示，也可以是意外发现的隐藏成就。目标应引导行动，不要求把每张地图变成待办清单。世界变化尽量利用既有实体配置：打开新地点、出现新事件、修改可用设施、获得地图或物品，而不局限于产量倍率。

## 7. 组合验收场景及真实缺口清单

建议把 A–E 组合成一条短小真实可玩的夏莱调查链：首次访问 → 获得地图和线索 → 认识人物 → 取得资料 → 开启合法路线或设施 → 阅读重要 Story → 返回后出现新的日常及收藏记录。选择实际已有数据，缺失的测试内容用独立测试包；不将候选场景写成正式剧情正典。

交付需给出具体配置清单：每一步使用的现有定义、事件、条件、效果、服务、显示入口；标注“当前已能表达/需要补接线/需要新增业务行为/需要负责人裁定”。不能只提供新类型。每个实际缺口提出最小补法与更大重构备选，并说明哪个真实行为使其必要。检查玩家成功、失败、取消、重访、读档、跨 Init 及正式 UI 是否可见。原型的最终验收是玩家能完成这些行为，不是数据模型设计完毕。
