# 共同合同与原型建设路线

## 1. 用一次修改解释所有权

假设作者将一个地点的名称修改后保存，并在 Story 中增加该地点的引用。P1 知道两个定义在哪些作者文件中；P2 的工作副本保存当前未提交的修改；P0 从当前文件及草稿得到统一定义、引用索引与诊断；P3 负责文本源到标准 Story 的转换；P6 可以执行相同检查和构建；Runtime 仅在显式应用一份合法产物时改变定义。玩家的到访、库存、剧情进度由运行领域保存，不能因为作者正在编辑而改变。

这就是共同合同最重要的部分。不要用类名取代这些行为。以下技术方案是推荐实验基线，不冻结类型名称。

| 信息 | 需要表达 | 谁维护 |
|---|---|---|
| 实体身份 | 现有类型与实际 ID、必要包来源；同名不同类型不混淆 | 领域合同、P0 索引 |
| 作者位置 | 文件、定义位置、必要字段位置、当前文件版本 | P1 与解析器 |
| 工作副本 | 尚未保存的值、修改历史、基于哪一版文件 | 共同作者服务 |
| 诊断 | 阶段、规则、严重性、原因、精确位置、相关对象 | P0/P3，Runtime 另报应用/行为问题 |
| 构建结果 | 使用的源和依赖、标准定义、资产、结果身份 | P0 |
| 玩家事实 | 当前位置、访问、库存、已知、剧情和其他领域状态 | 现有 Runtime 领域 |
| UI 状态 | 活动实例、Explorer 类型/来源/查询、滚动、浮层 | 既有工作台及对应实例 |

原有 `08-cross-system-contracts.md` 中的 EntityKey/Handle/FileIdentity、SourceSpan、ProjectSnapshot、CompiledBundle、EditPlan、Diagnostic 是技术参考。先用真实改名、文件移动和重复打开证明是否需要各自独立的身份；不预先将全项目旧 ID 全部迁为新命名空间。既有 ID 大小写及领域差异按原规则解释。仅在引用可确定且范围完整时才自动更新。文件来源和构建身份可先通过实际内容摘要或修订信息表达，不要求所有工作都依赖新项目 ID。

## 2. 共同问题必须先说清楚的具体裁定

### 保存、构建、应用

保存作者源可以包括未完成文本；需要明确显示构建阻断。结构化弹窗确认只能提交一致的局部操作。构建从选定快照产生发行物，不改变作者文件。应用需要真实 Runtime 检查并发布。一次保存成功不代表构建成功，构建成功也不代表当前存档允许应用。正式应用失败应保持旧运行状态，预览失败不改变玩家事实。

### 文件修改与多人协作

首轮允许本地单作者和外部文本编辑。读取时记录文件版本，保存前比较，失败保留草稿。跨文件改名/移动需要明确写入范围，验证备份和恢复。若实验表明需要持久事务、依赖锁、稳定 UUID 或恢复回执，再采用第一轮技术候选。外部编辑者不经过统一存储入口时，不能宣称提供完整隔离事务；需要在此条件下设计可理解的恢复规则。

### Schema、引用和诊断

P0 是共同定义审理入口；P2/P6 不另写业务规则。P3 提供源位置。领域合同负责真实引用目标及语义，避免扫描所有字符串猜测关系。统一位置规则应说明字符列、换行及字段路径如何定位；首轮只要求准确可复现，具体 UTF-16 或其他列单位由本地实际编辑器与 CLI 比较。错误附带实际相关实体与可行动解释，而非只返回内部 code。

### 旧系统切换

先在真实副本对照，不为保留旧架构而双写。对 Base 的实际不一致字段逐项列出来源值和运行效果，负责人裁定目标来源。新构建接入实际消费者后退出重复旧路径。旧格式保留必要的一次性导入，不永久维持两套作者权威。旧存档处理按项目既有政策与负责人选择，不默认为必须支持全面迁移，不自行删除存档。切换前可回退。

## 3. 推荐的建设批次（不是现阶段的施工授权）

| 批次 | 实际交付与可见结果 | 直接依赖 |
|---|---|---|
| R0 现状复核 | 原审计中的 Base/ZIP 差异、当前工作树、现有工作台和样例行为可定位；不重新写全仓库摘要 | 无 |
| R1 文件组织 | Base 副本按表拆、按实体拆、合一、快速层级化；能预览路径与对照定义 | R0 文件样本 |
| R2 共用审理 | 两处重复定义、缺失引用、坏文件等实际诊断；CLI 与现有编辑入口共用真实检查 | R0、R1 来源读取（可并行） |
| R3 共同构建 | 从同一来源输出可运行包；Base/独立工具不再分别定义新构建规则；实际 Runtime 副本加载 | R1、R2 |
| R4 作者交互试点 | World 的 Area/AreaMap/Node/Spot 实际查看、编辑、互索引、复杂条件弹窗与精准保存 | R1 来源、R2 诊断 |
| R5 DSL 管线与工具试点 | 临时语言前端接入、片段识别、标准结构输出、源位置、左右预览、CLI 共同检查；替换测试前端验证工具不依赖语法 | 实际 Story 合同；无需等待正式语言设计 |
| R6 文本实际运行 | 白子样例 JSON/DSL 等价、选择/续接/存档、隔离高级判定、错误跳转 | R3、R5，R4 宿主接口 |
| R7 编辑覆盖扩展 | Story 专用编辑接共同作者核心；普通领域从真实 Schema 逐项接入；退出重复消费者 | R4、R6 视需要 |
| R8 玩法验证 | 夏莱调查链的发现/地图/人物/物品/后续 Entry，用现有 JSON 先验证，补真实缺口 | R0 领域样本；不必等待 R1–R7 |
| R9 内容还原试点 | 来源清单到作者文件、原文核对、玩家入口、构建试播，记录真实覆盖 | 现有 JSON 可先映射；正式扩大依赖已确认工具与来源 |
| R10 接入与收敛 | 停用重复路径、统一实际使用说明、确认可扩展领域清单与未完成内容 | 各真实消费者迁移完成 |

批次不是统一套用 Foundation/Core Model/Services 的空模板。每一批必须产生可观察的操作或真实接口消费者。可以再拆 Task，编号由项目工具分配。R1–R4 不要求先完成全套文件事务；R5 不等待全部领域编辑；R8 不等待 DSL。P6 的最小 CLI 从 R1/R2 开始，与每个原型同步扩充，不在最后另造一套系统。

## 4. 评审决定分级

第一类是已经确认的应用方向：多文件、三种转换、全量查看编辑互索引、复杂结构详细交互、自然语言式 DSL、片段识别、沉浸双栏和高级判定、现有实体玩法、内容还原、Gameplay B 暂缓。不得由实现 Agent 默默缩减。

第二类是可直接做可逆试验的技术选择：使用哪个临时文本表示或模拟前端验证工具、使用现有 Datapack 作为运行产物、以现有 ID 开始的索引、普通 CLI、临时输出目录、现有布局承载。记录选择和比较结果，不要求每个变量都人工审批。

第三类是需要负责人确认的长期合同：文件组织与冲突策略、源格式权威、最终 DSL 语法及复杂行为写法（后续独立语言设计，不阻塞本轮管线原型）、作者工作台宿主策略、知识/物品跨 Init、关键剧情投放与完成奖励、正式来源和范围、运行包及旧档切换。保留第一轮 D01–D12 的原始证据和备选，逐项补上能区分方案的真实试验。只有影响不可逆正式数据或重大产品方向的选择才阻塞相关正式实施；其他互不依赖的研究继续。

## 5. 每个实际施工 Task 应怎样生成

开始前读取相关原型和现状证据，定位当前源码符号、直接消费者和现有测试。写清第一个实际修改对象、提取的数据、将迁移的操作、接线顺序、退出的旧路径和本节点独立验收。对尚未决定的产品细节，明确本实验临时值及禁止推广的边界。不能把原型说明简单复制为“建设 Core Service”工作项。

检查点记录真实文件/符号、行为变化、旧入口去向、定向验证和下一步。不要以设计文档数量、Interface 数量、测试数量作为成果。浏览器只用于真实视觉、输入、滚动和浮层等必要检查，其他尽量使用生产入口测试及已有 DEV Navigation。不得虚构测试结果。
