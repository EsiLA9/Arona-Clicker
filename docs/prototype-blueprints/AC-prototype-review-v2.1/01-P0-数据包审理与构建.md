# P0 数据包审理、构建与应用

## 1. 应用目标

作者将一个项目交给系统时，应能知道它目前有哪些文件、定义了什么实体、依赖什么包、哪些内容不能使用、为什么不能使用以及如何定位问题。修改之后可重新检查，确认之后才生成发行包并应用。合法性审理不是“构建按钮返回成功或失败”，而是贯穿编辑、导出、导入和实际游戏应用的服务。

例如作者新增一个地点 scanner，并在 Story 中引用它；若其所需资源或图片不存在，作者不需要运行游戏才发现。系统应该直接告诉他哪个文件中的哪条定义引用了哪个不存在的对象，并能从错误点击进入该字段。若缺失的是另外一个未保存的实体，则可以保留草稿、继续创建目标，然后重新检查。如果一个故事通过了静态审理，但某个玩家因条件不满足无法进入，该故事并非非法；行为验证应解释拒绝的原因，而不是把条件正常不成立误报为数据损坏。

## 2. 已有能力如何接入

原审计 A01–A06、A08、A10 已定位 `PackSource`、`parsePack`、`parseFragment`/`mergeFragments`、独立编辑器 `validateDatapack`、`registry-validate.ts:validateDatapack`、`ContentAuthoringPolicy`、`RuntimeContentCoordinator` 与 `PackManager`。需要重新建立这些能力之间的真实执行关系，而不是再写第三个完整校验器。建议先逐条枚举它们对真实样例的检查：检查什么字段、需要哪些其他实体、何时抛错、错误是否附带源位置、是否需要真实玩家状态。按照这一清单迁移规则，不笼统写“MERGE”。

保留现有路径/字节读取、ZIP 序列化和运行时定义查找。将可以脱离游戏执行的定义审理提取为共同服务；领域规则仍由对应领域维护。Runtime 继续负责需要当前存档、会话、启用状态才能确定的检查。旧包读取作为导入入口，而非新的作者数据权威。独立编辑器、游戏内编辑入口、Base 构建脚本、CLI 最终调用同一组静态规则，不能在各自入口重复实现。

原型中优先使用现有 Datapack 作为运行内容结构。新编译产物头、来源映射文件等可以增加在作者工具边界，不要求 Runtime 立即更换所有类型。是否需要永久的全新 bundle 格式，由真实消费者对照决定。

## 3. 建议建立的实际处理管线

1. 读取项目和已选择的依赖。P1 提供明确的文件集合、字节、来源和依赖版本。不能把整个磁盘目录任意文本都当作数据；未知文件作为资产或未识别文件报告。
2. 按格式解析。JSON 解析器提取值与源位置；Story DSL 交给 P3。一个文件语法错误时记录该错误，其余可读文件继续分析。无法识别的结构不得伪造默认值。
3. 识别定义。将每条定义归入真实领域，例如 Area、Spot、Story、StoryEntry。旧格式转换要记录转换前后的内容。重复 ID 或冲突来源必须显示双方，不能根据扫描顺序选最后一项。
4. 检查字段结构。包括必填、数组、类型、枚举、值域及已有 Schema 可表达的规则。此阶段不需要玩家数据。错误尽量定位到实体内字段。
5. 建立引用索引并检查。根据真实领域合同识别目标类型，而不是遍历所有看起来像 ID 的字符串。来源文件和具体字段可查询。区分必需引用、允许缺失的引用、动态表达式和只读依赖。索引有完整性状态；坏文件无法解析时不能宣称完整反向引用或允许自动删除目标。
6. 检查领域关系。地图节点对应地点、Story 转移目标、Entry 与正文、条件及效果的允许组合等。只审查已有明确规则；条件可达性不能静态判断时给出待行为验证，不声称永远不可达。
7. 构建。按明确合并规则生成标准 Datapack、资源和 Manifest。排序不得改变有序 Story 节点、选择和优先级。生成定义到源位置的对应表。构建失败不替换上一份有效产物。
8. 应用。PackManager 和 Registry 用完整候选验证依赖与当前运行状态，再发布。作者保存、构建和应用是三个独立动作。应用失败报告原因，旧启用包和游戏状态保持可用。
9. 行为验证。选定 Init、Entry、初始条件和操作序列，使用隔离 Runtime 执行实际命令。返回出现的内容、事件、拒绝原因和状态变化，不能修改正式存档。

以上是职责阶段，不强制每阶段都创建类、进程、独立数据副本或复杂中间格式。P0、P1、P3 应先约定最小输入输出；同一批数据可在内存中依次处理。

## 4. 审理交互原型

在 P2 中提供可打开的检查结果区域。检查当前实体、检查文件、检查整个项目和构建是不同范围。用户可以继续编辑时检查当前草稿；全项目构建必须以明确的一次内容版本为准。界面至少显示：检查范围、正在使用的来源版本、阻断构建的错误、允许继续的警告、尚未审查的部分和上一次构建结果。

示意（非现有错误码或真实文件行号）：

```
项目检查：addition-test + Base
错误 2，警告 1，部分引用未检查
[引用错误] scanner 的某一资源字段指向不存在的资源
  来源：00-world.json / scanner / 对应字段
  [打开字段] [查找可选资源]
[重复身份] 同一个 scanner 在两份文件中出现
  [打开第一处] [打开第二处] [查看差异]
[未检查] 一个 Story 文件语法错误，无法检查其出向引用
  [打开文本位置]
```

诊断动作必须真实进入原作者文件或结构化控件。若该字段位于复杂条件内，打开对应编辑弹窗而非仅打开实体概览。位置过期时重新解析并定位；无法定位时明确说明。修复建议可给出候选值或明确操作，不静默修改源文件。来源只读时提供可合法编辑的项目或改变引用，不假装能够保存依赖包。

草稿可以暂时包含不合法结构；保存与构建的关系须明确裁定。推荐源文件允许显式保存未完成作者内容（包括 DSL 语法未完成），并保留清晰错误状态；正式构建/应用必须阻断严重错误。结构化编辑可禁止产生不完整的原子操作，但不应禁止作者保存一份尚未完成的项目。不要把生产构建准入条件套在每一次文本保存上。

## 5. 首个真实原型与建设步骤

使用审计 A05 的 Base bundle 和 Base 分片、addition-test 的目录及两个 ZIP。分别读取，不把版本字符串相同的输入视为相同文件。建立现有运行包的对照记录：Story 的 initId、startContext、Entry availableInits、图片实际字节、scanner 容量。负责人选择迁入值；不需要为了继续工具实验提前解决全部差异，可用固定样本副本。

第一步：以现有解析器读取真实输入，输出定义清单和源位置；用重复 scanner 和缺失引用验证两处错误能定位。第二步：挑选一个 Area/Spot、一个 Story/Entry、一个资源引用规则，从独立编辑器和 Registry 中抽取共同定义检查，并让旧真实入口调用。第三步：通过 P6 的 check/build 与 P2 的检查结果区域消费同一报告。第四步：产生一个可由现有 Runtime 加载的临时包，验证位置、图片和 Story 行为。最后把重复检查迁出旧路径，而不是用新校验结果额外包住旧校验。

验收输入：坏 JSON 与其他正常文件并存；重复实体；不存在的必需目标；允许缺失的可选资源；两个同版本物理包内容不同；成功构建后故意输入错误；静态合法而实际条件拒绝；活跃剧情节点不存在的应用尝试。每个用例记录具体诊断、原文件是否改变、产物是否发布、Runtime 是否仍可使用。

未决：Schema 权威是否继续 TS-first；是否需要独立产物格式；警告策略；完整构建和增量检查的边界；保留哪些热编辑能力。首轮先证明共同规则、可定位诊断和真正构建，不以缓存、完整编译器架构或全套事务设施作为开始条件。
