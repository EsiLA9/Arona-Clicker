# AronaClicker 原型建设蓝图·第二轮参考稿 V2.1

状态：待本地源码核实和负责人评审。不是施工授权，不是已确认的新架构。本文与 01–07 是对第一轮设计的应用层重写，08 为共同合同和施工路线，09 为本地复核指令。

## 我们究竟要建造什么

AronaClicker 要逐步承载起始故事、蔚蓝档案原版世界文本全量还原、1.3R、2.3、2.3R 系列的内容。玩法 B 不属于本轮主要设计目标。这里的系列名以项目负责人定义为准，不擅自与官方卷章建立对应关系。我们要建造的不是一个更复杂的 JSON 编辑器，也不是一个完备但没有内容的游戏框架，而是从内容创作到玩家游玩的连续生产体系。

设想未来作者拿到一批已经取得的世界文本：其中有角色资料、地点描述、故事正文、对话选项、物品说明、演出指令。作者应该能够把它们按照自己的工作习惯放入若干文件，在同一个工作台中查找并补齐角色和地点，写入故事正文，设置其如何被玩家发现及触发，检查引用和实际运行，导出可用的包。随后玩家进入游戏，通过到访、认识角色、收录地图、取得资料和接受邀请阅读这些故事，而不是只能在剧情目录中逐篇点击。

这条过程就是各原型共同的验收对象。原型既可以复用成熟实现，也可以大刀阔斧地改造、合并乃至替换现有系统。复用的是已经成立的能力和交互知识，不是所有现有类和路径必须保留。

## 原型划分与明确分工

| 编号 | 原型 | 核心交付 | 明确不负责 |
|---|---|---|---|
| P0 | 内容检查、构建和应用 | 从文件和实体取得一致的诊断，生成可用包，明确应用前后结果 | 作者文件布局、玩家行为设计 |
| P1 | 多文件项目组织 | 全拆、合一、快速层级化、原地编辑、跨文件引用与来源 | DSL 语法、运行规则 |
| P2 | 全量数据作者工作台 | 公共资源浏览、结构化编辑、引用双向检索、复杂结构弹窗、实际保存 | 另建 Schema 权威、另写游戏执行器 |
| P3 | DSL 生产管线与创作工具 | 可更换的语言前端、片段输入、解析转换、源位置、沉浸双栏、高级预览与 CLI 接入 | 定稿或比较完整 DSL 语法；为语言独立建设游戏引擎 |
| P4 | 现有实体玩法闭环 | 发现、收集、探索、触发、权限及回顾的真实可玩样例 | 未确认的玩法 B、无真实用途的新系统 |
| P5 | 原版内容还原 | 来源与内容映射、批处理、差异复核、玩家实际进入路径 | 原文来源未确认时擅自生产正式还原内容 |
| P6 | 人类和 Agent 的工具 | 查询、检查、转换、构建、改错、可选结构化批改、隔离试播 | 另造一套验证规则、强制每次编辑都走复杂审批 |

P0 与 P1 共享输入合同；P2/P6 共享作者操作和诊断；P3 把文本转换成现有标准实体；P4 可先用现有 JSON 验证玩法，不必等待 P0–P3 全部完成；P5 的内容清单可提前盘点，并反向提出真实语言和编辑需求。

## 原型如何被确认

每个原型分三类要求：已经确认的应用方向（不可自行删减）、推荐试验方案（可以验证后调整）、必须由负责人裁定的产品选择（不能假装已定）。P3 的本轮重点是让语言可以持续修改：先设计文件接入、解析与转换、共同数据、诊断、输入框、沉浸预览和 CLI。语法、标记、缩进、关键字及具体书写惯例留给以后独立的详细语言设计；测试文本仅用于验证工具，不是正式语法候选。

本轮仅改写设计文档。不实施源码重构，不修改真实数据包，不新增正式业务定义。下一轮按 08 的建设批次将获准实验转为 Task。原型设计要具体到能让不同能力的模型依据文档构建，但不把未知的源码位置、类型名或最终语法写成事实。
