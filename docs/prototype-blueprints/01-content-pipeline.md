# P0：检查内容、生成可用包、决定何时应用

具体实现见[共同检查、引用与构建](14-datapack-validation-and-build-design.md)。该页给出规则登记、目录、引用边、依赖选择、覆盖和多包构建的操作规格。

## 先看作者遇到的具体问题

观测站测试包由几份 JSON 和一张 SVG 组成。作者打开 `datapack-dev/addition_test/`，想确认扫描仪正常工作、信号芯片能获得且有图标。现有目录里，`00-world.json` 的观测站列出了 scanner，scanner 的费用和产出引用 Base 信用点，它的主题引用配色组。 `02-story.json` 中 passive-signal 的重复完成奖励引用信号芯片，`01-content.json` 中芯片引用图片，图片地址指向包内 SVG。要判断“源哪里错了”，必须沿这些具体关系查，而不能在游戏没显示东西时只给一句“加载失败”。

以下是一轮日常操作：

1. 在项目选择页看到打开的目录、实际采用的 Base 依赖以及来源类型。目录副本与同版本 ZIP 可分别打开。作者点击“检查当前文件”，未保存的编辑内容也能参与这次检查；点击“检查项目”才读全项目及已选依赖。两种结果都标出范围和版本。
2. 把 `00-world.json` 的 scanner 主题引用故意改成缺失颜色组。诊断说清哪份文件、哪条 Spot、`theme.colorGroupId` 指向缺失值，并给“打开该字段”“查可选配色组”。作者修正前仍能保存源。另一个 Story 文件语法错误时，正常目录仍可检查，报告注明某些引用尚未检查完整。
3. 作者将同一个 scanner 误放到另一份 JSON。报告同时给两处定义，保留两处的可读内容供比较，让人删除、改名或移回原文件。不能按文件名排序替作者挑一份。若某条合法旧包覆盖与物理重复相似，由旧包明确规则和导入报告决定，不能混成普通包内覆盖。
4. 作者修好后点“构建”，明确选择保存版或一份开发试验副本。正式发行默认用已保存的来源。不自动先保存未完成草稿。输出是一份实际可导入包及构建报告。报告有输入版本、依赖、实体和资产摘要、警告及所生成路径。构建不写作者源。失败时保留上一次成功产物并标清旧版本。
5. 作者用临时游戏验证基线，例如能看到观测站、打开 Story、结算其奖励和显示图片。这里沿用真实 Registry 和领域服务。某个合法 Entry 的前置条件没有满足时，报告玩家拒绝理由，作者合法性结果保持原样。
6. 作者到正式游戏另行选择“应用”候选包。先展示启用集变化、缺依赖、活跃会话或读档影响。预检不过保留原包、当前进度与可用显示。正式切换规则依存档策略确认，试验先用隔离副本。

## 按内容发生的次序实现

### 读取、解析与保留位置

接收 P1 提供的文件路径、实际字节、声明格式、来源项目和本次依赖选择。资产、README、作者配置及可读内容各按用途分类；作者配置不得被当成 Datapack 分片。现行 `parsePack` 从根的 datapack.json 起读，将其他 JSON 按分片处理，同时识别图片。它通过 Promise.all 读取分片，遇坏文件目前整体拒绝，并返回按包合并的 Datapack 与图片 URL。原型保留现有 ZIP/文件选择入口作旧包导入，增加逐文件解析和来源记录；当前解析器本身不能返回每个字段的行列。

JSON 的读盘结果要带字段范围。遇到文件级错误先记录准确范围或最近可定位点，再继续处理其他文件，明确哪类检查无法完成。P3 文本前端返回同样可定位的候选。能读取的内容才做旧格式转换，并显式报告旧 Entry 等转换和改过的字段。作者路径和源文本始终可查。未识别字段由 P1 决定保留原文或阻止转换，不能因为工具没有生成控件而消失。

### 定义形状、引用、领域行为

可解析的对象先识别表、真实 ID、来源和字段类型。独立校验器中的 `validateTable/validateRecord` 会依 `TableSchema` 检查字段，`checkUniqueIds/checkIdFormat` 位于同一目录。它可发现若干作者错误，不能简单把只适用于某界面的提示升为发行阻断。先列出规则用的是哪个字段、数据来源、是否只在 UI 有效、是否能独立于运行状态，然后提取一条对照规则。

从 `AreaMap.nodes[].action` 开始，当动作是 attemptAreaTravel 时，只有 `areaId` 指向 Area；是 openMap 时 `mapId` 指向地图；没有动作或 inspect 时没有这条目标。这条引用既为指向查询、反向搜索和缺失检查服务，又为诊断放入引用字段的位置。处理场景中的不可靠事实：同名但 ID 不同的两个结果需要区分；某个坏文件可能藏有未知引用；动态选择器需要显示可能目标；对明确允许空的字段按真实领域决定合法性。发现必需引用缺失时不能输出正式产物。没有办法检查的部分应可见。

再做需要读多个实体的规则，例如区域地图每条边的两个局部节点存在、Story Entry 的激活形状符合类型、子剧情续接的目标和关系满足规则。静态检查计算不了玩家好感、位置或本轮选择时，写“要用实际状态验证”，不模拟另一套游戏。第一批校验结果至少分开文件语法、字段结构、重复定义、明确缺引用、领域条件错误、未检查部分。详细诊断包括项目、文件、实体、字段或行列、可执行下一步，以及关联位置。共同诊断检查问题的形状见[工作规则](08-cross-system-contracts.md)。

## 从已有入口搬出哪些规则

[A01–A06、A08、A10](11-current-implementation-audit.md) 保留详细证据。提取原则是同一输入给旧/新入口对照，再让已有入口调用移出的规则。

| 实际代码 | 第一批怎么接与验证 |
| --- | --- |
| `src/data-services/datapack/pack-parser.ts:parsePack` 与 `fragment-parser.ts:parseFragment/mergeFragments` | 保留旧包路径/字节和格式支持。把“声明识别”与“兼容合并”分别用于作者读取、旧包导入。让新读取返回定义来源，比较 metadata 与分片 name/version、列表次序、被旧合并覆盖的单例 |
| `tools/datapack-editor/validate/index.ts:validateDatapack`、`schema/editor-extras.ts` 与生成 Schema | 先提取一个普通字段和一个引用的共同检查，保留现有 UI 提示与生成路径，把检查结果接回原按钮和 CLI。UI extras 的标签/控件建议只负责显示 |
| `src/data-services/registry/registry-validate.ts:validateDatapack` 的 `validateAreaMapShapes`、`validateStoryEntryActivation`、`validateStoryContinuations` | 选择地图和一条 Story/Entry 规则，让公共定义审理和 Registry 准备统一调用真实领域规则。首次只提取可脱离 PlayerState 的部分。保留 Registry 出错的外部合同，作者诊断补位置 |
| `src/data-services/authoring/content-policy-dsl.ts`、`RuntimeContentCoordinator.applySpotMutation` | 复核编辑器特有输入形状、组深度限制与产品定义规则的区别。像现有有限条件编辑器的每组八项限制，不自动成为全部 Story/JSON 的非法条件。热写仍要对当前 Registry 更新/回滚，作者检查服务仅承接能够复用的静态规则 |
| `scripts/export-base-datapack.mjs`、`scripts/sync-base-datapack-bundle.mjs`、独立工具 `ui/io.ts:createDatapackPackage` | 首轮先保留它们作为对照。依次让一个实际脚本和独立工具调用共同构建；生成现有 Runtime 可载入的 Datapack+manifest+资源。验证一致后退出分别维护规则的旧做法 |
| `src/data-services/datapack/pack-manager.ts:buildRuntimeApplyPlan/applySelection`、`src/arona-clicker/runtime/runtime.ts` | 继续管理实际启用包、顺序及运行期准备。新产物还需走同一产品入口与验证，特别核对上一版本和失败回退，不直接把候选定义丢到活跃 Registry |

建议在首批实现记录一份规则迁移清单，逐行写旧消费者、提取后入口、测试输入、旧错误与共同诊断、旧重复规则是否已退出。一条规则尚不等价时继续保留原防护。避免作者端再建一份规则、Registry 旧校验再执行一份且两者无法对照。

## 构建面板、产物与行为验收

项目检查区域可以从工具带打开。第一行说明当前“文件/项目/草稿”范围、使用依赖、上次构建。诊断按阻断和可继续区分，并可按文件过滤。展开一条跨文件冲突能点两边。点复杂条件的问题先打开字段所在实体，再在权限足够时打开条件弹窗定位；旧位置过期重新检查。没有文件写权限时仍能查问题和建议，界面不展示会失效的“修复原文件”。

构建首轮产生现有 Datapack 能接收的定义、包清单、保持可用的资源地址和构建报告。按对象种类核对可重复性，对 Story 节点、Choice、列表、优先项保留有游戏意义的顺序。临时目录准备好且本地可用性校验通过后再发布。正式的新包头、内容锁和缓存各自需要后续证据；首轮固定输入清单和来源字节即可先对照。

| 测试输入 | 验收者要看到什么 |
| --- | --- |
| 一个非法 JSON ＋ 一个可读的 Spot 文件，后者有缺失颜色组 | 两个可行动结果及不完整范围，记录对应项目与位置；源内容可原样保存，无法发行 |
| scanner 在两份文件重复；更换文件枚举顺序 | 同一错误关联两处定义；未选择哪一条覆盖。当只读包合法同名时，显示来源和权限 |
| 破坏可选图或删除必需引用 | 以真实合同区分可选降级与阻断。用测试前先点名哪条规则允许回退，不能一律放过缺图 |
| 构建正常，然后破坏源或打断写盘 | 旧成功包仍可验证、标注旧版本；新构建失败有原因，不产生半包 |
| 对照 Base 分片和运行 bundle、addition-test 的两份 ZIP 和目录 | 双方各记摘要与关键实际差异。Story 的 initId、起始区、Entry 可达、scanner 的 baseCapacity、资产字节不得因为名称相同或排序归一而丢失 |
| 用诚实的初态走不满足条件的 Entry；用缺活跃节点的包应用 | 前者可构建、运行明确拒绝；后者准入失败保留原游戏和进度。模拟通知失败时再查实际应用结果 |

先把真实运行 bundle 用作行为对照。原型可以用选择明确的副本完成。正式迁移要决定两份实际数据的应采用值。接下来直接走 [R2/R3](09-construction-roadmap.md)，技术选项参见 [D01、D02、D06、D11](10-decision-register.md)。
