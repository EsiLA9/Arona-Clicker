# 施工路线：每批让真实使用者得到可操作的结果

这份顺序供负责人评审。源码实验或正式切换需要独立施工任务。资料由 Task 0429 链接到[实际证据](11-current-implementation-audit.md)，第一轮工程备选见[技术附录](technical-notes-v1.md)。

## 从第一份能真实操作的包开始

### R0 确定实物和当前可重现的行为

取 Base 运行 bundle、分片、addition-test 目录及两份 ZIP、区域成就示例与白子天台样本。给各自记录物理路径和内容摘要，确定哪些作为游戏行为对照，哪些作差异输入。复制到测试目录后，先跑真实读包、作者试播和世界旅行现有测试。P2 核实正在使用的运行工作树，不根据归档 Task 名推断已通过。交付物是可复查输入、具体差异、现有失败及真实入口；无需另写全仓审计。

### R1 打开包并完成实际全拆、合一、快速层级化

从 `exportBaseDatapackFolder` 和 `parsePack` 的现有输出入手。在同一 Base 副本上产出按表、按实体、合并单 JSON、按世界或角色分组的预览和实际输出。资源仍是独立文件。旧构建可重读，看到保留的定义、文件和改动理由；源文件无变化。用实际独立编辑器导入/导出的入口或最小 CLI 触发，列旧路径与新增共用操作。遇到未知字段、文件名冲突或重复实体必须在预览里可定位。R1 的最小依赖是存在可读样本和已选择的依赖；完整依赖锁不是开始条件。

### R2 点开两处真实错误并修正

选重复 scanner、坏 Story JSON 和一个缺失配色组。让文件读取给出对象位置，提取当前编辑器与 Registry 可共用的少量规则。实际编辑入口和 CLI 对照同一个结果。验收者点到两处重复或某字段，修正后重验；坏文件存在时其他可读文件仍被检查。这个批次可和 R1 做文件读取同步开展，需共享实际路径/字段返回。常用错误文案与现有代码对应，不为格式统一而抹去领域限制。

### R3 生成现有游戏真正可用的包

从同一批源构建实际 Datapack、manifest 和图片，先进临时 Runtime 对照。旧文件夹和独立工具导出各指定一个迁移入口，用自己可运行的样本证明共用结果。比较 Base 列出的 Story 与 Entry 差异，错误构建不能替换旧包。用实际 PackManager 应用副本，演练缺依赖、活跃故事不兼容和读档失败；保留退出条件所依赖的旧路径。正式切换选择待 D06/D11，成功试验以能读、能跑和能恢复为准。依赖 R1 的实物来源及 R2 的阻断规则。

## 让编辑器、文本和终端真的用上前面的服务

### R4 作者在夏莱地图里找到对象，打开条件并保存

首个待评审宿主为现有游戏内 Advanced Workbench，从 World 打开明确可读写的测试项目。按地图→节点→Area→Spot 操作，修改普通字段，检查两个标签的草稿与各自视图。接既有 Story 条件树与 Runtime 条件值处理，迁移一个 World 条件和一个已有 Story 条件消费者。保存回准确文件、点击诊断到字段、对照外部冲突和引用索引。走项目宽屏鼠标、真实滚动/焦点/浮层和 UI 自动化。R1 来源及 R2 校验可用后启动；无需等 R3 全面迁移与 DSL。

### R5 同一工具用两个临时文本前端，完成片段和双栏

先用现有 JSON 确认公共数据与作者显示；接两种实际读取发言者与正文的小型文本前端。两个前端都调用同一项目扫描、片段预览、插入撤销、双栏呈现和 CLI，生成同样的定义及各自源位置。真正换掉前端不需要改公共业务或播放器；如果一处分歧，先定位消费者直接读了具体语法。可以并行用已有 Story 合同搭试验，R4 提供实际宿主接线时完成复用验证。首轮只给临时格式帮助。正式语法、扩展名与编写惯例不进入这一批。

### R6 在现有播放器里跑完白子赴约和分支

使用真实白子父、子 Story/Entry、Area/局部标记样本。让 JSON 与语言接入返回的规范定义经过同一规则和构建加载。右栏作者阅读能展开两个分支；玩家试播存在真实选择和等待；高级判定能区分实值、拒绝及作者放行，诊断与原文对应。跑两条分支、赴约、保存恢复、无效目标、取消与正式存档隔离。R5 的文本输入、R3 的构建和 R4 实际宿主分别提供可用能力。无需全文语法完成就可用测试前端输出已核实的白子数据。

### R7 按真实表扩编辑能力，退出迁出路径

依据 P2 表清单逐域用原调用方验收普通字段、复杂结构、引用、保存和 Undo。先接 Story 专用正文为第二类使用者，再对角色、物品、商店、成长、地图和其他已有合同逐项扩大。每新增一类普通实体，演示已有通用目录、查询、引用、保存自动接入，列了哪些必要专用编辑能力。旧 Provider 若还在做同一搜索、保存或验证，只有行为对照后才退出。正式 Host 选择按 D05。此批可拆更多独立施工任务，先 R4，再按与 R6 的依赖接 Story。

## 可独立推进的内容和玩法

### R8 用现有 JSON 验证玩家真的能发现、获得、使用并回顾

用 Base、addition-test、area-achievement-demo 各跑 P4 五个试点：地图与资格、芯片及回顾、认识未拥有角色、随机日常与可靠邀约、三片档案到实际后续。记录每一步实际配置、调用、界面与状态。确定哪处只需配置、哪处缺接线以及哪个新行为真的缺字段或操作。先证明玩家能完成一条链及失败、重访与读档，不等待 R1–R7。确认跨 Init 或能力授予等变化后，再补最小范围的实现。

### R9 从一份来源材料到一次真实进入

先从已允许的项目样本做三项映射练习。核对台词、人物、地点、资源和演出；给一项缺图报告与可定位的来源。保存 JSON、检查、构建并试播，玩家能按明确条件到达内容。另验证导入源更新不覆盖人工修订。正式内容由负责人明确实际资料、版本、语言、范围、可接受替代后启；样本流程可并行，不等正式 DSL。

### R10 切换实际入口、统一帮助并演练回退

每个实际入口有一份切换记录，读者知道会进入哪里。例如 Base 脚本从各写一套产物到共同构建，独立工具从临时全包 JSON 到真实源操作，游戏内 Story 热写与保存源、预览、应用分别清楚。对照包、活跃进度、旧存档和作者真实工作树后，移除已无消费者的旧分支。旧只读包可继续通过明确导入支持。先预演运行和档案回退，再按项目策略进行正式切换。

P6 从 R1/R2 开始与用例一起增长，从查询到检查、格式转换、构建和试播，不在末尾另建一套命令业务。相关边界见[共同工作规则](08-cross-system-contracts.md)。

## 交付批次内怎样分任务

P0–P6 解释需求，R0–R10 给出交付依赖。构造页说明实际服务，获准后用 Task 精确交接。有些批次可分给不同实施任务，每件完成后都应有可操作结果。[首批施工草案](20-first-implementation-task-drafts.md)给出 R1、R2、R5 的第一件事。

| 批次 | 可以各自验收的实施工作 | 确认范围时要具备的设计或证据 |
| --- | --- | --- |
| R0 | 固定输入、比较同版不同实物、记录可复现行为 | 用实际文件和摘要确定读入顺序与测试入口 |
| R1、R2 | 按表全拆及合一；按实体和交错分组；保留源位置的目录；共同检查首组三项；地图和续接引用 | [顺序方案](15-datapack-fragment-order-design.md)、[共同合同](13-authoring-service-contract.md)、[规则及引用](14-datapack-validation-and-build-design.md) |
| R3 | 构建及旧 reader 读回；多包差异报告；临时 Runtime 应用和失败恢复 | 固定依赖、实际 build/admission 输出、既有启用规则 |
| R4 | Workbench 绑定项目和源定位；World 普通字段草稿与保存；迁入 Area/Entry 条件树；共同引用选择和只读来源 | [首个宿主和复杂字段](16-workbench-session-and-structured-editing.md)，具备真实文件写入通路 |
| R5 | 两小语言与共同处理；片段和撤销；双栏作者阅读、来源和旧结果 | [文本能力合同](18-story-text-and-preview-design.md)，从 JSON 先核实标准模型 |
| R6 | Runtime 临时试播；父子续接与保存恢复；六分支的高级判定与运行回执 | 现有 Story 语义清单、沙盒和可关联的真实记录 |
| R7 | Story 正文/Entry/目录；物品/掉落/商店；人物与成长；规则和目标；地图与 Operation；表现与设置。每域分开迁入真实消费者和退出旧路径 | [逐表编辑能力](17-entity-editing-coverage.md)，各域拿实物证明复杂编辑 |
| R8 | 五个机制对照可独立进行；旧图走通、人物访谈、档案收藏各做完整路线；出现明确缺口时再开框架任务 | [实体能力与活动](19-gameplay-capabilities-and-activities.md)，产品裁定见 D08/D09 |
| R9、R10 | 已有样本小批导入；实际来源确认后按资料批次；生产切换及逐入口迁出；包与档案回退演练 | 正式资料及使用范围、已有原型证据和正式迁移决定 |

## 每个获准的后续 Task 怎样验收

写明操作者、固定输入、真正要改的第一个函数与文件、它怎样迁到共同能力、已有两个可以验证的调用方、失败如何还原、对应的前置与后继。测试至少含正常使用、会误写或中断的输入、适用的持久化和显示。记录可否复现以及当时的代码和数据。只创建模块或生成类型不算结束。负责人决定长期策略前，可用协商好的测试副本继续验证其他独立批次。
