# docs/0x-plan&work/active/task-0021-datapack-workspace-repair — 数据包工作区功能修复

> 本文回答：如何将当前“数据包管理”首版工作区修复为可用的包库、启用集编辑、校验、应用与结果反馈页面。
> 当前状态：第一阶段闭环已落地；二次易用性、安全边界与依赖可视化方案已补充，待按本文第 15 节继续实施。
> 设计依据：[[docs/0x-plan&work/active/adr-0004-datapack-management]]、[[docs/0x-plan&work/active/roadmap-0020-service-workspaces]]、[[docs/0x-plan&work/registry&saves/04-service-workspace-plan]]。

## 当前核验状态（2026-09-06）

本文第 1 节保留为修复前问题快照。当前实现已完成其中的主要第一阶段修复：左侧分类具有工作区状态、启用集使用草案、校验与确认应用分离、基础包不可停用、依赖状态可见、未应用草案离开时会拦截，且应用前会执行存档保存检查。尚未完成的是独立导入预览、完整 Registry dry-run/回滚、内容哈希展示、全量残留管理和移动端抽屉体验。

## 1. 背景与问题结论

当前 Edge 中的数据包页已经接入统一的三栏工作区和主题表现层：

- 页面使用 `centerPanel.datapack.navigation`、`centerPanel.datapack.main`、`centerPanel.datapack.inspector` 三个 UI Host；
- 页面背景、面板和按钮已经能继承当前主题，SVG 三角形背景也能正常显示；
- 顶部“数据包”入口能够进入工作区；
- 包库弹窗能够显示已导入包、启用状态、依赖提示和排序按钮。

但当前页面仍是“工作区外壳 + 旧包库弹窗”的拼接，核心功能没有形成完整闭环。主要缺陷如下。

### 1.1 左侧导航是静态按钮

`全部数据包`、`已启用`、`未启用`、`有问题`、`导入` 只负责渲染，没有对应的 `section` 状态，也没有事件绑定和列表筛选。

证据：`src/ui/components/service-workspace.ts` 的 `renderNavigation()` 只输出按钮；`src/ui/controller-actions-topbar.ts` 没有绑定 `.service-nav-item`。

结果：点击左侧分类后页面不变，用户无法进入已启用、未启用、有问题或导入子页面。

### 1.2 “当前启用集”没有过滤启用状态

`renderDatapackMain()` 将完整 `catalog.entries` 传给 `renderPackCatalog()`，所以“当前启用集”区域显示的是所有已导入包，而不是当前启用包。

结果：标题、数量和列表内容的语义不一致；用户无法区分包库总量和当前 Registry 来源。

### 1.3 启用集变更没有草案层

当前包库按钮直接调用运行时命令：

```text
点击启用/停用 → setPackEnabled → applyEnabledPacks → game.reload
点击上移/下移 → reorderPacks → applyEnabledPacks → game.reload
```

这违反服务工作区已经确定的流程：

```text
当前正式配置 → 编辑待应用草案 → 校验 → 确认 → 应用 → 反馈结果
```

当前行为会造成：

- 单次点击就重建 Registry；
- 单次点击就清空并重建运行时状态；
- 没有查看变更范围的机会；
- 没有放弃草案功能；
- 没有失败后的旧配置保持提示；
- 没有应用成功后的结果和回滚入口。

### 1.4 导入会自动启用并立即重载

当前导入路径执行：

```text
解析 ZIP → 加入包库 → setEnabled(true) → applyEnabledPacks → reload
```

但页面文案写的是“导入后仍需单独决定是否启用”，设计文档也规定导入、加入包库和启用应分步完成。

目标行为应为：

```text
选择来源 → 解析预览 → 查看报告 → 加入包库 → 用户决定是否加入待应用启用集
```

### 1.5 右栏没有真实的选中对象

当前没有 `selectedPackId`，右栏只能显示固定文案，无法展示：

- manifest 信息；
- 来源类型、版本和导入时间；
- 内容哈希（若当前存储模型已提供）；
- 依赖及状态；
- 同 `modName` 的其他版本；
- 包内实体数量；
- 解析警告和错误；
- 当前启用草案对 Registry、图片和存档的影响。

### 1.6 “有问题”没有问题模型

当前只有简单的依赖提示，没有统一的校验报告，不能区分：

- 缺失依赖包；
- 同 `modName` 冲突；
- 版本替换；
- 循环依赖；
- Registry 重复定义；
- 悬空引用；
- Tag parent / TagRef 问题；
- 图片资源变化；
- 可能进入存档残留的实体。

### 1.7 当前运行时状态会在包应用时丢失

`applyEnabledPacks()` 最终调用 `game.reload()`，而 `reloadRuntime()` 会执行 `reset()`，重新创建默认 `PlayerState`。这会清除当前 `activeTheme`、进度和其他运行时状态。

该问题与数据包工作区修复强相关：应用按钮必须明确展示影响，并且不能把“浏览包库”误变成“立即重置游戏”。状态保留、残留和兼容策略应按 ADR-0004 的存档规则另行实现，但本任务至少要保证 UI 明确告知当前实现的影响，不能继续以静默方式发生。

## 2. 任务目标

将数据包页改造成一个正式的服务工作区，完成以下闭环：

```text
浏览包库 → 选择数据包 → 查看详情与问题 → 编辑启用集草案
→ 查看变更与影响 → 校验 → 确认应用 → 显示结果
```

必须满足：

1. 浏览、筛选、选择数据包不会改变运行时；
2. 启用、停用、排序先进入草案，不立即重载；
3. 导入先进入包库，不默认启用；
4. 校验失败时保持旧启用集和旧运行时；
5. 应用前展示 Registry、图片、存档和主题可能受到的影响；
6. 应用后显示成功/失败结果，并保留可继续修复的上下文；
7. 页面继续使用统一的三栏渲染和 UI Host 机制。

## 3. 目标信息架构

### 3.1 顶部区域

顶部仅负责进入数据包工作区，不直接执行导入、启用、停用、排序或重载。

可展示轻量摘要：

```text
数据包 2 个启用 · 1 项待应用变更 · 当前配置有效
```

### 3.2 左栏：分类与列表

第一阶段至少支持：

```text
全部数据包
已启用
未启用
有问题
导入
```

后续可增加：

```text
依赖缺失
同 modName 的其他版本
最近导入
```

列表项必须显示：

- 名称；
- `modName`；
- 版本；
- 来源类型；
- 正式启用状态；
- 草案启用状态；
- 问题数量或状态徽标；
- 是否为内置基础包。

所有状态必须同时有文字和图标/颜色，不得只依靠颜色。

### 3.3 中栏：启用集编辑器

中栏根据左栏分类显示包列表或导入流程。

启用集编辑器需要明确区分：

```text
当前正式配置
待应用配置
```

每个包支持：

- 加入/移出待应用启用集；
- 调整加载顺序；
- 在同 `modName` 的多个版本中选择一个；
- 查看是否会产生冲突；
- 显示草案变更类型。

变更类型至少包括：

- 新增启用；
- 停用；
- 排序变化；
- 版本替换。

底部固定操作区提供：

- `放弃修改`；
- `校验启用集`；
- `应用启用集`。

无草案变更时，放弃和应用按钮应禁用。

### 3.4 右栏：详情、问题与影响

未选择包时显示解释性空状态和“选择一个数据包查看详情”。

选中包时显示：

- manifest；
- 来源和版本；
- 导入时间；
- 内容统计；
- 依赖及状态；
- 同 `modName` 包版本；
- 解析警告与错误；
- 当前/草案启用状态。

存在待应用草案时显示：

- 变更数量；
- Registry 重建影响；
- 图片索引影响；
- 可能失效的引用；
- 可能进入存档残留的实体；
- 当前主题/色彩组可能失效的提示；
- 是否需要重新开始当前会话。

## 4. 建议状态模型

数据包工作区需要有独立 UI 状态，不得把草案直接写进 `PackManager` 的正式状态。

建议增加或等价实现以下状态：

```ts
interface DatapackWorkspaceState {
  section: 'all' | 'enabled' | 'disabled' | 'issues' | 'import';
  selectedPackId: string | null;
  draftEnabledIds: Set<string>;
  draftOrder: string[];
  validation: ValidationState;
  lastResult: ApplyResult | null;
  importState: ImportPreviewState | null;
}
```

其中：

- `section` 控制左栏分类；
- `selectedPackId` 控制右栏详情；
- `draftEnabledIds` 与 `draftOrder` 只代表待应用配置；
- `validation` 保存最近一次校验结果；
- `lastResult` 保存最近一次应用成功/失败结果；
- `importState` 保存解析预览，不直接改变正式启用集。

集合类型可以根据现有状态管理方式使用 `ReadonlySet`、数组或不可变快照，但必须保证渲染层不可直接修改正式 `PackManager` 数据。

## 5. 运行时接口改造要求

### 5.1 正式配置与草案分离

现有 `PackManager` 的正式状态继续负责：

- 包库；
- 正式启用集；
- 正式排序；
- 持久化。

UI 工作区新增草案层，负责：

- 修改启用状态；
- 修改排序；
- 计算差异；
- 请求校验；
- 用户确认后提交。

不得在用户点击单个开关时调用 `game.reload()`。

### 5.2 校验接口

需要有可消费的校验结果，而不是只抛出异常。建议报告至少包含：

```ts
interface DatapackValidationReport {
  ok: boolean;
  errors: ValidationIssue[];
  warnings: ValidationIssue[];
  changes: PackChangeSummary;
  impact: PackImpactSummary;
}
```

校验至少包含：

- `modName` 冲突；
- Registry 表重复或非法定义；
- 跨表引用错误；
- Tag 引用问题；
- 图片资源变化；
- 依赖提示；
- 被停用包的内容残留提示。

现有 `Registry` dry-run 可作为基础，但必须把结果转换成 UI 可展示的报告。

### 5.3 应用接口

应用流程应保证：

```text
校验通过 → 用户确认 → reload → 重建 Registry / 图片索引 → 返回结果
校验失败 → 不 reload → 保持旧配置和旧运行时
```

应用失败时必须：

- 保持旧正式启用集；
- 保持旧运行时可继续使用；
- 保留当前草案；
- 在右栏显示失败阶段和原因；
- 允许用户继续修复或放弃草案。

### 5.4 导入接口

导入流程必须拆成三个阶段：

1. 解析 ZIP；
2. 显示预览并加入包库；
3. 用户决定是否加入待应用启用集。

预览至少显示：

- manifest；
- JSON 数量；
- 图片数量；
- 被忽略文件；
- 解析错误和路径；
- `modName`、版本和内容哈希；
- 与已有包的同名/同版本关系。

导入包不应自动启用、自动替换当前运行内容或自动删除存档。

## 6. 主题与存档影响

本任务不在数据包页面内重新设计主题系统，但必须把影响说清楚。

当草案停用或替换提供 `ColorGroup` 的数据包时，校验报告应指出：

- 当前 `activeTheme` 是否引用该包中的色彩组或主题内容；
- 当前主题是否会回退；
- 哪些实体的 `colorGroupId` 可能失效；
- 当前页面是否需要重新注入主题变量。

当应用启用集会触发运行时重载时，页面必须明确展示当前实现会影响的运行时状态。若后续按 ADR-0004 实现状态保留，则应增加对应测试，确认仍有效的 `activeTheme`、存档数据和残留数据按规则处理。

## 7. 分阶段施工顺序

### P0：修复当前页面语义和死控件

- 增加数据包页面的 `section` 与 `selectedPackId`；
- 绑定左栏导航；
- 正确筛选全部/已启用/未启用；
- 将“当前启用集”改为只显示正式启用包；
- 选中包后右栏显示基础详情；
- 保留统一 UI Host 和三栏渲染入口。

验收：左侧每个分类都能改变中栏内容；点击包条目能改变右栏详情；浏览过程不触发 reload。

### P1：建立启用集草案

- 从正式 `PackManager` 创建草案；
- 支持启用/停用和排序编辑；
- 显示新增、停用、排序、版本替换计数；
- 增加放弃草案；
- 切换服务或离开页面时提示未应用变更；
- 删除包库弹窗中的即时应用逻辑。

验收：编辑开关和顺序时运行时不变化；放弃后恢复正式配置；页面显示待应用数量。

### P2：校验与影响预览

- 将 Registry dry-run 转换成结构化校验报告；
- 显示错误、警告、依赖、冲突和残留影响；
- 接入右栏问题和影响区；
- 无变更或校验失败时禁用应用按钮；
- 增加旧配置保持提示。

验收：错误配置无法应用；失败后旧 Registry 和旧页面仍可继续工作；用户能定位具体包和问题。

### P3：确认应用与结果反馈

- 应用前显示确认摘要；
- 应用中禁用重复提交；
- 应用后刷新 Registry、图片索引和页面；
- 成功显示应用结果、变更计数和主题/存档影响；
- 失败保留草案并提供重试/放弃。

验收：应用成功、失败、取消三条路径都有明确反馈；失败不丢失旧配置。

### P4：导入预览流程

- 将文件选择器入口转为导入子页面；
- 显示解析报告；
- 支持加入包库但暂不启用；
- 允许从预览页将包加入待应用草案；
- 删除导入成功后自动启用和自动清档行为。

验收：只导入不改变当前运行内容；用户确认应用后才会重建 Registry。

### P5：高级包库能力

- 删除包并进行启用状态、依赖和存档残留检查；
- 同 `modName` 多版本选择；
- 依赖缺失、循环依赖和引用问题分类；
- 内容统计和来源跳转；
- 应用历史和最近失败原因。

## 8. 测试要求

### 8.1 UI 测试

新增或扩展数据包工作区测试，至少覆盖：

- 左栏分类筛选；
- 正式启用集与全部包的区分；
- 选中包与右栏详情；
- 草案开关和排序；
- 放弃草案；
- 未应用变更提示；
- 校验错误展示；
- 应用成功/失败反馈；
- 导入预览不自动启用；
- UI Host 仍正确注册并继承主题作用域。

### 8.2 数据服务测试

扩展 `tests/data/pack-manager.test.ts`，覆盖：

- 正式配置与草案互不污染；
- 校验失败不触发 reload；
- 应用成功只 reload 一次；
- 应用失败保持旧配置；
- 排序草案不提前持久化；
- 导入包可加入包库但不自动启用。

### 8.3 运行时回归测试

增加数据包应用与运行时状态的回归测试，明确记录当前目标语义：

- 当前主题在包仍存在时是否保留；
- 当前主题所属包被停用时如何回退；
- Registry 重建后图片索引是否正确；
- 存档和残留数据的处理是否符合 ADR-0004。

## 9. 不应保留的旧行为

- 左栏分类只显示但不可操作；
- “当前启用集”展示全部导入包；
- 点击启用/停用立即重载；
- 点击排序立即重载；
- 导入后自动启用；
- 导入后自动删除存档；
- 右栏固定文案代替选中包详情；
- 校验失败只通过异常字符串展示；
- 应用失败后丢失草案或无法确认旧配置仍在运行。

## 10. 完成标准

完成本任务后，玩家或数据包作者应能够：

1. 从顶部进入数据包服务；
2. 浏览、筛选并选择一个数据包；
3. 查看 manifest、依赖、版本和问题；
4. 编辑启用集和加载顺序而不立即改变运行时；
5. 查看变更计数和影响范围；
6. 校验启用集；
7. 在确认后应用；
8. 在失败时确认旧配置仍在使用，并继续修复；
9. 导入一个包但暂不启用；
10. 在全流程中保持统一三栏页面、主题、键盘可访问性和清晰状态反馈。

## 13. 易用性检查结果

### 13.1 检查范围与方法

本次检查以当前 Edge 中的真实数据包页为对象，按普通用户的核心任务路径走查：

```text
进入数据包页 → 判断当前状态 → 查看已启用包
→ 筛选/选择数据包 → 查看问题 → 编辑启用集
→ 撤销或应用变更 → 导入新包
```

同时检查了键盘/可访问性树中的控件名称、当前状态表达和页面文案与实际行为是否一致。

### 13.2 P0：会导致误操作或任务失败的问题

#### P0-1 页面承诺与实际操作相反

页面标题下方写着“先预览和校验，再决定是否启用”，但用户在包卡片上看到的就是“启用/停用”即时按钮，点击后会触发运行时重载。

用户无法理解：

- 当前点击是在编辑草案，还是已经改变正式配置；
- 是否还有确认步骤；
- 失败后旧配置是否还在；
- 是否可能影响当前进度和主题。

修复要求：正式配置和待应用草案必须使用明显的状态标签，并把“应用”作为单独的确认动作。

#### P0-2 高影响操作没有影响预览

启用、停用和排序都可能改变 Registry、图片索引、存档可见性和当前主题，但当前界面没有显示影响范围，也没有确认提示。

这尤其容易造成用户在没有意识到的情况下改变默认配色或丢失当前激活主题。

修复要求：应用前必须显示变更计数、受影响的数据包、主题/存档风险和失败处理方式。

#### P0-3 导入流程无法安全预览

用户点击“导入数据包”后直接进入文件选择和运行时处理，没有在页面内看到 manifest、文件统计、解析错误、同名包和启用影响。

当前导入成功后还会自动启用并重载，违反“导入后再决定是否启用”的页面文案。

修复要求：将导入拆为解析预览、加入包库、加入待应用启用集三个动作。

### 13.3 P1：用户会迷失或无法判断页面状态的问题

#### P1-1 左侧导航看起来可用，但点击没有反馈

当前左栏有五个分类按钮，视觉上“全部数据包”带选中态，其余显示“查看”，但点击“已启用”“未启用”“有问题”“导入”后页面没有变化。

这会让用户误判是操作失败、页面加载失败，还是该功能尚未实现。

修复要求：

- 分类按钮必须切换中栏内容；
- 当前分类使用 `aria-current` 和明确文字状态；
- 分类旁显示数量；
- 空分类显示解释性空状态和下一步操作。

#### P1-2 “当前启用集”和“已导入数量”语义冲突

当前中栏标题为“当前启用集”，右侧却显示“2 个已导入”，代码还将全部包传入列表。

用户无法回答最基本的问题：

```text
我有多少个包？
当前实际运行了哪些包？
还有哪些包只是存放在包库里？
```

修复要求：同时展示：

- `包库：N 个已导入`；
- `当前启用：M 个`；
- 中栏“当前启用集”只列正式启用项；
- “全部数据包”分类才列出全部包。

#### P1-3 右栏标题暗示有选择，但页面没有选择机制

右栏显示“当前选择”，内容却是固定的“先校验，再应用”和“下一步”。包卡片不是可选择控件，也没有当前选中包标记。

修复要求：

- 包条目可点击或可键盘选择；
- 选中态同时使用边框、文字或图标表达；
- 右栏标题改为具体包名；
- 未选择时显示“请选择一个数据包查看详情”；
- 右栏操作必须针对当前选中对象。

#### P1-4 两个入口的职责重叠

中栏同时显示“导入数据包”和“打开包库详情”。左侧又有“导入”分类，用户不清楚：

- 哪个入口负责导入；
- 哪个入口负责查看包；
- 哪个入口负责启用；
- 是否会立即改变运行时。

修复要求：将导入、包库浏览和启用集编辑收束到同一工作区；保留一个主入口，其他入口只作为明确的上下文跳转。

### 13.4 P2：反馈、可访问性和恢复能力不足

#### P2-1 没有操作结果保留区

用户完成启用、停用、排序或校验后，页面没有持续显示最近一次操作结果。短暂 Toast 不能替代“旧配置仍在/新配置已应用/应用失败”的可追溯状态。

修复要求：右栏或页面底部保留最近操作记录，至少显示时间、操作、结果和下一步。

#### P2-2 没有撤销、放弃或离开保护

当前没有未应用变更概念，也没有离开页面时的提示。后续草案实现必须避免用户编辑后切换服务导致变更无声丢失。

修复要求：存在草案时显示“未应用变更”，离开数据包页或切换服务时提供继续编辑、放弃或返回三种选择。

#### P2-3 状态表达过度依赖视觉样式

当前选中分类主要依靠浅蓝背景和左侧标记表达，数据包启用状态也主要依靠按钮文字和颜色。需要确保缩放、低对比度和键盘操作下仍能理解状态。

修复要求：

- 使用 `aria-current`、`aria-selected` 或等价语义属性；
- 启用、停用、问题和草案状态使用文字徽标；
- 禁用按钮提供可理解的原因；
- 焦点样式清晰可见；
- 模态框打开后焦点进入模态框，关闭后返回触发按钮。

#### P2-4 窄屏任务路径尚未验证

三栏布局在窄屏下必须保证核心动作仍可见，不能把导入、校验、应用或错误详情隐藏在不可发现的区域。

修复要求：窄屏时左栏折叠为可返回抽屉，右栏变为详情页；中栏保留当前列表和主要操作。

### 13.5 易用性验收场景

实现完成后必须由测试或人工走查验证以下场景：

1. 新用户进入数据包页，能在 5 秒内分辨“已导入”与“当前启用”；
2. 用户点击“已启用”后能看到只包含正式启用包的列表；
3. 用户选择一个包后能在右栏看到名称、版本、来源和依赖；
4. 用户停用一个包时，页面先显示待应用草案，不立即改变游戏；
5. 用户能看到停用该包对主题、Registry 和存档的影响；
6. 用户可以放弃草案，页面和运行时恢复正式配置；
7. 用户校验失败时能定位具体问题，且旧配置仍可继续运行；
8. 用户导入一个包时能查看解析结果，并选择暂不启用；
9. 用户应用成功后能看到应用结果和新的启用集；
10. 用户应用失败后能继续编辑原草案，而不是回到无上下文的空页面；
11. 键盘用户可以完成筛选、选择、校验、确认和取消；
12. 窄屏用户仍能完成上述核心流程。

### 13.6 本次走查结论

当前页面的视觉层级和统一主题接入已达到可继续施工的基础，但可用性等级仍属于“不可交付”：

- 入口存在，但分类导航不工作；
- 信息存在，但正式配置与包库内容混在一起；
- 操作存在，但没有草案、确认和影响预览；
- 右栏存在，但没有对象详情；
- 文案表达了安全流程，实际行为却是即时重载。

因此实施顺序必须先解决 P0 的误操作风险，再补 P1 的状态与导航，最后处理 P2 的反馈、可访问性和窄屏体验。

## 14. 已落地的第一阶段修复

截至当前阶段，数据包工作区已完成以下闭环：

- 左侧分类已连接到页面状态：全部、已启用、未启用、有问题、导入；
- 数据包条目支持选中、正式启用状态、草案启用状态和排序操作；
- 中栏使用启用集草案，不再在点击条目时直接重载运行时；
- 已增加启用集校验、应用前确认、应用成功/失败反馈；
- 应用前由包管理器和 Registry 双重校验，重载失败时保留旧正式配置；
- 导入流程先展示 manifest、JSON、图片和忽略文件信息，确认后才加入包库，且默认不启用；
- 导入加入包库后不删除存档、不改变当前运行内容；
- “有问题”分类按缺失依赖计算数量；
- 数据包页继续使用统一 Service Workspace 与主题 UI Host；
- 已补充数据包配置草案、应用成功和应用失败的测试覆盖。

仍待后续阶段处理：离开页面时的未应用变更保护、应用影响的更细粒度预览、包删除/卸载、窄屏三栏折叠策略，以及完整的模态框焦点返回管理。

## 15. 二次易用性与运行时安全方案

本节针对第一阶段走查后仍然存在的实际问题补充约束。重点不是继续增加按钮，而是让“浏览、编辑、保存、确认、重载”成为互相隔离且可解释的阶段。

### 15.1 核心原则

数据包页面必须遵循以下不可混淆的状态流：

```text
包库快照
  ↓ 浏览 / 筛选 / 查看依赖
启用集草案
  ↓ 任意编辑（只改草案）
已保存草案
  ↓ 校验
待确认应用
  ↓ 用户确认 + 当前存档已保存
重新加载数据包序列
  ↓
新的正式配置与运行时 Registry
```

其中：

- 浏览包库、展开详情、查看依赖、筛选分类都不得触发运行时变化；
- 加入、移出、排序、版本选择都只修改内存中的工作区草案；
- 草案可保存为“待应用配置”，但保存草案本身不得 reload；
- 只有在“草案已保存 + 校验通过 + 用户确认”后，才允许重载数据包序列；
- 应用失败时保留旧正式配置、旧运行时和当前草案，不得自动回退到无上下文页面。

### 15.2 数据包移动与应用边界

“移动数据包”包含两类不同动作，必须在 UI 和运行时接口上分开：

#### A. 草案内移动

用户点击“上移”“下移”时，只改变草案中的 `draftOrder`：

- 不调用 `reload`；
- 不清空图片索引；
- 不改变当前 Registry；
- 不改变当前主题；
- 不写入正式启用集；
- 在页面上显示“加载顺序已修改，尚未应用”。

#### B. 正式序列应用

只有满足以下条件时才可执行：

1. 草案已显式保存，得到可识别的草案版本或草案快照；
2. 校验报告为通过，或用户明确确认可接受的警告；
3. 当前游戏存档已经保存成功；
4. 页面显示应用摘要；
5. 用户在确认框中确认“保存当前进度并重新加载数据包序列”。

确认框至少显示：

- 新增启用包；
- 停用包；
- 顺序变化；
- 同 `modName` 的替换；
- Registry 将重新建立；
- 图片资源和主题可能重新解析；
- 当前运行是否会被重置或重建；
- 存档保存失败时不会继续应用。

不应允许“点击排序后立即生效”或“导入后自动替换当前序列”。数据包导入、草案保存和正式应用必须是三个独立动作。

### 15.3 存档前置条件

数据包序列变化可能改变 Registry、图片、主题、故事入口和实体引用，因此应用操作应采用“保存并确认”的安全流程：

```text
点击应用
  → 校验草案
  → 生成影响摘要
  → 请求保存当前进度
  → 保存成功后打开最终确认
  → 用户确认
  → reload 数据包序列
  → 重建 Registry / 图片索引 / 主题派生
  → 返回应用结果
```

特殊情况：

- 当前没有可保存进度时，应明确显示“当前没有可保存的存档”，不能让用户误以为已经完成保护；
- 保存失败时停止流程，保留草案和旧运行时；
- 用户取消保存或最终确认时，不改变任何正式配置；
- 应用过程中失败时，报告失败阶段，并保留旧配置或进入明确的恢复状态；
- 不得通过静默清档解决数据包不兼容问题。项目当前允许旧存档失效，但必须由用户确认并看到结果。

建议应用结果使用明确的状态机，而不是只保存一条字符串：

```ts
type PackApplyPhase =
  | 'editing'
  | 'saved-draft'
  | 'validating'
  | 'awaiting-save'
  | 'awaiting-confirmation'
  | 'reloading'
  | 'applied'
  | 'cancelled'
  | 'failed';
```

### 15.4 依赖关系与序列内状态

数据包详情必须把“声明依赖”和“当前启用集是否满足”分开显示，不能只显示 `base · 已启用` 这种拼接文本。

每一条依赖至少需要以下字段：

```ts
interface DatapackDependencyView {
  dependentPackId: string;
  dependencyModName: string;
  requiredRange?: string;
  resolvedPackId?: string;
  resolvedVersion?: string;
  availability: 'enabled-in-sequence' | 'available-not-enabled' | 'missing';
  orderRelation?: 'before' | 'after' | 'same' | 'unknown';
  affectsDraft: boolean;
}
```

UI 文案建议：

| 状态 | 文案 | 处理建议 |
| --- | --- | --- |
| `enabled-in-sequence` | 依赖：基础内容 · 已在当前序列 | 正常 |
| `available-not-enabled` | 依赖：基础内容 · 包库已有，但未加入当前序列 | 提供“加入草案” |
| `missing` | 依赖：基础内容 · 包库中不存在 | 指向导入入口 |
| 版本不满足 | 依赖：基础内容 · 版本不满足要求 | 显示要求与当前版本 |
| 顺序异常 | 依赖：基础内容 · 位于依赖之前 | 建议调整顺序 |

依赖信息应出现在三个位置：

1. 数据包列表卡片：显示问题等级和简短状态；
2. 右侧详情：显示完整依赖树、解析到的包和版本；
3. 草案影响摘要：显示本次修改是否会使依赖从“序列内”变为“序列外”。

必须区分以下概念：

- 包存在于包库；
- 包存在于当前正式序列；
- 包存在于待应用草案序列；
- 包在序列中的位置满足依赖要求。

“有问题”分类应基于结构化校验问题生成，不再只统计缺失依赖。至少覆盖缺失依赖、未启用依赖、版本不满足、加载顺序异常、`modName` 冲突和 Registry 加载失败。

### 15.5 滚动与内容不被挤出

当前三栏容器已经设置了基础 `overflow-y: auto`，但底部“启用集草案”在实际视口中仍可能被列表推到屏幕外。滚动策略应从“整个页面自行滚动”调整为“每个内容区承担自己的滚动职责”。

桌面布局建议：

- 左栏独立纵向滚动，保持分类入口可访问；
- 中栏独立纵向滚动，包列表和草案详情不能把操作区挤出；
- 右栏独立纵向滚动，长依赖树和影响报告不能撑破布局；
- 中栏的草案操作区在有待应用变更时使用 `position: sticky` 固定在中栏底部；
- sticky 区域必须有不透明背景、上边框和足够的底部内边距，避免遮挡最后一条数据包；
- 任何列表都不能通过固定高度裁剪错误信息、依赖关系或确认按钮。

窄屏布局建议：

- 900px 以下不应直接丢弃右栏，应把详情转换为抽屉或中栏下方的可展开面板；
- 640px 以下左栏改为可折叠分类条，中栏保留列表和草案操作；
- 导入预览、校验报告和应用确认都必须在当前滚动容器内完整可达；
- 当键盘焦点进入 sticky 操作区时，浏览器应自动滚动使其完整可见；
- 页面切换分类后应将中栏滚动位置重置到顶部，返回详情时保留选中包；
- 长依赖树使用局部滚动或分组折叠，不得把整个确认区域推到不可见位置。

滚动验收条件：

1. 20 个以上数据包时，最后一个包的操作按钮可访问；
2. 校验错误超过 5 条时，错误列表可以滚动且应用按钮仍可达；
3. 依赖树超过视口高度时，详情标题和应用状态仍可判断；
4. 375px 宽度下仍能完成选择、查看依赖、保存草案、校验和取消；
5. 浏览器缩放到 200% 时没有横向溢出导致关键按钮消失。

### 15.6 基础包与不可移动项

内置基础包不能继续以普通可停用包呈现。包目录模型应向 UI 暴露至少一个能力字段：

```ts
interface PackCapabilities {
  required: boolean;
  removable: boolean;
  reorderable: boolean;
  enableable: boolean;
}
```

对基础包的建议表现：

- 显示“核心包 / 始终启用”；
- 不显示“移出启用集”；
- 不允许拖到会破坏基础依赖的位置；
- 详情中解释“其他数据包可能依赖此包”；
- 校验接口仍然拒绝草案移除基础包，避免 UI 绕过约束。

### 15.7 实施顺序

建议按以下顺序继续施工：

#### P0：阻止未保存、未确认的运行时重载

- 所有启用、停用、排序和版本切换只修改草案；
- 增加草案保存状态；
- 应用前强制保存当前存档；
- 保存成功后再确认；
- 只有最终确认后才 reload。

#### P1：修复基础包与依赖语义

- 增加 `required` 和能力字段；
