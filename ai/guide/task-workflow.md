# Task 工作流

Task 是交给施工者的工程规格。它说明为什么要改、系统如何运作、改成什么、怎样迁移以及如何判定交付。需要跨会话跟踪、协作或交接时建立 Task，普通小需求可以直接处理。立项讨论与调查证据可另存，施工者从 Task 正文取得本次建设所需的设计。

## 创建与协作

```powershell
npm run task -- newTask <slug> "<标题>"
npm run task -- newSubtask <task-id> "<范围>" "<负责人>"
npm run task -- archive <task-id>
```

`newTask` 从 [[ai/guide/templates/execution-task]] 生成骨架，以活动文件和 `ai/archive/history.zip` 中的最大编号递增，写入文件名、标题和 `ai/plan/00-index.md`。创建时状态为「待处理」。交付规格前，先按 [[ai/guide/task-read-set-routing]] 核对改动涉及的源码、直接调用方和测试，再填写正文并删除模板提示。已知领域直接走 [[AGENTS]] 的对应入口。

有独立分工时才用 `newSubtask`。命令登记范围、负责人和状态，实际分派由协作者负责。工具优先在「施工记录」前建立 `SubTasks` 表，兼容在旧文档的「相关文件与资料」前插入，两处都没有时追加到文末。执行者更新表中状态，交付后再用 `SubOutcomes` 记录实际结果、证据和问题。整合结论确有需要时可以另写 FinalOutline。整体状态留在 Task 头部，分工状态和各自结果各有一处权威记录。

## 编写施工规格

完整建设型 Task 默认采用以下结构。目标设计是正文主体。公共服务、数据或持久化结构、多个消费者的迁移、共享 UI、退役旧服务、新模块和重要原型衍生任务，应充分交代目标设计、施工、迁移边界和验收。

1. **任务目标与范围**。说明要解决的具体问题、交付的能力和使用者能获得的结果。原型衍生 Task 写明负责模块的哪部分建设，将原型和批次编号作为追踪入口。
2. **当前实现**。说明直接相关的数据结构、服务、入口、消费者和问题，用核实过的源码路径、符号及调用关系支撑。现有事实与待建设的结构分开写，保留能解释这次改造的依据。
3. **目标设计**。写明模块和职责、数据由谁持有和读写、公共入口的输入输出及失败结果。数据改造给实际字段、类型或可施工的示例。界面写清区域、控件、布局、状态与操作结果。公共化须写明共同服务接管的职责、各调用方仍要提供的内容、原实现的去向，以及如何与相邻服务协作。已确认的结构明确写出，私有实现细节可留给施工者。
4. **施工方案**。按服务或建设阶段说明如何从现状落到目标。写实际能力如何建立、入口如何接线、数据怎样迁移、何时退出旧职责。文件定位、调查和测试可以支撑施工方案，建设动作与迁移结果仍须写清。
5. **依赖与施工边界**。分别说明开工所需条件、交付某项功能所需条件、可并行工作及后续消费者。明确要保留的行为和已确认的约束。同属一个原型的多个任务按实际依赖安排。
6. **验收标准**。从真实入口描述正常操作、必要的失败行为和可观察结果。涉及迁移时核对真实消费者改接及旧职责退出。测试提供证据，验收以系统行为和实际产物为准。
7. **工作项**。用复选框索引可独立确认的建设成果或迁移阶段。条目应能对应前面的设计和施工方案，设计细节留在正文。
8. **施工记录**。未开工时写「待施工」。开工后记录实际进展、问题、设计偏差、验证和最终交付；交接时写明首个可执行的下一步。改动已确认设计时同步修订正文，并在记录中注明变更原因。

用完整的中文段落解释因果、行为和施工决策。列表适合工作项和并列规则，表格适合字段及行为对照，代码块适合实际结构和样例。「统一合同」「稳定身份」「保持行为」等概括必须落到对象、字段或可观察结果。复杂设计按主题开小节，禁止用术语堆叠、调查步骤或测试清单代替设计和建设。兼容方案服务于已经确认的结构改造，禁止借兼容或最小改动缩减建设范围。修订时逐项保留已确认要求和仍有效的证据；裁定改变时交代改变了哪项要求。确有未决细节时，给出当前推荐结构、待确认的问题及判定依据。

原型衍生 Task 应独立写明自己负责的设计。引用蓝图用于追踪来由、联系相邻工作，接手者应能从 Task 直接理解本次施工和失败处理。调查资料可以单独跟踪，包含调查入口、方法和预期产出；进入施工前，把调查结论转成可执行的设计。

交付前按接手者的视角复读。能否指出第一处建设动作、解释数据如何穿过真实调用，以及判断一次失败后应得到什么结果？按实际建设补齐缺失内容。篇幅由设计需要决定，章节数、字数和列表数量均无机械门槛。

## 小任务怎样写

局部修复可合并现状、预期和改法，再写可观察的验收。只有确实需要追踪时才加工作项和施工记录。以下示范取自已完成的 Runtime Editor 面板滚动修复（提交 `f2565ef1`），按开工前的短规格呈现。

### 修复范围与改法

运行时编辑器交由外层面板滚动，切换到较长的编辑页会牵动整个面板。调整 `src/ui/css/runtime-editor.css`，让 `.runtime-editor-panel-body`、表单与网格限制在可用高度内，由右侧 `.runtime-editor-panes` 独立纵向滚动，左侧切换区留在原位。

### 验收

打开运行时编辑器并切到长表单页，右侧可滚到末尾，左侧切换区始终可用。再切到短页，面板高度和左侧位置保持稳定。

## 完成与归档

按实际结果更新头部状态及施工记录，标明执行过的验证及仍需核对的事项。Task 已完成或取消，且没有待分派、进行中或受阻的 SubTask 时，用 `npm run task -- archive <task-id>` 写入归档并移出活动索引。配套资料另用 `npm run archive:docs -- add <路径>`，归档后核对现行引用。操作细节见 [[ai/archive/README]]。

生命周期命令按文件、索引、状态和可选的 `SubTasks` 表工作。旧格式和合并章节的小 Task 可继续登记、分工和归档。当前待施工 Task 按实际需要迁移格式，已有规格和授权仍然有效。文档检查按 [[ai/guide/conventions/doc-maintenance]] 验证可机械检查的内容，设计质量由阅读和评审判断。
