# Task 工作流

Task 是 Agent 恢复工作所需的入口：说明目标、完成条件、当前进展和下一步。只为需要跨会话跟踪、协作或交接的工作建 Task；普通小需求直接处理。默认模板见 [[ai/guide/templates/execution-task]]。

## 创建与协作

```powershell
npm run task -- newTask <slug> <标题>
npm run task -- newSubtask <task-id> <范围> <负责人>
npm run task -- archive <task-id>
```

`newTask` 从默认模板生成待补全骨架并登记 `ai/plan/00-index.md`，不分析源码、不自动完成方案；Agent 按下节补全后才可交付。编号扫描活动 Task 与 `ai/archive/history.zip`，递增且不复用。`newSubtask` 只在确有独立分工时使用：它在父 Task 的 `SubTasks` 表追加 ID、范围、负责人和状态，不会自动派发 Agent。执行者更新该表的状态；完成后才在 `SubOutcomes` 添加实际结果、证据和问题。没有分工时不创建这两个章节。

按任务需要添加文件清单、事实与决定、验证细节或 FinalOutline。不要为预想中的可能性预建空章节，也不要在多个位置重复负责人、状态、结果或证据：Task 维护整体状态和下一步，SubTasks 维护分工状态，SubOutcome 维护子任务交付，FinalOutline 仅负责需要整合时的最终结论。

## 编写具体、可执行的 Task

先读取命中的源码、调用方及相关测试，再写当前依据与改动方案。严禁以兜圈子的原则口号、粗糙行为清单或纯粹设想交付 Task；“优化结构、明确边界、保持行为、完善测试”等表述必须落到具体对象与调整方式。仅列文件名或验收场景不构成实施方案。

- **当前依据**：指出已核实的文件和关键符号，以及要解决的具体重复、耦合、缺陷或缺失。区分现有实现与拟新增内容，不把猜测和拟定 API 写成源码事实。
- **具体调整**：说明哪个对象改成什么，哪些逻辑新增、迁移、合并、保留或删除。小任务可用几句话说明；涉及结构、状态或跨模块契约时，给出职责去向、必要的字段／接口形状、调用顺序及失败处理，不能只写“抽一个服务”“统一处理”。
- **衔接与验证**：指出直接调用方如何改接、旧路径如何退出，以及哪个测试或操作验证哪些结果。工作项应对应上述实际改动，验收应能判断方案是否完成。
- **尚未确定**：对影响方案的未知点写清调查入口、方法、预期产出与下一步判断，不臆造实现。调查型 Task 可以只落实这些调查步骤；文档等非代码任务说明目标位置、内容或规则如何调整，不硬套函数签名。

例如，代码规整任务应写成：“将 Controller 的空实例初始化移入 workspace-session，使用统一默认工厂；打开与关闭调用方改用该入口，删除原初始化方法；验证新实例不继承旧历史且仍共享草稿。”这同时交代位置、调整、接线与可验证结果。

交付前自查：执行者能否据此定位代码并开始第一处修改，而无需重新猜测你所说的“优化”是什么？未满足时继续补依据和设计。删除模板占位符与无关条目，不为凑详细程度预写完整实现、堆砌接口或扩展任务范围。

## 执行与记录

- 按 [[ai/guide/task-read-set-routing]] 选择必要资料；已知领域直接走 [[AGENTS]] 对应入口，不通读无关文档。
- 在 Task 的“当前进展”中只维护已完成事项、正在进行事项和下一步。执行范围、验证和结论按实际需要补充；未运行的检查明确写未运行。
- 只在决定影响后续工作时记录事实与决定。来源冲突或未裁定问题以证据和待决项记录，不把猜测写成事实。
- SubTask 应有独立交付边界。主 Agent 回收实际 SubOutcome，检查相互影响；需要综合判断时再写 FinalOutline，不复制各 SubOutcome。

## 完成与归档

更新 Task 头部状态及当前进展。Task 和 SubTasks 均结束后运行 `npm run task -- archive task-编号`；命令归档 Task 并从活动索引移除。配套资料另用 `npm run archive:docs -- add <路径>`。归档后检查旧引用；操作细节见 [[ai/archive/README]]。
