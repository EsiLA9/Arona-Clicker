# 跨会话原型蓝图工作流

适用于跨模块的调查、设计、负责人评审和后续施工交接。当前 AronaClicker 任务从 [[ai/plan/task-0429-prototype-architecture-blueprints]] 接续，写作和审查使用 [[ai/guide/prompts/prototype-blueprint-review]]。一次只读负责原型、直接依赖、与当前问题有关的现状证据。立项、后续裁定、现实基线和目标设计分别留存。

## 各类文档怎样接续

原型规格讲用户能做什么，施工路线讲先后与依赖，构造页讲共享数据、入口和异常怎样接。实际 Task 在明确授权后以具体代码改接、真实消费者、退出和可执行验收登记。批准前可起草 Task，记录待确认的试验输入和先决条件。一个 R 批次里若有多个独立交付，分别安排。

## 按一个真实的人会怎样操作来写

1. 用普通中文交代应用起点。谁拿着哪一份内容，从哪个按钮、文件、事件或命令开始，屏幕或输出显示什么。需要了解 Init、Area、Entry、草稿等概念时先解释它们之间的区别，用真实包说明。
2. 逐步写出每次动作的结果。用户刚刚修改的具体值往哪里去，哪个文件或领域状态由谁改变，查找位置与引用从哪里得来。再说明取消、坏输入、只读、外部变更、保存失败或读档恢复之后如何继续。
3. 从实际入口倒查代码和测试。查路径、符号、直接调用方、真实数据与当前输出。说明新行为复用哪些能力、需要把哪段现有逻辑接出来，至少指定一个实际消费者和回归入口。工具截图、类名、设计图和测试文件存在本身不能证明行为。
4. 再写建议结构和备选。字段、流程和接口只固定前文解释过的语义。工程名词首次出现时交代它解决的具体问题，如读取后文件被改、同一实体从两处打开、应用了不同版本。用小例子教读者怎样发现问题和恢复，不把名词或类型签名当成答案。
5. 给首个可执行的真实样本。写输入路径、对象 ID、操作顺序、应看到的结果、一个失败对照、如何重复验证。每个交付批次按实际操作命名。如“让作者从地图打开设施并保存条件”，后面说明第一个文件/函数、实际消费者、旧入口去向和何时通过。

## 给新施工者足够的构造说明

- 已有完整的操作流程时，从评审指出的缺口继续。如重复引用的提取者、数据路径、文件顺序、目录权限、构建回读和试播隔离。保留有效正文和旧证据。
- 一个要跨多个入口的数据结构给出一份初始工作合同。注明拥有方、使用方、输入版本、正常和失败输出来由、保留到何时、怎么找到文件。字段改变同步改至少两个真实消费方的验收。
- 用真实函数列出第一处改动、旧行为如何复用和已经有无消费者。再写实际试验的可观察结果、反例、恢复、测试入口、停止旧分支的条件。设计里使用明确候选形状可以减少并行猜测。
- 玩法说明要有体验、在场内可见的下一个行动与回顾，另外留技术验证场景。现有机制缺口有证据时允许设计相应领域重构，把它交给独立负责人裁定。

## 怎样保留调查、技术选项和不确定性

- 确认分支、HEAD、工作树和有关的 GALHCG 项目身份。只重新调查影响当前决定的链路，保留旧证据。读代码、实际执行测试和候选设计分别记录。用“已有”“需要接线”“要实验”“负责人决定”等直接说明。不要用测试条数或审计篇幅代替对一个场景的核实。
- 先让作者或玩家获得一个完整的可观察行为，然后根据需要验证文件锁、事务、长期身份和重试。把未采纳的实现备选放附录。已确认的应用方向不能因篇幅删减，未知地方要写能判断的实验。
- 详细程度由读者能否独立完成任务决定。表格便于对照，连续过程写成步骤或自然段。可拆出专题页，但正文应交代入口和结论去向；避免依靠上一次聊天的省略。正式评审先让一位未参与调查的读者依文档说出首个可执行结果和一个失败恢复步骤。
- 当用户更新范围，写明新决定覆盖哪些旧说法，更新依赖页、评审任务和下一步。重要未决事项至少有事实、可选方案、试验数据和裁定所需结果。正式语言设计、数据迁移等可以独立确认，不为可逆的其它工作增加等待。
- 跨会话前先在 Task 记已完成、当前切片、依据和首个可执行下一步；进展说明给路径和验证结果。规则记录于 guide，当前事实在审计/源码，规格放蓝图。相关入口见 [[ai/guide/task-read-set-routing]] 和 [[ai/guide/conventions/doc-maintenance]]。

本工作流可用于只调查的任务。只有用户确认范围后才从 [Task 工作流](task-workflow.md) 建立实施入口，经确认的实验与正式功能分开。每次评审标注当前代码和数据、允许采用的选择、真实验收与剩余问题。
