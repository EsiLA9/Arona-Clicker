# 原型调查及设计重写提示词

适用：用户给出新的产品方向、评审稿或待重写蓝图，希望不了解背景的施工者能按规定做服务。它依赖 [[ai/guide/prototype-blueprint-workflow]]，当前任务目标和授权以 Task、用户最新裁定和工作树为准。

~~~text
写给第一次进入项目的作者工具开发者、玩法开发者或 Agent。
你的结果将用于独立施工和验收。读者可能不知道这个游戏如何进入世界线、
不知道哪些文件是作者源，也不知道哪些选择仍然待评审。把这三点在需要时讲清。

先做三件事：
1. 核对当前项目根、分支、HEAD 和工作树。读取用户指定参考稿和实际负责的旧设计。
   重要现状从现有源码、直接调用、实物文件和测试核实，记录符号、输入、结果与限制。
   保留原审计、已发现的数据差异和有价值的技术备选。报告实际执行了什么。
2. 写出完整使用过程：谁打开哪一份包、文件、地方或任务，他首先看到什么，
   点击或输入了什么，每一步能否继续，修改写到哪个具体对象或文件，
   保存、检查、构建、试播和应用分别改变什么。坏输入、取消、外部变化、
   运行拒绝和恢复之后，说明用户下一步去哪里。
3. 才给设计接口、实现接线和交付顺序。每项共用能力都找一个现有输入、
   现有函数和真实消费者，写出怎样改接、保留或退出。
   对照相同操作的旧版、新版，说明通过的可见结果。候选类型可以辅助，
   先讲清它为什么存在、何时要用和出现冲突怎么办。

主体文档按真实场景搭建。可实作的段落包括最小输入、对象和字段、实际入口、
产物、失败后的可恢复信息、第一步要核实的函数、验证原有能力的测试。
不要顺序抄写工作项列表。复杂行为可拆附页，用正文把新人带到正确小节。
术语只在必要时出现，并把它翻译成会观察到的过程。不得压缩真实行为、
数据例子、失败分支、备选用途和适用范围。不要把页数或字数当验收条件。

用以下方式区分要求：
- 已核实的事实附来源和测试入口。看了测试、运行了测试、未来应该测试分别说清。
- 已确认的应用行为写成能够执行的步骤。它们不能被临时实验范围取代。
- 推荐试验用可逆输入和真实消费者。不确定细节给两个可分辨方案、观察结果和决定条件。
- 长期产品决策留给负责人。只有被明确确认的范围才能转成施工任务。

已有完整应用规格而评审指出构造缺口时，补实际数据结构、调用步骤、迁移对象和反例。
说明原型规格、建设路线、子系统构造与施工 Task 各自入口。一个大批次拆成多个可验收的结果。
当前范围仅设计时，可以写待评审任务草案；实施前另核实授权。并行的作者工具应共用项目读取、
实体和字段来源、诊断、引用、编辑返回、构建与试播合同，写清拥有者及何时重新取得。

对 AronaClicker 的本轮约束：
P0 从实际检查、保存、构建、试播和应用出发，逐条复用并迁移现有规则。
P1 完整说明全拆、选中合一、发行 ZIP、快速层级化和真实文件回写。
P2 说明全量实体的查找、正反向引用、条件详细弹窗、真实共用路径和专用 Story/地图。
P3 设计可替换的文本接入、共同模型、输入框片段、源位置、左文右读、
   作者阅读／玩家试播／高级判定以及 CLI。用两个极小的替身验证更换语言，
   两个试验接入要读真实输入，改字改变语义，坏文本诊断指出准确范围，并经实际编辑、检查、
   构建和 Runtime。语法随后独立设计。作者阅读、玩家试播和高级判定各有输入和输出。
P4 先写玩家的发现、获取、使用、触发、回顾，再用实际已有实体尝试。
   保留机制验证，另设计可持续的活动、回顾及获得能力后的实际使用。缺口有证据时可以提议
   重构或增设机制，写清状态和兼容。先用当前 JSON。
P5 分开原内容校对和玩家入口设计。资料、版本或范围未明时用获准小样本。
P6 给新人一次从查事实、编辑、查错、修正到构建试播的完整练习，
   说明真能运行的命令和纯候选命令；直接文本保存不需繁琐审批。

收尾时抽查：没看旧讨论的人能不能从一页开始动手说明第一个真实改变，
能不能判断源保存与构建的区别、追到实际字段、处理一个失败。
更新 Task 当前进展、决定和验证结果。只做授权范围内的文档、核对或施工。
~~~
