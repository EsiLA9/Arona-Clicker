## 先把关系分开

| 关系 | 例子 | 是否需要保留父游标 |
| --- | --- | --- |
| 投递 / 解锁 | 路过 Area 获得活动故事入口 | 否；只是可开始内容 |
| 独立根故事启动 | 玩家点击 Area 的主线入口 | 否；创建 / 恢复目标空间自有游标 |
| 同 run 内容转移 | 一段主线 goto 下一文档，或 insert 一段回忆后返回 | 使用现有文档位置 / 栈；不创建子 Entry |
| 场景切换 | 同一故事去天台或借用另一角色空间演出 | 保留当前运行身份；不因此新增调用边 |
| 完成后接续 | A 已完成，进入某 Area 投递 B；好感上一段完成后推下一段 | 否；A 已结束，B 是新根故事 |
| 需要返回的子调用 | A 停在 kizunaCard，B 完成并把局部结果传回 A | 是；唯一需要本阶段父子关系的核心情形 |
| 长期任务关联 | A 邀请玩家去远处做 B，再回来告诉结果 | 可拆成独立 Entry 与持久事实；坚持续接同一次 A 时才需要带调用身份的远程邀请 |

启动来源（Area / Chara / Trigger / 系统）与运行角色（根故事 / 关联子故事 / 回放）正交；Active / Passive 是现有投放语义，不能直接等同于主 / 子。主线 / 活动 / 好感是内容目录，也不应承担调度权限。

## 严格子调用规则建议

1. **正式返回边只允许根游标 → 一个子运行。** 子运行最多一个父亲，没有自己的子调用能力；每个父运行首版最多一次成功调用。重试未成功的同一邀请不算增加一层。多个空间可以各自持有未启动卡片或待返回结果，但正式活跃子运行全局最多一个。
2. **角色由实际启动上下文确定，不由画面、owner 或 active/passive 推测。** 子故事跑到另一 Area / Chara、进入另一个 StoryDef 或切成新 request，都保留“子运行”身份；换场景、换 ID、跨事件不恢复调用权限。
3. **目标引用必须绑定。** kizunaCard 使用所属 Entry 的明确 kizuna 关联；一次运行只能回给创建它的具体父游标。首版关联羁绊 Entry 的正式启动只走该入口，不接受普通 Area / system 请求绕开父绑定；单独阅读走隔离的重读。复用正文可建立不同 Entry，不把一个子运行同时挂给两个父亲。
4. **静态检查覆盖内容闭包。** 从子 Entry 根 StoryDef 沿所有 goto / insert 检查可达文档，含 Click 结果、Operation 和入口卡；禁止其中的 kizunaCard、自调用、间接循环调用及已知会启动另一个 Entry 的行为。不能只扫根文档，也不能依赖某分支“通常不会选到”。共享文档只要用于子上下文，就必须满足子上下文约束。
5. **动态准入覆盖全部启动入口。** 普通 startStory、startCardStory、requestEntry、Trigger / Effect、FollowUp 的直接启动、同步监听和延后请求必须在真正安装 run 前统一复核。来自子运行的启动请求不能换成 system、换 owner 或排到下一轮就绕过约束。一次性请求的来源需随延后记录保存；不要求把将来所有世界事件永久归因给这次故事。
6. **子故事可以改变世界、解锁和投递，不能在尚未返回时再串起新播放。** 其奖励、旅行或完成事件可能让 C 就绪，这是正常玩法；允许创建 C 的入口。若监听器请求直接开 C，应拒绝此次抢播或改成已有可持久投递；没有投递机制时明确返回未启动，不能声称已排队成功。B 的回传与子槽释放先完成，独立 C 的播放另走准入。
7. **完成与返回独立。** 只有本次关联子运行正常结算并结束 finishing，才生成这次返回；旧完成日志、重读、同 StoryDef 的其他 Entry 完成都不能代替。全局完成广播仍可服务世界响应，但不是任意父游标的回调地址。
8. **阻塞是父游标的续播与替换锁。** A 在邀请、子运行、待返回期间仍占有自己的逻辑记录；新 Passive、好感段或强制入口不能把它当成空槽。玩家可离开和浏览；真实移动权限还要看当前前台故事规则，不能由 A 的旧 Active/Passive 标签一概锁住世界。
9. **返回不抢前台。** B 完成只留下 A 的结果和待续播标记；回到正确 Init / 空间并显式激活后才越过原卡片。若另一故事正占前台，先保留待续播，不能因刷新 A 就把另一故事挤走。
10. **取消不是正常返回，也不是回滚。** 子取消可让父邀请可重试；父取消使旧返回失效。已结算奖励、旅行和其他世界写入不因重试撤销。已结算但 finishing 失败的子不能被当作全新未结算运行盲目重开；需保留结果 / 回执并单独恢复或让玩家明确结束。
11. **存档保存关系，而不保存一个可任意扩展的调用栈。** 只需父记录、可选单一子记录、绑定身份和一次性结果；必须验证不存在孤儿、双父、跨 Init 错配或恢复后第二个正式子。定义失配时也要成对处理关系，不能机械重启一端。
12. **回放是独立播放上下文。** 深度仍为一，子返回只能影响此次临时父记录；不能通过正式命令写回正在等待的真实角色故事。

这些是边界要求，不要求现在新增通用权限框架、事件调度器或全局队列。已知非法作者结构在 Registry 拒绝；动态冲突在现有服务准入处拒绝并保持原状态。

“禁止嵌套”与“首版每父运行最多一次成功调用”也需区分：A 调 B 返回后再调 C 并不增加深度，但超出当前单一羁绊的作者需求，首版不开放；不能把它与 A 调 B、B 再调 C 混为同一种非法拓扑。执行身份由 Runtime 赋予，不允许数据包用 localFlag 或 isChild=false 一类字段自行升权。

## 100 个玩法与拓扑样本

下面按建议语义推演。“独立”表示没有返回边；“子调用”表示需要明确父绑定。表中 Busy、就绪、投递和恢复是产品行为建议，不是对现有 API 返回值的命名承诺。

### A. Area 主动故事：入口与运行（01–10）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 01 | 进入 Area，首次发现主线入口，稍后再读 | 只保存投递，不预创建游标或阻塞空间 |
| 02 | 同一 Area 同时获得主线与两个活动入口 | 三条投递可共存；玩家开始一条才创建一个根运行 |
| 03 | 获得入口后离开，再回来点击 | 投递保留；启动时重查位置、Init 和条件 |
| 04 | 重复进出 Area 或重复发现同一入口 | 去重投递；不能增加运行数或重复发奖 |
| 05 | 玩家从故事目录手动唤起主线 | 根启动；不能因为按钮在 Chara 页面就视为角色子调用 |
| 06 | Area 入口指定一个角色 owner | owner 决定归属路径，来源仍是 Area 邀请；是否能占角色槽需准入 |
| 07 | 主线读一半离开页面，再点同一入口 | 恢复同一次运行，不能 start 新 run 覆盖旧 token / flags |
| 08 | 入口投递后条件失效或活动结束 | 保留 / 隐藏策略可另定，但点击不得强开；失败不消费入口 |
| 09 | 同一目标同时由可用性发现和 FollowUp 投递 | 普通根入口可以按 Entry 合并；带父返回的邀请不能仅按 Entry 合并 |
| 10 | 主动故事 B 已经完成，旧入口还在界面上 | 正式启动复核完成；允许重读时进入临时回放，不制造新正式返回 |

### B. Passive 的场景抽取（11–20）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 11 | Area 空闲时随机抽一段天气闲聊 | 选中后在 Init 自有槽创建根运行，不是子故事 |
| 12 | 角色空间随机抽一段日常聊天 | 在对应 Chara 槽创建根运行，记录该空间聊天历史 |
| 13 | Area 抽到的正文说话人是某角色 | 说话人不是 owner；不因此新建该角色游标 |
| 14 | Chara 闲聊中玩家选择另一个角色页面 | 原进度 / 有限表现保留；不把全文搬到新角色历史 |
| 15 | 普通可打断闲聊中手动开始主线 | 走明确取消 / 替换根运行规则，不补造返回父关系 |
| 16 | 不可打断 Passive 中收到主动故事入口 | 可以投递，暂不播放；不能把收到入口当作强制抢占 |
| 17 | 一直点“继续聊天”，同时触发多次抽选 | 当前槽未空不能重复抽到多个运行；拒绝重复输入 |
| 18 | Passive 节点强制移动到另一 Area | 仍是同一运行的旅行；到达事件可以投递，不递归开新故事 |
| 19 | 池中无候选、全冷却或角色被 block | 返回无故事，不创建空游标或等待对象 |
| 20 | 羁绊卡片正在等待，玩家再次点闲聊 | 父记录仍占位；不能绕过卡片抽一条新 Passive 覆盖 |

### C. 好感就绪与连续对话（21–30）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 21 | 在地图上送礼涨好感，聊天空间未打开 | 标记 / 派生就绪，不必立即创建角色对话 run |
| 22 | 一次好感跨越三档 | 三段先后就绪；进入空间逐段开始，不创建三层父子 |
| 23 | 打开角色空间，已有半途好感对话 | 优先恢复原 run，不推新的就绪段 |
| 24 | 好感对话没有羁绊邀请 | 普通根故事顺序完成，无需子槽 |
| 25 | 好感对话出现 kizunaCard，玩家暂时离开 | 原游标停在卡片；只锁其续播 / 替换，不常驻占子槽 |
| 26 | 子故事奖励又令同角色好感跨级 | 新段变就绪，先保留当前父对话；不在回调前插队 |
| 27 | 两个角色同时达到好感门槛 | 各自就绪，各自独立根记录；不是两个并行子运行 |
| 28 | 两个角色都停在羁绊卡片 | 两个等待邀请可共存；先点的一张占子槽，另一张保留 |
| 29 | 父对话后半程完成后触发下一好感尾巴 | A 真正完成后再启动下一根 Entry；不是 A 再次调用子故事 |
| 30 | studentBlocks 阻断解除时父对话仍在卡片 | 解除角色投放门槛不等于解除卡片等待；两种阻塞不能共用一个布尔值 |

### D. 典型羁绊调用（31–40）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 31 | A 卡片 → B 正常结束 → 回到 A | 一层子调用；从原卡片后继继续，A 仍是同一个 StoryDef/run |
| 32 | B 的 Choice 写返回分支键 | 仅复制声明键；A 用 requiresFlag 判断后文 |
| 33 | B 不写任何返回键 | 正常返回照样解除等待；不能把“无 flags”当作未完成 |
| 34 | B 起始场景恰好是父 Chara 空间 | B 仍在独立子槽，不覆盖父槽，也不污染父聊天风格 |
| 35 | B 中多次 Area ↔ Chara 切换 | 只改演出场景 / 显式旅行，父绑定和子身份保持 |
| 36 | 子故事仍在 typing，玩家切回父空间 | 父显示等待，不越过卡片；切页不能伪造 B 完成 |
| 37 | B 完成时玩家正在另一角色页面 | 保存返回结果，释放子槽，不自动跳页或后台播完 A |
| 38 | B 完成时已经显示 A 的空间 | 由明确的返回激活处理；查询 A 不自行恢复逻辑 |
| 39 | B 取消后重试 | 不传成功结果；保留同一父邀请，创建新的关联尝试；旧尝试返回失效 |
| 40 | B 已结算但尾通知失败 | 保留结算和结果回执，不直接当取消后免费重开；先解决 finishing 的失败恢复 |

### E. 前往其他地点做故事（41–50）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 41 | A 说“去天台找我”，旧结构让 A 完成，到天台投递 B | 当前是 FollowUp；若只是同一故事后文，优先合并为原游标地点续播，不能把旧分割当作产品要求 |
| 42 | A 停在卡片，B 本身演出从天台开始 | 点击后子运行直接切到 / 前往其起始场景；无需长期事件等待 |
| 43 | A 停在卡片，玩家必须自己走到天台才能开 B | 若 B 必须独立 Entry，则是带父绑定的远程邀请；若 B 只是后文，则原游标地点续播，不创建子运行 |
| 44 | 同一远程邀请 B 在多个地点都能接受 | 多个入口必须引用同一调用尝试；接纳一次后其他入口失效，不能各启动一次 |
| 45 | 玩家已在目的地时才收到邀请 | 必须明确“当前位置即满足”还是“下一次进入”；现有 next-enter-area 不能自动当作当前位置匹配 |
| 46 | A 让玩家打一场战斗，回来交任务 | 默认独立任务 / 完成事实 + 后续 Entry；不让通用游标长期等待任意战斗事件 |
| 47 | A 要求完成 B 和 C 两条独立主动故事后回来 | 多条件任务汇合，不是单一子调用；用明确持久条件组织，首版不开放子 join |
| 48 | B 的场景在别的 Init | 不把跨 Init 当普通旅行；需明确跨世界任务结构，首版子调用不支持跨 Init 运行 |
| 49 | 玩家做远行任务途中顺便阅读活动 C | 若 A 已完成，普通独立根播放即可；若 A 仍等关联 B，则不能让 C 意外成为返回目标 |
| 50 | 父空间长期不再可访问 | 可达性是内容校验 / 产品恢复问题；不能让 B 随便把返回位置改成当前屏幕，需明确取消或修复入口 |

### F. 系统事件与直接开故事（51–60）

| 编号 | 玩法 / 流程 | 游标处理建议 |
| --- | --- | --- |
| 51 | Init 首次进入自动开始开场故事 | 系统启动一个根运行；不虚构父游标 |
| 52 | 某个设施升级后直接开始系统剧情 | 根启动请求，走正常空间占用准入；没有空槽不应无声覆盖父卡片 |
| 53 | 设施升级解锁一个主动故事入口 | 仅投递；可与正在播放的故事共存，无调用深度 |
| 54 | 普通根故事的 Effect 要求启动另一 Entry | 必须明确为既有替换 / 完成后接续，不能偷偷保留父亲成为通用子调用 |
| 55 | 非好感主线突然需要“看一个片段再接着讲” | 若无独立 Entry 奖励 / 投放需求，用 insert StoryDef；不新增子 Entry 类型 |
| 56 | 非好感活动确需独立 Entry 完成后返回 | 实际需求会要求第二种受限作者包装；先列待扩展，不把普通 entryRequest 全面升级 |
| 57 | 场景系统要求“直接开始子故事”，但没有父运行 | 语义不完整：应作为独立根故事，或先建立明确父邀请；禁止孤儿子运行 |

## 推演得到的结构结论

### 最小仍是自有记录 + 一个子槽，不是通用等待图

许多“等待”其实是待领取入口、好感就绪、冷却或任务条件；不应都变成等待游标。多个父空间都可以显示卡片，但只有被正式接纳的 B 占子槽；B 返回结果交给 A 后就释放子槽，不必等玩家真的读完 A 后文才释放。

来源空间记录需与场景投影分开；首次落地的来源主要是 Chara，但 Init 来源也应能表达。Init 的各 Area 通常共用 Init 自有故事槽，不因为每走到一个 Area 就创建一个根槽。是否为 Area 单独增加长期游标，现有样本没有证明必要。

角色有三类相互独立的“忙”：原空间已有故事、全局子槽占用、前台正在播放别的故事。不能合成一个 isPlaying：否则会出现等待父锁住旅行、子一结束父就抢画面，或父退出前子槽一直不释放等问题。这里需要明确准入判断，不等于需要第三个核心游标。

### 长期远行应先判断是否真的需要保留原 run

“先聊完邀约 → 去天台继续 → 回来聊后文”不能因旧实现用了多个 Entry 就认定它们应独立。后续调查建议：同一叙事优先原游标地点续播；确有独立结算、解锁、目录或任务生命周期时才保留多 Entry。只有要求在另一个独立 Entry 运行后恢复原卡片，并使用本次 B 的局部结果时，才需要真实返回边。

如未来确认“卡片出现 → 自己走到目的地领 B → 回来续接同一次 A”，最小扩展是把父绑定附着于远程邀请，接受邀请时才创建子运行；不是新增 WaitForAnyEvent。需要单独决定邀请的可接受地点、到达即接受还是手动点击、过期与取消。普通 AreaStoryDelivery 当前按 Entry 去重，不能直接假装已具备这份调用身份。

### 内容组织约束不能禁止正常世界后续

此前 Task 建议整体排斥关联 Entry 的 reactions / followUps，过于宽泛。B 完成后投递活动 C、A 完成后挂载后续监听都可成立；应禁止的是重复实现同一次返回、以及子运行未释放时递归抢播。投递或将来独立触发不等于嵌套。不能为防调用风暴而禁止剧情改变世界。

反过来，只在作者类型上写“子故事无 kizuna 字段”又不够：StoryDef 转移、普通请求、事件监听和延后启动必须遵守同一运行约束。首版不开放子故事主动发起任何 Entry 播放；允许其结果投递未来根入口。

### 准入必须能区分结果

发起请求后，至少要让调用方区分：已开始 / 恢复已有运行、仅投递、因占用未开始、内容或资格拒绝。若使用延后请求，必须已有可追踪身份与持久记录，不能对父卡片谎报成功。准入失败不消费卡片，不发完成，不提前支付或重新结算。现有 StartDeferred 与真正已安装运行的区别需要实施时对齐。

## 需要继续裁定的少量问题

1. 真实子故事占用前台时，其他根故事的手动开始首版是否统一提示稍后？建议先禁止新增前台抢播，仍可浏览空间和投递入口；已开始的后台有限表现保持既有语义，不为此引入整套暂停调度。
2. 同一羁绊目标是否仅允许关联卡正式启动？建议首版如此；直接独立正式阅读同一正文用另一 Entry，单独重读使用既有隔离入口。
3. 天台样例应先判断是否能归并为一个故事的地点续播。只有确需独立子 Entry 及返回的远行才考虑远程调用作者字段，不能因为已有 FollowUp 而维持被迫分割。
4. 正常返回恢复 A，与取消 B 后恢复卡片可重试，是两条显式不同路径；已结算但 finishing 失败还需单独恢复，不能归为“未完成就重开”。
5. 好感组合跨 Init 如何保存 Chara 来源、重置与失配如何一起处理？沿现有 Init 快照核实，不扩展跨 Init 子调用。
6. 父后文默认只在返回来源空间后播放；“点击返回”交还前台与真实世界返程应分开，不能因为场景 owner 相同就认为玩家已经回来。

## 继续调查：替代 FollowUp、尾段推送与被迫分割

### 核实的实际用法

对 src/arona-clicker/content/ 的声明搜索显示：基础内容中只有一个 followUp 调用，即 story-conversation-walls.ts 的星野天台邀约；只有一个 pushAfterStory 尾段声明，即 character/affection-content.ts 的 affinity_hoshino_bond_tail。reactions 在本次基础内容搜索中没有实际挂载声明，相关合同与工厂有测试覆盖；这不代表外部数据包没有使用。

天台链目前包含三份机制状态：前段完成日志、FollowUp 的 fulfilled 标记、Area 待领取入口，另有 studentBlocks 的条件阻断。FollowUp 的 fulfilled 对 Active 目标表示“已投递”，不表示后续故事已完成。当前测试明确要求到达只投递、玩家手动接取再播放；还覆盖多 Active 同时投递和 Passive 直接启动，不能把所有用途无差别改成自动续播。

尾段扫描依据已完成的 StoryDef ID，且拥有优先于普通好感台阶的推送规则，不携带上一运行的局部表。基础尾段挂到 bond_hoshino_1，而已有邀请卡指向 bond_hoshino_evening：它们不是已经核实的一条完整“前段—子故事—尾段”链。需先明确应该归入哪个父好感 Entry，不能直接按角色名合并。

### 建议新增的有限能力：地点续播

仅有 kizunaCard 还不能完整取代“玩家自行前往某处后继续”的 FollowUp。最小补充是当前游标的一种明确地点等待交互，暂称 areaContinue，不新增通用等待对象或事件表达式：

```text
同一个 StoryEntry / StoryDef：
  星野聊天：“天台见。”
  → 地点续播卡：areaId = 夏莱天台
       原游标保留；玩家自由行走，不占子槽
       到达后在天台显示“继续本故事”，手动接受
  → 天台相遇正文（采用地点演出场景）
  → 后续节点 / 明确回到 Chara 场景
  → 整个故事真正完成
```

卡片可作为 Click 的一个受限 interaction 分支，沿用 token、稳定 nodeId、节点后继和快照；具体字段尚未决定。来源 Chara 仍是该运行的归属，目标 Area 只是该等待点的继续条件与接纳场景。现场演出不因归属 Chara 就自动成为普通聊天记录。

到达事件只让当前等待点可接受，不自动执行后文。接受命令复核当前 Init / Area / 等待点 / token；已在目标 Area 时可立即接受，重复进入或重复点击不重复执行。入口从游标派生，不额外创建一个目标 Entry，不再维护 FollowUp fulfilled 与第二个 Entry 的投递完成状态。普通主动故事入口仍有自己的 AreaStoryDelivery，二者可复用卡片显示但不能混用业务身份。

地点等待只是同 run 的线性进度；它与 kizunaCard 一层调用独立。一个完整故事可以先后到多个地方，也可以在某处给出唯一羁绊卡，但并不因此多出 Entry 调用层。首版建议手动地点等待只用于根运行，避免子运行长期等待旅行而占住唯一子槽；子运行中立即执行的显式旅行仍可保留。

### 可以消除哪些旧结构

| 原结构或动机 | 新结构 | 可删除的叙事胶水 / 保留的语义 |
| --- | --- | --- |
| 羁绊完成后为了几句后文单独造 tail Entry | 父 kizunaCard 后的节点 | 可移除该用途的 pushAfterStory、尾段独立完成与扫描；恢复父后文优先于新好感推送 |
| 同一故事等待到达，把前段提前结束后用 FollowUp 起后段 | 当前游标的地点续播卡 | 可移除该用途的 followUps、前段假完成、目标专用 Entry 与投递标记 |
| 为移动场景切成多个 Entry | 同 run 显式移动 / 场景切换 | 场景切换不再承担运行交接；正文仍可分文档复用 |
| 为让角色“等你回来”而先完成，再写 block | 活跃故事的地点 / 返回等待状态 | 可去掉这一用途的完成后 studentBlocks；真正的持久角色投放门槛不能一起删除 |
| 用 reaction + triggerStory 充当原故事接线 | 线性节点或受限回调 | 不必安装持久监听来接回自己的后文；影响其他世界系统的 reaction 仍有独立用途 |
| 真正完成章节后解锁下章、活动或多个支线 | 独立 Entry 的资格 / 投递 | 仍需要持久完成事实和投递，不应为了统一而永久扣住旧游标 |

即使允许合并，也不要求一个故事只能有一个源码文件；goto / insert 可组织文档，而 Entry 数量取决于真正的投放与结算边界。

### 必须正视的行为差异

1. **不是已有能力直接改名。** areaContinue 是拟议能力；现有普通 requiresFlag / Condition 不会保存等待点并在到达后续播。
2. **不强制旅行。** 用 moveToArea 代替会消除玩家自行前往的玩法；地点续播只检查玩家是否到达。
3. **当前匹配与下一次事件不同。** 新建议采用当前位置匹配，旧 FollowUp 是来源完成后的下一次进入；已经站在天台时是否需要重进必须明确，不能声称完全等价。
4. **播放锁要按等待阶段判断。** 天台来源原有 leaveArea:false / interruptible:false，若仍简单按 Entry 全程禁旅行，新等待点会让玩家永远无法去目标地点。节点等待必须允许旅行，同时保持原游标不被覆盖。
5. **角色门槛持续时间可能改变。** 旧 block 的 Area 条件到达就解除，新原游标可能直到整个故事结束仍占槽；这是不同体验，需要确认，不能把所有 studentBlocks 自动删掉。
6. **持有根槽是成本。** 特别是 Init 根槽长期等地点，会影响其他 Area 主线启动；若内容要求多个独立任务并行、等待时还可在同槽读别的故事，应继续用独立投递 / 任务记录，而不是再加一串等待游标。
7. **完成与奖励边界要一起合并。** 原前段的首次 / 重复奖励、冷却、统计与后续激活会延后；真正需要中途独立结算的段落仍可保留 Entry。迁移不能重复领奖或无意删掉原来的结算。
8. **StoryDef 终点不等于组合根身份。** 当前完成记录会使用 terminalStoryId；合并或复用旧后文时需审查根身份和 hasReadStory 前置，不能因一个 goto 仍把完成记成旧后段，或让外部前置永远不能满足。
9. **回放也要可读。** 组合重读的地点续播应只切换虚拟演出场景并继续，不要求玩家真实旅行或改正式 Area；局部 flags 沿当前回放保留。其隔离仍是待实现项。

### FollowUp 字段是否整体退场

建议目标是消除“为了等地点或回几句话而被迫分割 Entry”，不预设保留旧 followUps 的作者写法。当前基础天台内容是值得优先改写的样本，相关 mount 可在所有真实用途迁出后评估删除。

但独立未来入口投递、完成后对世界的持续影响不会因为有游标就消失。若最终移除 followUps 字段，这些用途仍须由明确的资格 / 投递机制承接。现有 StoryAvailabilityDeliveryMount 只服务指定 entryIds 列表，语义是可用后首次所在 Area 投递；仅给目标 Entry 加 hasReadStory 条件，不能自动等价替代任意目标 Area、严格 next-enter、一次性 fulfilled、多目标扇出或 Passive 直接启动。不能只删除旧字段再宣称完整替代。

推荐顺序：先合并确认属于同一故事的尾段与天台链，确定地点续播及一层返回；再盘点剩余独立投递 / 世界响应用途，决定统一的作者入口及旧字段退场。这里没有授权实施迁移，也不为了删字段提前建设通用工作流系统。
