# Task 0438 · 按来源保存 Datapack 原文件

状态：待处理

对应 [M01 原地保存与失败边界](../../docs/prototype-blueprints/AC-module-blueprints-v3/01-project-source.md) 和 D2。属后续作者工具建设。依赖首批 [[ai/plan/task-0437-datapack-layout-tools]] 及 M04 的 D1 草稿核心。已有 M02 来源定位与 M03 诊断可接入，完整检查和生产构建不作为单文件保存的门槛。

## 当前依据与施工

- `PackSource` 负责列举与读字节，`tools/datapack-editor/ui/io.ts` 用下载导出，`DatapackFileImport` 无写宿主。基于 Task 0435 的源路径、Pointer、原文件做文件级补丁。M04 把同一文件的草稿改动聚齐交给 M01，优先接一个真实 Spot 名称和同文件另一实体字段，保留其余定义、未知字段和资源。对源 JSON 无法可靠定位的结构化改动返回冲突并留草稿。
- 增加可写目录宿主及保存计划。先验真实路径、文件摘要和新文件不存在，再写回并重读。前置试验选择一个可实际写回的桌面宿主，必要时使用 Node 终端适配。ZIP 和只读依赖走副本导出。摘要用于源文件冲突，以实际写入消费者为限。
- 先交付单文件阶段。只有唯一来源可建议重定位，歧义时由作者选择。同一文件的改动一次提交和重读。提交遇到外部修改或失败时保留该文件草稿与原底稿。

## 第二验收点 · 跨文件移动

同一个实体从源文件移到目标文件是一次逻辑操作。以 Story A 从 `story1.json` 移到 `story2.json` 为例。

1. 同一计划生成两份修改后的完整文件。提交前验证两边的路径、摘要和声明唯一性，保留原字节和预期写入摘要，并把两份新文件先暂存到扫描范围之外。新目标原先不存在时也要记录。暂存和备份未完成时不替换任一文件。
2. 先替换目标，再替换源，避免源已删除而目标尚未可读。替换期间当前作者会话不发布该次移动的中间状态。两份都成功后重读，确认同一实体只出现一次且位于目标，才报告保存成功并更新 M04 底稿。
3. 目标成功而源替换失败时，将目标恢复到原字节，或删除本次新建的目标。恢复前核对目标仍是此次写入的版本，避免覆盖外部改动。回退成功后重读，报告移动失败、保持原先位置和草稿。若无法安全回退，返回 `partial`、具体文件状态、备份位置及可执行的恢复步骤。保留本次恢复记录，重新打开时仍可识别未完成移动。对应项目的发行与继续写入受影响文件等待恢复核对，草稿保持可查看。

M04 对互不关联的成功写入可分别推进底稿。跨文件移动涉及的两份文件按同一结果处理。首轮按这一种补偿流程验收，后续按实际需求评估通用事务。

## 可用交付与验收

从实际可写目录打开同文件两实体，修改、保存、重开，两处值都更新。覆盖外部修改、源移动、只读 ZIP 和可保存但暂有缺引用的定义。跨文件测试分别注入预检失败、目标成功但源失败和回退时目标已有外部修改。验证自动恢复后 A 仍只在原处，无法安全恢复时可找到原件和恢复位置，移动不会报成功或推进底稿。补一次重开后恢复验证。
