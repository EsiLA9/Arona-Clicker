# Task 0349：好感—羁绊的一层回调与播放边界

状态：阶段讨论已整合至 [[ai/plan/task-0350-story-continuation-and-cursor-design]]，未施工。创建于 2026-11-03；本页保留讨论记录，后续统一在 0350 推进，不表示运行机制已实现。

## 本轮判断与范围

游标是 StoryEntry–StoryDef 的运行状态记录。多游标服务于“好感前半段 → 羁绊故事 → 返回聊天后的简单后半段”，不以构建通用协程或回调框架为目标。

| 需求 | 对前案的判断 | 本轮收敛建议 |
| --- | --- | --- |
| Entry 完成后回传信息 | 前案支持，但任意 Entry 相互回调容易形成调用网 | 只开放好感 Entry 关联一个羁绊 Entry，固定一层返回 |
| 保留原对话并播放子故事 | 需要保留两个运行记录，但不需要独立等待系统 | Init / Chara 自有游标，加正式播放时单一的子故事槽；等待只是父游标状态 |
| 玩家与回放理解故事内容 | 前案偏重运行结构，不能直接成为产品目录 | 沿用主线、活动、好感及其关联羁绊的内容组织；游标与回调只在内部处理 |

保留会话空间、游标和屏幕渲染的职责区分。先前关于任意 event 唤醒、独立等待游标、任意深度调用和整表 flags 合并的讨论不作为本阶段默认方案。

## 本轮拓扑推演摘要

已补充 [[ai/plan/report-0349-story-cursor-topologies]]，列出当前事实、统一准入建议与 100 个玩法样本，覆盖 Area 投递 / 手动启动、Passive 抽取、好感就绪、羁绊回调、远行接续、系统事件、竞争拓扑、Init / 存档及回放。样本用于判断边界，不是全部实施清单。

- 必须区分投递、独立根启动、同 run 的 goto / insert、换场景、完成后接续和真正的子调用。Active / Passive、Area / Chara 来源、主线 / 活动目录都不能独自决定根 / 子身份。
- 多个空间可各自停在卡片，但只有真正启动的子故事占唯一子槽；子返回结果保存到父记录后就释放子槽，不必等玩家读完父后文。前台播放权与槽的归属还需分开判断，不新增第三个核心游标。
- 严格禁止嵌套要同时覆盖子 StoryDef 的 goto / insert 可达文档、普通入口请求、Effect / Trigger、旅行与完成事件、延后请求；启动来源由 Runtime 保留，不能换 owner / system 身份绕过。不能只检查有没有第二张 kizunaCard。
- 子故事可解锁、投递未来故事；未释放时不得递归抢播。全局 storyCompleted 的 storyId 广播不足以证明本次子调用完成，回传必须匹配具体运行与父绑定。
- 不能因为旧实现把 A 结束后交给 FollowUp 开 B，就认定作者需要两个独立故事。同一故事的远行接续优先保留原游标，用受限地点续播点表达；只有确有独立完成 / 奖励 / 投递边界时才保留独立 Entry。独立子 Entry 的远程邀请则是另一种扩展，不与同游标地点续播混淆。
- 阶段建议：其他正式子故事占用前台时，新故事只允许投递 / 保持就绪，手动抢播返回忙；浏览空间和世界 Tick 不因此一并停止。具体前台体验仍待裁定。

## 替代 FollowUp 等被迫分割的结构

本轮继续调查后，修正“完成后接续应默认维持旧 FollowUp”的倾向：是否是一段完整故事由作者的叙事与结算边界决定，不能反过来由现有分割式实现决定。详细事实、差异和替代条件已补入拓扑报告末节。

| 旧用途 | 建议表达 | 是否消除拆分 |
| --- | --- | --- |
| 羁绊完成后 pushAfterStory 推一段尾巴 | 同一父 StoryDef 的 kizunaCard 后继续，flags 来自这次子调用 | 是；不再需要专门的尾段 Entry 和历史完成扫描 |
| 同一邀约先结束，FollowUp 等进入 Area 再开后文 | 原 StoryDef 中设置地点续播点，玩家到达后手动接着播 | 是；只是当前游标的一个等待点，不创建子 Entry |
| 故事要求立刻去另一地点继续 | 现有显式移动节点，加当前运行继续 | 是；但不能用于替代玩家自行前往的玩法 |
| 同一故事分文档复用或插入回忆 | goto / insert 等现有文档组织；不额外造 Entry | 可消除运行与结算拆分，不要求把所有正文拼成一个文件 |
| 故事真正结束后解锁其他主线 / 活动或多个入口 | 独立入口资格、投递与必要的事件记录 | 不应强行合并；投递能力仍有独立职责 |
| 完成后长期影响世界的 reactions、持续解锁或任务门槛 | 既有领域 / 条件 / 事件能力 | 不由临时游标取代 |

**地点续播点提案**：作者在同一 nodes 中放一个面向产品的“到指定 Area 继续”交互（暂称 Click 的 areaContinue，字段名未定），仅填写 areaId；不开放通用 event、任意回调或返回地址。到达前保持当前等待点并允许正常旅行；到达后显示“继续本故事”，手动接纳后才推进后继。当前位置已经符合时即可接受，不要求离开再进；这与旧 next-enter-area 的严格下一次事件并非完全同义，迁移需明确。

该续播入口由游标等待点派生，不另建目标 StoryEntry，也不把它塞进仅按 Entry 去重的普通 AreaStoryDelivery。进入事件只更新可继续状态，不从 UI 查询隐式推进。接纳时再次核对 Init、Area、具体游标与 token；后续画面使用该地点的故事演出场景，不把现场正文自动计入来源 Chara 历史。来源空间与局部 flags 保留。地点续播不占子槽、不增加 Entry 调用深度，多个地点可以在同一故事中依次续播。

这样只需区分三种明确作者意图：**立即移动继续、玩家到地点后继续、进入独立羁绊后返回**。地点续播可以与一层羁绊组合，但它不是第二次子调用。首版建议只允许空间自有根游标进入需要玩家自行旅行的地点等待，避免一个子故事长期占住唯一子槽；是否允许子故事自身等待地点另行裁定。

被合并故事的原完成标记、首次 / 重复奖励、冷却、block、reactions 激活时机和目录条目都要重审，不能只移动正文。等待中的根游标仍占对应空间；若产品要求等待期间该空间继续接其他独立故事，或多个长期任务并行，保留投递 / 任务记录比增加等待游标列表更合适。

当前内容仅发现一个基础包 FollowUp（星野天台）和一个 pushAfterStory 尾段声明。尾段关联 bond_hoshino_1，而现有邀请卡指向 bond_hoshino_evening；迁移前必须明确真实父入口，不能因角色相同就直接拼接。这里只记录替代方向，未修改内容。

## 会话空间、游标与屏幕渲染

- **会话空间**：保存空间历史，主要是 Chara 聊天历史，并提供场景与原有聊天风格。
- **游标**：记录 Entry 播放进度、父子关联、阶段和局部 flags，处理完成回传；不直接代表某块屏幕或历史列表。
- **屏幕渲染**：组合当前场景与剧情呈现，决定最终可见内容；读取与刷新本身不执行节点或回调。

游标归属、场景来源与历史归属分别表达。好感前后段属于原 Chara 聊天；羁绊演出保留自己的输出与临时风格，切换场景不自动变成其他 Chara 的聊天，也不改写其实际聊天风格。羁绊输出仍可随运行快照保存恢复，“不进入角色聊天历史”不等于丢弃演出进度或输出。显式移动节点的真实移动行为与这些呈现 / 历史规则分开。

## 面向数据包作者的末端 Entry 提案

复用现有 Entry 的归属、触发条件与奖励字段；好感 Entry 只增加可选的 **kizuna 关联**，StoryDef 仍是包含前后文的一份有序 nodes。以下是拟议结构示意，不是当前可导入的合同：

```json
{
  "id": "demo:passivestory:affection_02",
  "type": "passive",
  "owner": "Hoshino",
  "repeatable": false,
  "affectionRequired": 2,
  "storyId": "demo:story:affection_02",
  "kizuna": {
    "entryId": "demo:activestory:bond_02",
    "returnFlags": ["Bond-promised"]
  }
}
```

示意省略了 availableInits、triggerCondition、weight 等现有必填字段，不改变它们的合同。

- storyId 包含好感对话的完整节点流。作者在需要邀请的位置放一个 Click，其交互为专用 kizunaCard；卡片出现即阻塞父故事，不自动执行卡片后的节点。
- kizuna.entryId 指向独立 ActiveStoryEntry，拥有自己的 StoryDef、完成和奖励策略。
- kizunaCard 从所属 Entry 的 kizuna 关联取得目标，不在节点中重复写目标 owner、游标 ID 或返回地址。Runtime 保留卡片所在文档和后继位置，成功返回后自然接着执行卡片后的节点。
- returnFlags 是允许回传的局部键名列表；省略表示不回传键，但成功返回仍会续播。不开放任意事件、回调脚本、目标游标 ID、返回地址或可配置调度策略。
- 入口卡复用现有呈现能力，名称优先取关联 Entry / Story 的现有显示信息；本阶段不增加另一套卡片外观配置。

```text
同一个好感 StoryDef：
  前半段 Talklet / Choice
  → Click：interaction.kind = kizunaCard
  → 后续 Talklet（可声明 requiresFlag: Bond-promised）
  → 原 Entry 正常结束
```

用户已否定 afterStoryId 及固定拆分前后 StoryDef 的方案：它增加了作者组织负担。本方案只保存当前卡片等待点，续接位置由 nodes 顺序决定，不引入通用返回地址配置。

### 固定约束

- 首个作者入口为有 owner、非 repeatable 的角色好感 Entry；目标必须是 ActiveStoryEntry。首版一个羁绊 Entry 只归属一个好感关联，父 Entry 只有一张可返回的 kizunaCard，卡片必须有对应关联。关联羁绊 Entry 的正式启动仅走该绑定，其他普通 Area / system 入口不能把它开成无父子故事；单独阅读走隔离回放，复用正文可引用同一 StoryDef 的另一 Entry。是否向 Init 故事开放同类卡片，留待实际内容需求确认。
- 每个关联只有一个子故事，子故事不能再发起本类回调，父运行成功返回后也不能再次进入本类调用；不开放递归、链式回调、并行子故事或等待列表。Registry 核对引用与绑定，Runtime 复核深度和子槽占用，不能只靠编辑器隐藏字段。
- 现有 goto / insert 仍是 StoryDef 内部内容组织手段，不因此获得跨 Entry 的通用返回能力；现有普通 entryRequest 也不自动升级为回调 API。组合各段不得用普通入口请求绕开上述子故事限制。
- 不叠加入口卡目标、pushAfterStory、reactions / followUps 来重复实现同一次返回；但不整体禁止这些正常内容能力。子完成后解锁 / 投递未来根故事、父真正完成后安装后续反应均可成立，须走统一启动准入，不能在子返回前递归抢播。拓扑推演修正了前案对这些字段的一概排斥。

## Runtime 的最小行为

1. 原空间自有游标 A 到达 kizunaCard，卡片出现即成为阻塞点：保留当前 StoryDef、卡片及后继位置、局部 flags 与来源空间，不执行后续节点。此时不记录 A 完成，不结算 A 奖励或推进下一好感段。
2. 玩家可以暂不进入羁绊并离开空间。卡片仍留在 A 的等待点，普通继续不能越过；再次回来仍显示可用入口。
3. 玩家点击且 B 准入成功后，A 从“等待点击卡片”转为“等待子故事结束”，B 使用单一子故事槽。槽已占用或准入失败则保留可点击卡片，不替换其他故事。A 等待期间原空间不能自动投放另一 Entry 覆盖它；其他空间仍可保留自己的记录。
4. B 正常完成并结束 finishing 后，回传结果并将 A 标为“等待回到来源空间”。父子关系绑定跨读档稳定的具体运行身份，不凭 Entry 历史完成状态唤醒；结果在 Player 清空 run 前保留。仅完成 B 不在后台执行 A 的后续节点。
5. 玩家返回来源空间时，通过明确的激活命令消费这次返回，越过原卡片，从它的后继节点继续；已在来源空间时也走明确的返回意图，不靠读取 / DOM 刷新推进。继续沿用 A 原有 flags 与返回键，后文直接用 requiresFlag 判断。
6. A 的同一故事正常结束后才完成 A、结算 A 的奖励和好感后续；B 按自己的 Entry 结算一次。不把卡片前后切成新的 Entry，也不在出现卡片时提前完成 A。

这里“阻塞当前空间”建议准确理解为阻塞该空间自有游标的故事推进与替换，不默认封锁浏览历史、离开空间或整个游戏操作。父游标来源可以表达 Init 空间或某 Chara 空间，并带上所属 Init；首个好感玩法实际阻塞对应 Chara 游标。B 借用其他场景不迁移 A 的来源，也不把当前屏幕所在空间当作返回目标。B 自身的移动 / 交互限制仍按其播放规则处理。

等待只是 A 的有限阶段，不另建“等待游标”实体；旧称“核心游标”在本场景收敛为唯一子故事播放槽，不再增加第三种中央调度游标。其他空间可保留自己的记录，不要求一并停止或共享 flags。

B 取消或未结算失败不回传成功结果，A 可回到邀请阶段重试；A 已取消则丢弃返回，不复活旧对话。取消重试不撤销已提交的世界效果。若 B 已结算但 finishing 失败，需保留回执和最终结果，不能当作未完成后直接新开一遍重复结算。父阶段、子运行、最终结果与回传消费状态共同保存，恢复不重复执行动作、结算或回传；Init 切换沿现有快照边界保存所属关系，不能串到其他 Init。

## flags 的有限回传

- A、B 各持有独立局部表；本需求不自动向 B 传入 A 的整表，也不共享可变 Map。
- 成功返回时只复制 returnFlags 中的键。列表中的键在 A 中先清除，再按 B 的最终表复制存在项，避免“B 本次没有选该分支，A 却保留旧标记”；A 的其他键保持。缺省列表相当于空列表，不另加合并模式或改名配置。
- 这是 Entry 局部 flags，不写 PlayerState.flags，也不是 session.flags 的持久 setFlag 名称记录。requiresFlag 继续只检查键存在，false / 0 / null 仍算存在。
- 不需要作者写“完成 flag”解除等待：成功返回决定续播，回传键决定后半段内容。

例如 B 的某选项写入 Bond-promised，A 的后半段包含 requiresFlag: Bond-promised 的“别忘了答应我的事哦”；未选择时该键不返回，相应 Talklet 跳过。

## 玩家目录与回放

主线、活动等沿现有内容目录组织，不因这次改动增加“主游标故事 / 子游标故事”分类。好感条目展示关联羁绊；卡片前后就是同一故事的节点，不成为额外目录条目。此提案也不把主线、活动变成新的 active / passive 执行类型。

完整回放按“好感前段 → 羁绊 → 好感后段”自然组织，不显示调用栈、等待对象或 flags 表。组合回放在独立临时上下文中处理返回，不占正式子故事槽，也不唤醒正式好感游标、不改变正式完成进度 / 奖励 / Chara 历史。已有单独重读 B 的入口不需要补造 A，更不能向真实 A 发送返回。

实施时须单独核对回放：当前 replay 会跳过整个一般 Operation（含该节点的 localFlag），而 Click 结果动作仍可能有世界副作用，不能把现有 replay 直接当作满足上述隔离的实现。组合回放应保留分支所需的局部 flags 计算，并隔离世界写入；不为普通历史回放顺带扩展另一套作者配置。
