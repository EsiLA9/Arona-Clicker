# Task 0338：缩短游戏启动等待并展示真实进度

状态：实施中 — 启动阶段反馈、详细当前内容与可导出的分段耗时日志已补齐；偶发重启慢的现场数据、性能基线和按数据优化仍待完成。

## 目标与范围

- 用户反馈：启动游戏耗时较长，等待时不知道正在做什么。
- 目标：找出并减少启动关键路径耗时；从打开游戏到 Lobby 可操作，持续提供真实、易懂的阶段反馈，失败时能够判断停在哪一步。
- 范围：游戏入口、模块加载、Runtime 创建、本机包库恢复、开发包发现与读取、启用包应用、Registry 初始化、UI 首次挂载及首个可操作画面。
- 非目标：独立 Datapack Editor、游戏运行中性能、重塑 Lobby、改变存档语义或启用包顺序。不得为了提速跳过必要校验、静默忽略坏包或提前启动 Tick。
- 当前实现先交付启动阶段反馈和诊断能力；达到性能目标仍需完成同配置基线与优化后测量。

## 实施步骤

- [ ] **建立基线。** 记录浏览器、设备、启动命令、构建模式、数据包数量和大小、缓存条件；分别测开发服务器已就绪后的首次访问、刷新，以及生产构建预览。开发服务器启动耗时单独记录。至少覆盖仅 Base、当前开发包集、本机已安装启用包三类配置。
- [ ] **分段观测。** 记录导航到启动壳可见、模块就绪、Runtime 创建、包库恢复、开发包发现 / 读取 / 解析、启用包计划 / 校验 / 应用、Registry 初始化、UI 挂载、Lobby 首帧与可操作时间；记录主要长任务和请求瀑布。开发诊断可查看各阶段耗时，玩家界面保持简洁。注意嵌套计时避免重复累计。
- [ ] **按证据优化。** 先处理实测占比最高的等待。候选包括缩减首屏模块依赖、延后非首屏功能、移除重复工作、受控并发读取和合理切分同步计算。每项保留前后测量；若采用缓存，明确失效条件并覆盖 editing 包变更，不得读旧内容。异步化时检查所有调用方及失败回退边界，不并发修改共享 Registry / Runtime。
- [ ] **展示真实进度。** 沿用现有启动壳和项目视觉规范，显示当前阶段、已等待时间；能获取真实总数时显示包 / 文件完成数。不能计算比例的阶段使用不确定进度，不显示伪造百分比或倒计时。成功完成首帧后再撤去启动壳。慢阶段提示“仍在处理”并展示当前工作，不能仅靠动画掩盖主线程阻塞。
- [ ] **完善失败反馈。** 显示失败阶段和简洁原因，提供刷新重试入口及可展开 / 复制的诊断信息；包库恢复失败后继续使用当前会话的现有语义保留，并给出可见警告。等待超阈值不直接判定失败；不提供未经实现的取消 / 恢复按钮。同步异常、异步异常和入口模块加载失败均需有对应反馈路径。
- [ ] **回归与收尾。** 验证首次进入 Lobby、新建 / 恢复 Init、包启用集、坏包失败与回退、离线字体、刷新和重复启动；更新启动机制文档与任务实际结果，集中做直接改动范围的地图只读复核。

## 验收标准

1. 有可复现的基线和优化后报告，原始资料放入 `.test-artifacts/`；相同设备 / 包集 / 缓存条件每组至少 5 次，记录原始值、中位数和范围。冷缓存与热缓存分组，不混合平均。
2. 建议性能目标：在复现用户慢启动的配置中，“导航到 Lobby 可操作”的中位数较基线减少至少 25%；其他配置无超过 10% 且可重复的退化。此数值是待基线验证的工程目标，不是已测结论；若基线显示瓶颈在外部环境或目标不可行，先记录原因、替代目标和取舍，再调整任务，不能用只增加提示替代耗时优化。
3. 静态启动壳在主应用模块就绪前可显示；每个主要阶段都能观察到相符提示。优化后剩余的长耗时同步段需逐项说明；不能仅插入 Promise 微任务就声称已给浏览器绘制机会。
4. 等待期间显示阶段与耗时；有实际完成数时正确递增。建议超过 3 秒的阶段显示慢阶段说明；界面不出现虚假百分比、提前完成或无限“正在启动”而缺失错误信息。
5. Lobby 可操作后才结束启动状态；包加载规则、Registry 校验、包应用失败回退、存档恢复、新建 / 恢复 Init 和 Tick 启动时机保持正确。
6. 为阶段顺序、失败 / 降级、真实计数及实际改动的性能逻辑补行为 / 回归测试；不得仅以文本匹配或不稳定墙钟阈值作为自动化验收。通过 `npm test` 执行，完整输出位于 `.test-artifacts/latest.log`。按影响执行类型、架构和构建检查，并在真实浏览器核对生产预览、慢网 / CPU 降速、离线及错误路径。

## 验证与结果

### 2026-10-30：偶发重启慢的现场记录

- 用户补充：偶尔重启时前序工作等待很久，先记录日志以便反馈占比。本轮只增加观测，不在没有现场数据时裁定或优化瓶颈。
- 计时提前至静态壳内联脚本；覆盖 `main.ts` 执行前的入口加载、导航前段、八个阶段、绘制前等待、工作中的异步等待与阶段间隙。记录并行模块耗时和当前内容，模块耗时不作为互斥占比累计。
- `window.__startupLog.print()` 输出表格；`report()` 返回可序列化报告，`report(1)` / `report(2)` 读取此前两次启动。独立本机缓存仅保存最近三次，阶段边界和页面离开时写入；存储损坏或写入失败不阻止游戏启动。完成、失败及中断现场不被迟到回调覆盖，原复制诊断按钮附带同一报告。
- 待收集：用户下一次慢启动时发送当前 `report()`，如已刷新则发送 `report(1)`；区分入口加载、等待绘制、实际阶段工作，随后再按占比调查对应请求或调用链。
- 验证：启动壳、阶段编排、内容摘要及开发包读取的定向回归共 4 文件 / 20 项通过，包含入口前等待、导航耗时占比、绘制 / 工作拆分、失败现场冻结、三次日志轮换、坏缓存及写入失败降级；类型、架构、文档检查通过。生产构建输出到 `.test-artifacts/startup-log-build/` 通过，保留已有大 chunk 提示；测试日志保存为 `.test-artifacts/startup-log-tests.log`。未进行本次浏览器实测或偶发慢启动性能结论。
