# Task：Story / StoryEntry 的 Init 目录、自动归档与玩家保留记录

状态：待处理

## 目标与验收

- 目标：在每个 Init 下建立正式的故事目录。用 Mod 显式骨架、系统自动骨架、玩家持有记录的历史骨架、已载入但未编排内容的补全骨架组成一棵树，再补上作者资料、内容与阅读进度。Story Editor 和玩家「故事」工作区共用这棵树的结构与归属解析，各自应用可见性规则。
- 完成条件：现有故事编排可继续浏览，作者能管理目录并分别放置 Story 与 StoryEntry。角色目录自动生成且能按 Mod 权限编辑。玩家在当前 Init 能浏览公开内容，切换、卸载或重新载入 Mod 后，仍能定位自己持有的阅读记录，重读资格继续由现有引擎判定。下文的验收场景覆盖四种来源及相互作用。
- 边界：沿用 Story、StoryEntry、Init 的现有身份和调用语义。目录不会成为触发、跳转、分支解锁、发奖或重读的条件。首期只生成角色类自动目录，玩家只浏览当前 Init，作者可切换 Init。目录资料只支持标题、纯文本简介、现有封面资源和排序。

## 当前事实与接入点

- `Story.initId` 是作者对正文的整理维度，缺省归「其他」。`StoryEntry.availableInits` 表示入口适用的 Init，空数组表示全 Init；`owner` 表示角色归属。三者分别保留原义。参见 `src/data-services/contracts/story-node.ts`、`src/data-services/contracts/story-entry.ts` 和 [[story-and-effects]]。
- 当前 `StoryEntry.catalog` 以分类、篇章、章节和顺序编排。`withAuthoredStoryCatalog()` 把这些位置叠到 `baseStoryHierarchy`，玩家导航和作者目录弹窗都依赖这一路径。玩家旧导航还有主动入口的同 Story 日志回退。接入点见 `src/ui/columns/authored-story-catalog.ts`、`src/ui/columns/story-navigation.ts`、`src/ui/story-editor/catalog-dialog.ts` 和 [[runtime-editor-and-project-checks]]。
- 当前 `StoryService.getStoryReplayStatus()` 按 Entry 读取当前 Init 的阅读进度，并参考可精确定位 Entry 的旧投放完成记录。先核对这些记录能提供哪些身份和历史位置，再决定最小补充数据。参见 [[init-state-snapshots]]。

## 先组装目录骨架，再补充展示内容

第一步仅确定节点身份、父子关系、Init、来源与内容位置引用。第二步在已定结构上解析标题、简介、封面、挂载内容、历史提示、公开投影和统计。标题或文案变更不参与身份和父级匹配。

| 骨架来源 | 目录如何产生 | 在合并树中的作用 |
| --- | --- | --- |
| **Mod 显式编写** | Mod 在指定 Init 下声明稳定目录 ID、父目录和同级顺序，可以直接建立空目录、多层目录或在同层同时安排目录与内容。 | 正式编排的结构来源。内置目录与已有 `catalog` 在切换时先按旧路径和顺序接入；以 ID 和明确映射合并，同名异源保留各自身份。 |
| **系统隐式生成** | 从具有明确自动目录语义的数据生成。首期把角色目录放到各 Init 固定的「角色故事」下，以 Init ID 和角色 ID 确定身份。有该 Init 适用的归属 Entry，或角色所属 Mod 写了该 Init 的目录资料时生成。 | `AutoCreated` 表达生成来源及来源实体，`Manual` 表达作者声明的目录。自动角色目录的父级固定；所属 Mod 可补充资料和管理其内部子目录。后续确有第二种来源时再增加对应的生成规则。 |
| **玩家持有记录** | 当前 Init 中曾经实际读过或完成的内容，其目录或祖先已经无法从加载内容解析时，用已知的稳定路径和当时向玩家公开的标签恢复缺失层级。 | 优先复用仍存在的祖先，缺失区段以历史节点保留。若正文或 Entry 未加载，保留记录及已读/已完成状态，显示「内容未载入」，无重读动作。若只有目录消失而内容仍可用，按当前入口和引擎规则处理，历史路径仅用于保留原浏览位置。 |
| **已载入内容补全** | Story 或适用 Entry 没有可解析的显式位置或可用的自动归属时，从仍有确定依据的旧目录关系补齐缺段，其余归入该 Init 的「未归档」。缺省 Init 的 Story 在作者「其他」中兜底。 | 确保载入内容可以整理。补全位置可被作者日后明确归档取代，生成的骨架不自动写回 Mod。已经缺失的玩家内容由上一行处理，不能靠补全虚构可用入口。 |

- **节点合并按身份。** 显式目录和自动目录都有稳定身份；自动目录资料通过明确的来源引用附加，不能通过同名手动目录覆盖。历史骨架只填加载树缺失的部分，已载入节点的现行结构优先。兜底结构最后填空。选择确定性的同级顺序，以作者排序优先，值相同时用稳定身份打破平局。
- **内容位置按编排意图。** 先采用合法的显式位置，再采用符合权限的角色自动归属，最后补全。保留历史路径的条目可出现在原路径的历史视图中，但同一 Entry 只有一个当前主要位置。按稳定身份确认是同一条 Entry 后，恢复加载时将记录并回当前位置，避免历史占位与现行条目同时重复展示或计数。只有名称相同的条目不应相认。
- **损坏引用须可定位。** 作者保存及 Datapack 校验覆盖未知 Init、未知父目录、目录成环、跨 Init 父子关系、重复 ID、无权写入、Entry 放入非适用 Init。遇到已加载内容的失效位置，编辑器保留可诊断信息，浏览仍有兜底。移动目录保留 ID；删除有子目录或内容的位置时，先明确指定迁移位置或转入「未归档」，保留 Story 和 Entry 本身。

## 归档、Mod 权限与公开规则

- **Story 和 Entry 各自归档。** Story 有一个正文归档位置，沿用 `Story.initId`。为正文选择某个 Init 的目录时，界面明确显示该 Init 归属。Entry 在每个适用 Init 下最多有一个当前主要位置。全 Init 可用的 Entry 可在各 Init 的「未归档」查到，仍可按 Init 指定位置或满足角色自动归属。正文可被别的 Init 的 Entry 引用，移动正文或入口互不改位。作者能从 Story 定位引用它的 Entry，也能从 Entry 跳回正文。
- **Mod 权限在写入时核对。** 角色所属 Mod 能在其编辑态中改角色目录的标题、简介、封面、公开规则、子目录和自有内容顺序。默认标题跟随角色名，显式标题保留。权限依据实际角色来源和可写的编辑态数据包，不能仅凭目录、角色或 Entry 的 ID 前缀授予。其他 Mod 只在目录方开放收录、内容方显式添加自己的 Entry 时才能跨 Mod 挂载，自动归属也不能绕过该约束。对现有 Mod 引用和卸载行为按当前 Registry/Datapack 规则接入。
- **作者可见与玩家可见分别处理。** 作者能浏览所选 Init 的完整结构、待归档条目、来源、权限和校验提示。玩家沿用「故事」工作区，只看当前 Init。默认有可展示的 Entry 或持有的历史记录才露出目录及路径，作者可显式提前公开安全标题、简介和封面。公开父目录不自动公开隐藏子目录、Entry 或它们的数量。正文仅通过玩家可见的 Entry 浏览。
- **统计以当前 Init 的精确 Entry 为单位。** 首期展示「已读」和「已完成」，已读含已完成；父目录对子树按 Entry ID 去重。历史记录只在玩家确实持有且该记录可见时计入，同一记录恢复加载前后只算一次。沿用旧主动入口的同 Story 日志可见性，仅作为旧条目可见性的延续，不推断 Entry 的已读、已完成或重读资格。默认不展示可能泄露隐藏内容的总数。

## 历史骨架与存档接入

- 先核对已有 Entry 阅读记录、旧投放完成记录和归档相关接口。若现有记录无法在未加载时恢复目录，增加最小的按 Init 保存的可选路径元数据，记录 Entry 稳定身份、必要的目录 ID 链及当时已公开的标签。阅读与完结仍走现有状态写入边界。正式阅读或完结生效且位置可解析时留存路径；对于已持有精确进度的旧记录，当目录仍载入且公开路径可确认时，可在既有状态写入时机补记当前已知路径。仅进入编辑器、试播或重读页不得新增正式阅读记录。
- 目录快照只保存玩家当时已能看到的路径和必要标签。隐藏标题、未读故事文案和完整 Mod 目录不写入历史元数据。已知祖先用现行节点；已保存的缺失区段用历史记录；旧存档缺路径时，按可靠身份收拢到「历史未归档」，无法定位 Entry 的 Story 日志可沿用现有档案展示，不能生成精确 Entry 历史节点。若 Init 本身未载入，历史继续留在原 Init 的存档范围，待该 Init 回来时解析。
- 内容不可用时只提供记录视图。Entry 或其正文重新加载后，按相同稳定身份恢复现行目录和可用性，再由既有规则判断能否重读。验证存读档、切换 Init、禁用和重新载入 Mod 时，记录及已知路径不会被索引重建丢弃。按 [[ai/guide/conventions/architecture-discipline]] 核对新增可选元数据的状态归属和项目存档策略。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 同一 Init 同时有四种来源 | 作者声明父子目录，角色目录自动出现，未载入的已读内容保留历史层级，已载入未编排内容得到位置。相同 ID 正确合并，同名不同来源不合并，输出顺序稳定。 |
| 同一正文被两个 Init 的 Entry 引用 | 正文归档独立。各 Init 只看自己的适用入口及进度。全 Init Entry 在不同 Init 可分别归档和统计，默认也可找到。 |
| 角色目录的所有权和跨 Mod 挂载 | 角色改名后目录身份不变。角色所属 Mod 可保存资料。外部 Mod 无权改资料，且双方明确选择后才可挂入其自有 Entry。导出再导入保留合法配置。 |
| 目录或 Mod 卸载后存读档，再重新加载 | 已持有内容按可恢复路径保留，缺失正文或 Entry 时没有重读动作。旧记录缺路径时进入「历史未归档」。重载后记录随稳定身份恢复，已读和已完成数量不翻倍。 |
| 作者提前公开一段简介，目录还有隐藏 Entry | 玩家可看简介，隐藏条目、标题、子目录和数量不会从树或父目录统计泄露。显式禁止重读的 Entry 可保留已读记录；仅有旧同 Story 日志的入口不增加精确进度。 |
| 旧编排、作者移动和异常目录引用 | 原有分类、篇章、章节和条目顺序接入新树。改名和移动保持引用及进度。非法结构给出可定位提示，其余目录仍可浏览。 |

用定向行为测试覆盖合并、权限、存档、公开和重读边界。通过 `npm test` 运行相关用例，按项目规则保留日志；契约改动同步生成 Schema 并检查类型和文档。宽屏浏览器走查聚焦作者移动与定位、玩家浏览以及内容未载入的提示。
